## [2026-11-11] 브라우저 틱의 «깨움 기다리며 헛돌기»를 수로 가르고, 호스트 깨움(opt-in)으로 돌려준다 (wie-featurephone-tick-busy-wait-heat-measure-and-host-yield)

**무엇을**
- 계측 하네스 `wie-backend/src/tick_occupancy.rs`(시험 전용)를 넣었다. 모의 vsync·모의 시계에서 실제 `Executor`·`SpeedClock`·`FramePacer::budget_for_period_us`·`AchievedSpeed` 를 돌려, 프레임의 벽시계를 {에뮬레이션, 틱 안 깨움 대기, 호스트 몫} 으로 가른다. `cargo test -p wie-backend tick_occupancy -- --nocapture` 가 아래 표를 찍는다.
- 호스트 깨움(opt-in). 엔진 쪽은 `Executor::tick_for(…, max_wait)` 와 `Platform::wake_margin_ms()`(기본 `None` = 종전) 와 `SpeedClock::wake_delay` 다. wasm 쪽에는 `set_wake_margin(ms?)` · `wake_in_ms()` · `wake_tick()` 3개를 더했다(계약 `methods` + `hostWakeNote`). 호스트 계약 전문은 `wie_featurephone/src/lib.rs` 크레이트 문서 «Host wakes» 에 있다.
- `scripts/audio-probe.mjs` 에 `--wake-margin <ms|off>`(반복 가능)와 `--browser webkit` 을 더했다. 실행마다 `busy %` 를 낸다. busy % 는 `tick()`·`wake_tick()` 안에서 보낸 벽시계 비율, 곧 엔진이 메인 스레드를 쥔 몫이다.
- 계약 `artifacts.maxBytes["wie_web.js"]` 를 40,000 → 42,000 으로 올렸다. 같은 툴체인 로컬 빌드 기준 39,859 → 40,710 B 다.

**왜.** 운영자 신고(아이폰 17 Pro Max · 발열 · 충전 멈춤 · «2배속 탓인가») 때문이다. `executor.rs` 는 모든 태스크가 잠들었고 박자 잡힌 깨움이 예산 안에 있으면 시계를 읽으며 그 시각까지 돈다(메이플스토리2007 sleep(60) 격자 수정). 그 몫이 발열의 얼마인지 아무도 재지 않았다.

### 1. 점유율 표 — before(현행) / after(호스트 깨움 ε=3 · 타이머 지연 0~3 ms 균등)

모델: 바쁜 게스트 = 0.5 ms 조각마다 yield, 영원히. 수면 게스트 = 한 게임 프레임 2~4 ms 일(무작위 — 고정값이면 위상이 잠긴다) 뒤 `sleep(n)`. 메뉴 = 1 ms 폴(`POLL_SLEEP_MS`).
rAF 콜백은 vsync 뒤 0~1 ms 에 온다. 시계 읽기 1회 = 1 µs. 10 s 를 돈다. 레인 CPU 와 무관한 «모의 시계 비율»이다.
열은 순서대로 em(에뮬레이션)·wait(틱 안 깨움 대기)·busy(합)·late(sleep 이 늦게 깬 게스트 ms, p50/max)·frames(게임 프레임 수)·achieved 다.

- **⒜ 바쁜 타이틀은 헛돌기가 0.2% 다.** 발열이 곧 에뮬레이션이다(60Hz 88% · 120Hz 63~69%). 호스트 깨움은 손대지 않는다(시험이 before == after 를 단언).
- **⒝ 수면 박자 타이틀은 60Hz 에서 헛돌기가 엔진 몫의 절반~2/3 이다**(sleep(60) 1배 10.6/15.3 · sleep(20) 2배 45.9/67.5). 호스트 깨움이 그것을 ε 수준으로 줄인다.
- **대기 몫은 위상에 따라 출렁인다.** 게임 주기가 프레임 격자와 맞물리면(sleep(60) 2배 = 30 ms ≈ 2프레임 · sleep(20) 1.5배) 깨움이 늘 예산 밖 틈에 떨어진다. 그러면 현행은 거의 안 돌고 «대신 늦게» 깬다(late max 4~7). 그런 칸에서는 after 의 대기가 before 보다 많다(ε 만큼 · 박자는 정확해진다). 120Hz 는 예산이 5 ms 라 돌려줄 대기가 원래 적다.
- 덤: 현행은 수면 박자 게임을 조금 늦게도 돌린다(sleep(20) 2배 60Hz: 게임 프레임 719 · achieved 1.874). 호스트 깨움이면 767 · 2.000 이다.

### 3. ε — 잰 값

- 타이머 지연을 쟀다(`setTimeout`, 3~20 ms 지연, 300표본 × 2회, headless, 스크립트 = 증거 디렉터리 `timer-jitter.mjs`).

  | 엔진 | rAF 에서 건 타이머 p50 / p99 / max | 타이머 300개 연쇄(중첩) p50 / max |
  |---|---|---|
  | WebKit | 1 / 3 / 3 ms | 3~4 / 7 ms |
  | Chromium headless | 3 / 10 / 10 ms | 3 / 10.5 ms |
- 하네스로 ε 를 쓸었다(sleep(60) · 1배 · 60Hz). 지연 0~3 ms 에서 ε=3 이면 wait 1.7% · late max 0 이다. ε=2 면 0.7% · max 1, ε=0 이면 0.0% · max 3 이다. 지연 0~10 ms 에서는 ε=6 이어도 max 4 다.
- 그래서 **권장 ε=3**(WebKit, 아이폰의 모든 브라우저)이고, 타이머는 «rAF 틱 뒤에서» 건다. 연쇄가 짧아야 중첩 클램프(4 ms)를 안 탄다. ε 는 셸이 넘기는 손잡이로 뒀다(브라우저마다 다르다).

### 4. 불변 — 지킨 것과 근거

- **sleep(60) 박자**: 기준선(현행 하네스) late max 는 2~7 게스트 ms 다. 호스트 깨움은 모든 칸에서 그 이하다(0~1). 시험 `a_paced_sleep_keeps_its_timing_when_the_host_wakes_it` 이 sleep(60)·sleep(20) × 3배속 × 2주사율에서 late max·p50 ≤ 기준, 게임 프레임 수 ≥ 99% 를 단언한다(지연 0~3 ms 모의 타이머 포함).
- **영웅서기4 `POLL_SLEEP_MS`**: 양보 판정은 `paced` 만 본다. 1 ms 폴은 종전대로 틱을 살리지 않는다. 기존 `test_tick_does_not_wait_for_a_1ms_poll` 이 불변이다.
- **`achieved_speed`**: 정의는 그대로다. 하네스가 매 틱 `AchievedSpeed` 를 먹이고 «≤ 배속 · 현행의 99% 이상»을 단언한다. 실측은 −0.7%(sleep(60) 2배 120Hz) ~ +6.7%(sleep(20) 2배 60Hz)다.
- **60Hz/120Hz 예산 규칙**: rAF 틱은 종전대로 `FramePacer` 예산을 쓴다. `wake_tick` 은 `FramePacer` 를 건드리지 않는다(간격을 빠른 화면으로 읽는다). 예산은 «직전 rAF 예산 + ε»다. ε 를 더하지 않으면 깨움 전 대기가 게스트 조각을 먹어 2배·120Hz 에서 게임 프레임이 291/298 로 줄었다.
- **기본 동작 불변**: `set_wake_margin` 을 안 부르는 호스트(`wie_validate`·네이티브·현행 핀 셸)는 `max_wait = None` 이다. 엔진 코드 경로가 종전과 같다. 기존 시험 전건 green(`cargo test --all`).
- **개악 대조**: ⒜ 양보 제거(`max_wait` 판정 무력화) → `the_host_wake_hands_back_the_wait` 를 포함해 3건 RED. ⒝ ε 제거(`wake_delay` 가 margin 을 안 뺌 → 타이머가 깨움 시각에 걸려 지연만큼 늦음) → `a_paced_sleep_keeps_…` RED. 둘 다 최종 코드에 한 건씩 넣고 `cargo test -p wie-backend tick_occupancy` 로 확인했다.

### 5. 「2배속이 점유를 얼마나 올리는가」

- **CPU 를 계속 쓰는 무거운 게임**: 2배속이어도 점유가 그대로다(60Hz 88.2 → 86.7%). 이미 프레임 예산을 다 쓰고 있어서 2배속은 «더 빨라지지 못할» 뿐이다(achieved 0.84 → 1.68). 이 게임들은 배속과 무관하게 뜨겁다.
- **sleep 박자로 도는 가벼운 게임**: 2배속이면 게임 일이 2배다(에뮬레이션 4.7 → 9.0% · 12.8 → 21.6%). 현행은 그 위에 깨움을 기다리는 헛돌기까지 붙는다. sleep(20) 류는 60Hz 에서 39.8 → **67.5%**(1.7배)로 오르고, 그중 46%p 가 헛돌기다.
- 호스트 깨움을 켜면 같은 2배속이 18.2 → **34.5%** 다. 일이 2배인 만큼만 오른다. 실엔진(`pace_j2me`)도 Chromium 2배 busy 20~36% → 10.3~10.5%, WebKit 19~23% → 13~15% 였다.
- **답**: «2배속 탓»은 가벼운 게임에서 반쯤 맞다. 일이 2배라서 오르는 몫은 정상이다. 헛돌기 몫이 거기 붙어 부풀리던 것이고, 이 PR 이 그것을 걷어낼 표면을 낸다. 무거운 게임의 발열은 배속과 무관하게 에뮬레이션 그 자체다(아래 6).

### 한계

- 기기 계측은 없다. 아이폰의 발열·충전 멈춤과의 연결은 «엔진이 메인 스레드를 쥔 비율»까지만 잰 것이다. 블릿·합성·오디오 워클릿은 호스트 몫 열에 섞여 있고 따로 재지 않았다.

- 하네스의 일 비용(조각 0.5 ms · 프레임 2~4 ms)은 합성값이다. 실엔진 대조 1종(`pace_j2me`)이 방향과 크기를 확인했을 뿐, 타이틀 분포(바쁨 대 수면 비율)는 재지 않았다.
