### 1. 예산 — 어디서 깎고 어디서 나오나

```rust
// wie-core-arm-aot/src/lib.rs
pub struct RunFrame { …, pub budget: u32 }            // 이 호출이 더 돌 수 있는 게스트 명령 수 · Default 는 u32::MAX

// wie-core-arm/src/engine/arm32_cpu.rs · Arm32CpuEngine::run
budget: count - budget_consumed,                      // 건넨다
budget_consumed = count - frame.budget.min(count - budget_consumed);   // 돌려받는다

// wie-core-arm-native/src/codegen.rs
left = budget − 1                                     // 명령 머리 — 건너뛴 조건 명령도 센다(해석기도 한 걸음으로 센다)
pc ← 다음 명령; brif(left, 다음 명령, dispatch)       // Emitter::commit — 영역 안의 간선: 남았을 때만 넘어간다

// wie-core-arm-native/src/lib.rs · NativeExecutor::execute
if pc < 0x1000 || pc == frame.end || frame.budget == 0 { return Ok(CompiledExit::Dispatch); }
```

- **세는 단위는 해석기와 같다.** 영역 함수는 명령 머리에서 하나를 깎고, 다음 명령으로 가는 영역 안의 간선에서 «남았는가»를 본다. 다했으면 다음 명령의 PC 를
  적은 채 `Dispatch` 로 나온다 — 해석기가 예산이 다한 실행을 멈추는 자리와 같다(다음 명령은 아직 돌지 않았다). 엔진 루프는 돌려받은 값으로
  `budget_consumed` 를 맞추고 종전 순서(끝 주소 → 예산)대로 `End` 나 `Yield` 를 낸다.
- **영역 진입에서 한 번 더 본다**(`guard(left == 0)`). 엔진은 예산이 0 인 채로 들어오지 않지만 프레임은 바깥 입력이다 — 0 에서 깎으면 `u32` 가 한 바퀴 돈다.
- **실행기는 예산이 0 이면 다음 영역으로 잇지 않는다.** 이 줄이 없으면 다음 영역이 진입 검사에서 PC 를 그대로 둔 채 나오고, 이어 부르기 루프가 그 PC 를 다시
  찾아 끝나지 않는다.
- **폴트한 명령은 깎은 것을 돌려준다**(폴트 블록의 `+ 1`). 널 읽기는 `InterpretOne` 으로 해석기에 넘어가 거기서 세어진다(0608 §2). 돌려주지 않으면 예산이 1 인
  실행은 컴파일된 시도에서 예산을 다 쓰고 해석기 차례가 오기 전에 내주기를 되풀이한다(§5 의 변이).
- **남은 예산은 게스트 레지스터가 있는 자리에 둔다**(`Emitter::budget`): 보통 영역은 프레임의 칸을 읽고 쓰고, 레지스터를 호스트 지역 변수에 올려 두는 루프
  (`cache_loop`)에서는 예산도 지역 변수에 두었다가 나갈 때 한 번 적는다.
- **세지 않는 실행기는 그대로다.** `RunFrame::default()` 의 예산은 `u32::MAX` 라 예산을 건네지 않는 호출(upstream 시험 · `wie-web` 의 warmup)은 종전처럼
  영역이 끝날 때까지 돈다. wasm 실행기(`wie-web`)는 칸을 건드리지 않으므로 엔진이 0 을 더한다 — 종전과 같다(브라우저에는 배선돼 있지 않다).
- 캐시 키에 `offset_of!(RunFrame, budget)` 를 더했다. `size_of::<RunFrame>()` 이 80 → 84 라 옛 지속 캐시는 그것만으로도 빗나간다.

**나올 때 적히는 값 — 한 가지 달라지는 점.** upstream 의 영역은 «뒤에서 덮이기 전에 아무도 읽지 않는» 레지스터 기록과 플래그 갱신을 빼고 만든다
(`eliminate_dead_alu_stores` · `live_flag_updates`). 예산으로 나오는 자리가 그 사이일 수 있다: 그때 프레임에는 그 값이 적혀 있지 않다(만들어 내지 않는다).
스레드가 어디서 이어 돌든(다시 컴파일된 코드든 해석기든) 다음에 도는 명령들이 그 값을 덮으므로 게스트는 보지 못한다. 보는 쪽은 그 사이에 스레드의
레지스터를 읽는 호스트 코드뿐이다 — GC 의 보수적 루트 훑기는 «안 쓰이는 값»이 낡았을 뿐이라 영향이 없다. 시험의 조각 대조(§5)는 그래서 죽은 값이 없는
프로그램으로 레지스터 · 플래그 전부를 견준다.

- 그래서 검사를 옮겼다(`982c4c009`). 명령마다 블록을 새로 만들지 않고, 명령 사이에 이미 있는 간선(`Emitter::commit` 의 `jump`)을 «남았으면 다음 명령, 아니면
  `dispatch`»로 바꿨다. upstream 은 영역을 떠나는 간선에서만 PC 를 적는데(«Internal edges need no published PC») 이제 영역 안의 간선도 떠날 수 있으므로
  거기서도 적는다.
- **release 에서는 절반만 돌아왔다**(§3 의 첫 화면 표). LGT 는 컴파일 대기 0.97 → 0.75초(main 0.55), KTF 는 1.60 → 1.65초로 그대로다(main 0.84).

  예산 칸과 PC 칸에 쓰는 값이다).
- **남은 컴파일 비용의 원인은 «명령마다 조건부 탈출 간선 하나»다.** 간선의 검사와 PC 적기를 빼고 깎기만 남긴 스크래치 변형(`variantV1-decrement-only.patch` ·
  선점은 안 된다 — 원인을 가르려고만 지었다)의 컴파일 대기는 KTF 1.04초(첫 회 2.02 는 빌드 직후) · LGT 0.55 · 0.60초로 main(0.80 ~ 0.83 · 0.52 ~ 0.53)에
  붙고, 피크 RSS 도 438 ~ 443 · 299 ~ 310 MB 로 main + 30 MB 다. 같은 묶음의 이 PR 은 1.58 ~ 1.68 · 0.79초 · 537 ~ 550 · 332 ~ 340 MB 였다.
  영역의 명령은 전부 바깥에서 들어올 수 있는 진입점이라 명령마다 블록이 하나씩 있고, 거기에 조건 분기가 붙으면 cranelift 가 다룰 간선이 명령 수만큼 는다.
