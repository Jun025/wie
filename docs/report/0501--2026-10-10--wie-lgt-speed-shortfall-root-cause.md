## [2026-10-10] LGT 표본 배속 미달 원인 가르기 — 게스트 루프 «일 + 고정 10 ms» 구조 × 프레임당 엔진 CPU (wie-lgt-speed-shortfall-root-cause)

### 결론

남는 미달은 **게스트 루프 구조와 엔진 경로의 곱**이다. 측정 창은 원인이 아니다.

- 두 표본 모두 프레임마다 «일을 하고 → 끝에서 `MC_knlSetTimer(10)` 을 다시 건다»(아래 계수: 건 타이머 전건 10 ms · `pace_from` 전건 0).
  배속 시계는 그 10 ms **대기만** S배 줄인다. 일(프레임당 CPU `a`)은 벽시계로 그대로다. 그래서 프레임 주기는
  `a + 10/S`(벽 ms)이고, 달성 배속 = **`(a + 10) / (a + 10/S)`** — S→∞ 에서도 상한 `(a + 10) / a`.
- 이 한 줄이 아래 네이티브 표 8칸을 **오차 3% 안**에서 맞춘다(최대 −2.5% · `a` 는 1배 칸에서만 뽑았다 = `12000 / 1배 수 − 10`).
  `287af341` a ≈ **5.2 ms**(2배 → 1.46 · 상한 2.9) · `863b8ab6` a ≈ **12.8 ms**(2배 → 1.26 · 상한 1.78 — **어떤 시계로도 2배가 안 된다**).
- 0494 의 수수께끼(«창 안 tick 대부분 짧음 = CPU 포화 아님인데 왜 미달?»)는 이것으로 풀린다: 일과 대기가 **직렬**이라
  대기 시간에 남는 CPU 를 다음 프레임이 쓸 수 없다. 2배에서도 `287af341` 은 창의 약 절반을 대기 스핀으로 보낸다(아래 `spin`).
- `a` 의 내용(호스트 프로파일): `287af341` 은 **프레임 하나에 `MC_grpDrawLine` ≈210회, 그때마다 프레임버퍼 «전체»를 게스트 메모리에서
  읽어 오고 다시 쓴다** — 타이머 콜백 시간의 **65%**. `863b8ab6` 은 ARM 해석 57% · 같은 전체 복사(`MC_grpFillRect` ≈133회/프레임) 18%.
- ⇒ 고칠 수 있는 몫은 «엔진 경로»(프레임버퍼 전체 복사)뿐이고, 그것으로도 `863b8ab6` 은 2배에 못 닿는다(추정 1.26 → 1.32). 제안은 worklog 1건(별 PR).

### 방법

- 빌드: 전 = `4bf649ff`(#531 착지 전) · 후 = `ac7271e4`(#531 머리 — 착지 `48bcfdc0` 과 Rust 차이는 #530 배속 상한 3→2 뿐이라 [1, 2] 측정에 무관).
  각각 release `wie_validate`. 배속 범위는 운영자 정정(1~2배)대로 {1, 1.5, 2}.
- 창: 0494 그대로 게스트 시간 [12 s, 24 s](`--frame-hz 60 --speed S --pacing 12/S --timeout 24/S`). 지표 = 그 창의 WIPI 타이머 발화 수.
- ★**부하 분리 — 게스트 시계를 스레드 CPU 시간에 묶었다**(스크래치 · 커밋 0): 측정 내내 load1 30~90(10코어 · 다른 레인 스윕)이라
  벽시계 기준 수는 «이 프로세스가 받은 코어 몫»을 잰다(첫 회 벽시계 실행: 받은 몫 25~50%). 그래서 `HeadlessPlatform::now()` 와
  창·기한을 `CLOCK_THREAD_CPUTIME_ID` 로 돌렸다 = «코어 하나를 전용으로 가진» 실행. 대기 스핀도 CPU 를 쓰므로 시계가 그대로 간다.
  반복 2회 차이 ±2% 안(아래) — 부하가 load1 30 → 62 로 바뀌어도.
- 스크래치 계수기(커밋 0): 실행기 `wait_until` 스핀 시간 · 태스크 폴 시간 · 타이머 콜백 CPU · GC · 틱 종료 사유 · `MC_knlSetTimer` 인자 분포 · `pace_from` 종류.
- 호스트 프로파일: macOS `sample` 12 s(1배 · 벽시계 release · 주 스레드 8,912 표본) — 포함(inclusive) 표본 수.
- 그리기 호출 수: `RUST_LOG=wie_wipi_c=debug` 8 s 실행에서 API 이름 계수.

### 브라우저 표(0498)도 같은 모형으로 맞는다

0498 의 60Hz 브라우저 수(후 빌드)를 같은 식으로 읽으면:

- `287af341`: 1배는 #531 이후에도 **틱당 1회 = 60/s 에 묶여** 있다(719/12 s — 게임 자체 속도는 1000/15.2 = 66/s).
  1배가 묶여 있어 거기서 `a` 를 뽑을 수 없으므로 2배 수(552~562)에서 거꾸로 풀면 wasm `a` ≈ 5.8 ms — 네이티브 5.2 ms 와 가깝다
  (예측이 아니라 정합 확인이다). ⇒ 남는 0.45 는 상한이 아니라 프레임당 일이다. 0498 이 «tick p99 16~17 ms = 틱 안의 일감»이라 쓴 결론과 같은 방향이지만,
  그 근거(tick 길이)는 대기 스핀(`wait_until` — 실행기가 예산 안의 타이머를 «돌면서» 기다린다)도 포함하므로 일의 증거는 아니었다. 이 회차의 콜백 CPU 가 그 증거다.
- `863b8ab6`: 1배 450~467 에서 뽑은 wasm `a` ≈ 16 ms 로 **예측** 2배 1.24, 실측 후 1.30 · 전 1.40(각 단발 · 벽시계 · load1 31~67). 타이머 상한과 무관(0498 결론 그대로).

### 프레임당 일 `a` 의 내용 — 호스트 프로파일 (1배 · 주 스레드 · 포함 표본)

| | 타이머 콜백 | ARM 해석(`Cpu::step`) | `MC_grpDrawLine` | `MC_grpFillRect` | 전체 복사(`FrameBuffer::canvas` + `FramebufferCanvas::flush`) |
|---|---|---|---|---|---|
| `287af341` | 4,498 | 465 (10%) | 2,893 (64%) | 204 | **2,932 (65%)** |
| `863b8ab6` | 6,436 | 3,685 (57%) | 0 | 1,504 (23%) | 1,133 (18%) |

(괄호 = 콜백 대비. 그 밖은 `wie_validate` 자신의 `frame_richness`·해시 — 브라우저엔 없다.)

- 경로: `wie-wipi-c/src/api/graphics/framebuffer.rs` — `FrameBuffer::canvas()` 가 `data()` 로 버퍼 크기만큼 `vec![zeroed]`(큰 할당 →
  `madvise`)를 만들고 게스트 메모리 전체를 읽어 오며, 그리기 한 번 뒤 `flush()` 가 전체를 다시 쓴다. **기본 도형 하나마다** 240×320×2 B 를 두 번 옮긴다.
- 호출 수(8 s): `287af341` `MC_grpDrawLine` 97,272 / `MC_knlSetTimer` 464 = **프레임당 210회** ·
  `863b8ab6` `MC_grpFillRect` 40,012 / 300 = **133회** (+ `MC_grpCopyFrameBuffer` 1회).
- 프로파일 비율로 본 추정(측정 아님): 전체 복사를 없애면 `a` 가 `287af341` 5.2 → ≈1.8 ms(2배 1.46 → ≈1.74) ·
  `863b8ab6` 12.8 → ≈10.5 ms(1.26 → ≈1.32). 1배 자체도 빨라진다(같은 식) — 그건 화면 갱신 수가 느는 것이고, 원래 기기의 주기에 대해선 말할 수 없다.

### 가르지 못한 것 · 하지 않은 것

- **`863b8ab6` 의 게임 진행이 «프레임 수»인지 «시각»인지는 못 갈랐다.** 프레임마다 `MC_knlCurrentTime` 을 3회 읽는다(899/300) —
  시각 기반이면 2배에서 프레임 수는 1.26배여도 «음표 진행»은 2배일 수 있다(타이머 수 지표가 진행을 덜 센다).
  키 없는 첫 화면을 게스트 시각 0.25 s 간격으로 1·2배 찍어 맞춰 봤으나 반복 애니메이션이라 같은 화면이 여러 시각에 다시 나와
  (자기 주기 1배 7.25 s · 2배 5.75 s — 두 가설 어느 쪽도 예측하지 않는 값) 판정을 못 했다. `287af341` 은 화면이 정지해 있어(28/28 같은 바이트) 묻는 것 자체가 무의미하다.
- **배속 의미를 바꾸는 처방(대기를 S배보다 더 줄여 프레임률을 맞추기)은 제안하지 않는다.** ⑴`863b8ab6` 은 대기를 0 으로 해도 상한 1.78이라 2배가 안 되고
  ⑵타이머가 게스트 시계보다 빨리 울리면 시각을 읽는 게임(바로 위)에서 시계와 타이머가 어긋난다. 이득이 두 표본 중 하나뿐이고 위험은 전체라 이번엔 남기지 않았다.
- `wie_validate` 의 SKT·KTF 미달(0494)은 범위 밖이다.

### 사용자 영향

코드 변경 없음(문서 회차). 배속 슬라이더에서 일부 LGT 게임이 2배로 안 빨라지는 이유가 «버그»가 아니라
«프레임마다 하는 일이 벽시계로 고정이고 게임이 그 끝에서 10 ms 를 쉰다»는 구조임을 확정했다. 줄일 수 있는 몫(그리기마다 화면 전체를 복사)은 별 PR 로 제안한다.
