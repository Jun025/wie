## [2026-09-20] 개명 이전 경로를 «git 에게 물어» 되찾았다 — 제안이 예고한 대가는 둘 다 실측으로 거짓이었다 (wie-census-map-provenance-offset-and-engine-paths-p1)

채택 제안 `2026-09-19-census-map-provenance-offset-and-engine-paths#p1` 의 이행.
「엔진 경로를 옛 이름까지 따라가게 할지 정하라」 — **따라가게 했다.**

### 무엇을

`scripts/game-lab-census-map.mjs` 의 엔진 커밋 계수가 **개명 경계에서 멈추던 것**을 고쳤다.
2026-09-19 회차가 `ENGINE_PATHS` 리터럴을 `cargo metadata` 도출로 바꾸면서 「오늘의 배치」만
보게 됐고, 그 대가로 7월 기준선의 엔진 커밋 수가 **269 → 153(43% 소실)** 로 내려가 있었다.

`historicEnginePaths()` 를 신설해 **git 자신의 개명 기록**(`git log --diff-filter=R -M
--name-status`)에서 «과거의 엔진 경로»를 도출한다. 목적지가 cargo 도출 집합 안에 드는 개명 쌍의
출발지가 곧 «한때 엔진이었던 경로»다. 최소 부동점까지 돌려 **998쌍 → 280경로**(네 시대:
`crates/wie_*` · `wie_impl_*`/`wie_vendor_*` · `wie_*` · 오늘의 `wie-*`)를 얻는다.
**7월 기준선 153 → 259.**

### 왜 지금인가

제안이 남긴 유일한 미결이 「깊이를 되찾을 것인가」였고, 이 표를 읽는 사람이 보는 수가
**실제의 57%** 인 채로 한 회차를 더 넘기면 그 수가 인용된다.

### 대가 — 제안이 예고한 두 가지는 «둘 다 거짓»이었다

제안 원문의 tradeoff: 「옛 이름을 더하면 그것이 곧 **리터럴 목록의 부활**이고, 이번 회차가
기각한 두 벌 문제가 그대로 돌아온다. git 은 여러 경로에 `--follow` 를 지원하지 않으므로
**자동 추적도 값싸지 않다**.」

- **⑴ 「리터럴의 부활」 — 아니다.** 크레이트 이름을 **한 글자도 타이핑하지 않는다.** git 이 이미
  가진 개명 기록을 묻는 **두 번째 도출**이지 진실의 두 번째 사본이 아니다. 2026-09-19 회차가
  기각한 것은 「사람이 적은 목록이 조용히 드리프트한다」였고, 여기에는 적을 목록이 없다.
- **⑵ 「값싸지 않다」 — `git log` 한 번이다.** loadavg ≈75 에서 **0.35~1.15초**(5회). loadavg ≈205
  에서는 2.7~5.0초였으니 **초가 아니라 비를 읽어라.** `--follow` 는 애초에 필요 없다 —
  개명 쌍을 전수로 받아 뒤에서 거르면 된다.

**실제 대가는 다른 것이고, 그것은 적는다**: 도구 1회 실행에 `git log` 전수 개명 탐지 1회가 붙는다.
이 생성기는 CI 에서 돌지 않고(`.github/` 참조 0) 손으로만 도는 ~1초짜리 도구라 그 비용을 냈다.

### 되찾은 것이 «리터럴이 물던 것»과 같은지 — 대조

최근 90일, `git rev-list` 양쪽 전수 비교:

| 집합 | 90일 | 7월 기준선 |
|---|---|---|
| 리터럴 globs (~2026-09-19) | 65/90일 · **304** · p50 1 / p90 2 / MAX 4 | 269 |
| cargo 도출만 (2026-09-19) | 56/90일 · **168** · p50 1 / p90 3 / MAX 6 | 153 |
| cargo + 도출 historic (이번) | 65/90일 · **294** · p50 1 / p90 2 / MAX 4 | **259** |

★**이번 집합이 리터럴의 «진부분집합»이다** — 리터럴에 없는데 이것이 세는 커밋 **0건**,
리터럴이 세는데 이것이 안 세는 커밋 **10건**. ★그 10건은 **한 건씩 읽었고**, 「전부 의도한
좁힘」이라는 손쉬운 요약은 **거짓**이다 — 네 부류다:

| n | 무엇 | 출처 |
|---|---|---|
| 4 | `wie-web/src` 의 TS·CSS·HTML 절반 | `0182` `limits[]`(cargo 는 `src/rust` 만 보고한다) |
| 4 | `wie_jvm_support/tests`·`wie_midp/tests` | `0182` 가 **리터럴이 «잘못» 물었다**고 지목한 base-swap 고아 3파일 |
| 1 | `wie_tauri` | `0182` `limits[]`(`wie_app` 은 `7a439bd0` 이 워크스페이스 밖에 뒀다) |
| 1 | ★`bfa1ef2f` | ★**좁힘이 아니다** — 병합 커밋이고 `git rev-list` 는 주어진 경로에 대해 부모와 TREESAME 인 병합을 떨군다. 거친 `wie_*` 는 TREESAME 이 아니고 `wie_cli/src/bin` 은 TREESAME 이라 갈렸다 ⇒ **경로 세분도 × 병합 단순화**이지 커버리지가 아니다 |

⇒ **깊이는 되찾고 기각된 것은 되살리지 않았다.** ★마지막 1건은 아무도 예측하지 않았고,
적어 두는 이유는 「10건 전부 의도한 좁힘」이 **쓰고 싶어지는 문장이면서 거짓**이기 때문이다.

### «살아 있는 이름»은 버린다 — 그리고 그 판정은 «디렉터리»가 아니라 «경로»다

HEAD 에 아직 존재하는 후보는 뺀다. 살아남은 이름은 역사가 아니라 **cargo 가 일부러 빌드하지
않는 살아 있는 경로**이고, 그것이 바로 리터럴이 물어서 제거된 부류다.
실측: 후보 285 중 생존 5(`src`·`wie_cli/src` — 이미 cargo 경로라 무영향 — 그리고 `test_data`·
`wie_jvm_support`·`wie_midp`), 실제 탈락 3이 7월 깊이 **270 → 259(11커밋)** 를 치른다.

★**경로 단위 판정이 값을 한다**: `wie_jvm_support/` 는 고아 `tests/*.rs` 3개로만 살아 있고
`wie_jvm_support/src/` 는 **완전히 사라졌다**. 디렉터리 이름으로 판정하면 진짜 개명 이전
엔진 작업 11커밋을 함께 버린다.

### 사람이 읽는 줄에 «깊이»가 붙는다

제안의 tradeoff 는 「아무것도 하지 않고 깊이는 근사치라고 **헤더에 적는 편**이 맞을 수 있다 —
지금 코드가 그렇게 하고 있다」고 했다. ★**그 문장은 소스 주석에 대해서만 참이었다** — 표를 읽는
사람이 보는 **출력 헤더에는 그런 고지가 없었다.** 이제 세 상태를 말한다(침묵 없음):

```
★★ STALE — the engine moved 259 commit(s) … · 106 of them found under 280 pre-rename path(s) this tree no longer uses
★★ STALE — … · none of them touch any of the 280 pre-rename path(s) checked
★★ STALE — … · ★depth UNMEASURED — git did not hand over its rename records, so this count stops at the newest rename and is a FLOOR
```

★셋째가 중요하다 — 개명 기록을 못 받으면 **조용히 작아진 수**(= CURRENT 쪽 편향)가 나오는데,
그것이 이 파일이 존재 이유로 삼은 단 하나의 금지 방향이다. `null` 을 삼키지 않고 FLOOR 라고 말한다.
CURRENT 판정에는 이 꼬리를 **깊이를 못 쟀을 때만** 붙인다(붙일 커밋이 없는데 붙이면 잡음이다).

### 개악 — 양방향 (전건 제품 호출부 실행 · 이 저장소에 scripts/*.mjs 시험 하네스가 없다)

| 축 | 개악 | 결과 | 판정 |
|---|---|---|---|
| BASE | — | 259 · historic 106 · 280경로 | green |
| M1 | historic 을 계수에서 뺀다 | **153** · 「none of them touch」 | red |
| M2 | HEAD 생존 필터 제거 | **270** · 285경로 | red |
| M3 | git 개명 기록 조회 실패 | **153** · **★depth UNMEASURED … FLOOR** | red |
| M4 | 쌍 순서 뒤집기(oldest-first) | 259 · 106 · 280 — **BASE 와 동일** | green(불변식) |
| M5 | 부동점을 1패스로 제한 | 259 · 106 · 280 — **불변** | ★판별 못 함 |
| M5b | 1패스 **+** 순서 뒤집기 | 259 · 106 · **125경로** | red(경로집합만) |
| M6 | 목적지 검사 제거 | **262** · 109 · 299경로 | red |
| 원형 복귀 | — | 259 · 106 · 280 | green |

★**M5 가 판별하지 못한 것을 숨기지 않는다** — 오늘의 이력에서는 1패스로도 같은 답이 나온다.
부동점 루프가 지키는 것은 **커밋 수가 아니라 «경로 집합의 재현성»**이고(M5b), 그 구분은
주석에 적었다. ⇒ **읽어야 할 수는 커밋 수이지 경로 수가 아니다.**

### ★M4 가 «내 코드의 결함»을 잡았다 — 순서 의존이었다

초판 폐포는 `under(from, set)`(출발지가 이미 엔진이면 건너뜀) 가드를 썼다. 그것은 **단조가
아니어서** 같은 저장소·같은 입력에 대해 git 기본 순서(newest-first)로는 **35경로/248커밋**,
뒤집으면 **78/259** 를 냈다. 두 답 중 어느 쪽을 보고 있는지 읽는 사람이 알 방법이 없다.
⇒ 목적지 검사만 남겼다(단조 ⇒ 최소 부동점 존재 ⇒ 순서 무관). 두 순서 모두 **280/259**.
★그리고 그 가드를 빼자 `wie_jvm_support/src`·`wie_midp/src` 의 **11커밋이 정당하게 되돌아왔다**
— 위 「경로 단위 판정」이 바로 그 자리다.

### ★기각한 최적화 하나 — 「명백히 동치」인데 아니었다

계수와 **같은 `--since`** 로 개명 스캔을 좁히는 것: 「창이 열리기 전에 사라진 경로는 창 안에
커밋을 가질 수 없다」 — 논리가 맞아 보이고 몇 배 빠르다(0.06~0.19초 vs 0.35~1.15초).
**실측은 거짓**: 되찾는 보정이 2026-09-10 에서 +3 → +1, 2026-09-01 에서 **+34 → +2** 로 떨어진다.
근인 — 이 트리는 **upstream base swap** 을 먹어 이력이 선형이 아니다. HEAD 에서 도달 가능한
커밋이 «개명이 없던 계보» 위에 앉은 채 커밋 날짜만 창 안일 수 있다. **`--since` 는 날짜로 거르지
조상 관계를 따르지 않는다.** 그 두 델타를 다시 재지 않고 이 경계를 되살리지 마라(주석에 박았다).

### 새 표가 늘 달라지지는 않는다 — 델타 곡선

cargo 도출만 ↔ historic 포함 (같은 HEAD):

```
since 2026-09-18  10 → 10   (+0)      since 2026-09-01   79 → 113  (+34)
since 2026-09-16  21 → 21   (+0)      since 2026-08-01  114 → 169  (+55)
since 2026-09-15  26 → 27   (+1)      since 2026-07-01  153 → 258  (+105)
since 2026-09-10  35 → 38   (+3)
```

★**갓 뜬 표에는 영향이 0** 이고 보정은 «표가 얼마나 뒤로 닿는가»에 따라 커진다 — 그것이 «깊이»다.
★단 이것은 **측정이지 증명이 아니다**. 같은 꼴의 「개명은 다 지나간 일이다」 추론이 바로 위
`--since` 항목에서 거짓으로 판명됐다.
