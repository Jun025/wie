#### 2-2. `c3057f46c59b` — 엔진 탓 아님(게임 안의 상태)

- 막힌 지점: 미션 시간이 다 돼 실패한다 → 실패 이야기(`data/fail1.txt`) → «다시하기 / 튜토리얼 / 돌아가기» 메뉴. 커서가 «튜토리얼»로 가면 불러오기 스레드 `c.run` 이 `ArrayIndexOutOfBoundsException: 98 > 54` 로 죽는다. 그 뒤 메뉴가 키에 반응하지 않는다(정책 120초 재현 4/4).
- 따라간 순서(임시 로그 · 커밋 안 함):
  - 메시지 형식 `{} > {}` 는 핀의 `Jvm::load_array`/`store_array` 경계 검사다. 실제 호출은 `System.arraycopy(src, 0, dst, 0, 98)` 이고 `src` 가 54칸이다.
  - 호출 자리를 AOT 이미지에서 찾았다. `call_native` 에 들어올 때의 스택이 트램펄린(`0x158f84`) → 정적 호출 썽크(`0x1591d8`) → 복귀 주소 `0x1040a0` 이다. 그 함수(`0x103edc`)는 `System.arraycopy(this.A, 0, this.B, 0, this.C)` 다. `this.C` 는 게임 자신의 해독 메서드(`0x159090` 경유 정적 호출)가 쓴다. 그 사이에 엔진 호출은 `available()` 과 `read(byte[], 0, n)` 뿐이다.
  - `this` 는 매번 같은 객체(`0x48435b80`)다. 필드를 찍으면 `C` 는 «글 끝 표식 `<!` 의 위치»다. `fail1.txt`(153바이트 · 글자 100 · `<!` 앞 98)를 읽은 뒤 98 이 된다. `text1.txt`(54바이트 · 숫자 목록)에는 `<!` 가 없다. 그래서 `C` 가 바뀌지 않고 98 이 남는다. 처음 부팅 때 같은 파일을 읽을 때는 `C` 가 0 이라 무사했다.
  - ⇒ 게임이 오래 사는 읽기 객체의 길이 필드를 «표식이 없는 파일»에서 갱신하지 않는다. 엔진이 다르게 할 자리가 없다. 같은 키라면 실기에서도 같은 순서로 난다고 본다. 실기 확인은 없다.
- 처분: 엔진 수정 없음. 진행 요령 한 줄을 달았다. «다시하기»를 고르면 미션이 다시 시작된다(재현 1회 · 예외 0). progress 는 그대로 `stuck` 이다(정책 키는 이 메뉴에서 «튜토리얼»로 간다).
