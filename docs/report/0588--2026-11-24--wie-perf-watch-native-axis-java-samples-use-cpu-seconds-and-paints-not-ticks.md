## [2026-11-24] perf-watch native 축 — Java 로 돌며 그리는 표본은 tick 이 아니라 그린 장수로 나눈다 (wie-perf-watch-native-axis-java-samples-use-cpu-seconds-and-paints-not-ticks)

**무엇을**: 주간 속도 감시(`scripts/perf-watch.sh` · `perf-watch.mjs`)의 native 축에서, 고정 표본 가운데 Java 로 돌며 그리는 둘(J2ME `835acd535a5f` · SKT `d1234e0ddb75`)의 판정 단위를 «50M tick 당 CPU ms» 에서 **«1000 paints 당 CPU ms»** 로 바꿨다. 그 짝은 두 쪽이 같은 순간에 뜬 것만 센다. KTF · LGT 네 표본과, 한 번 그리고 쉬는 J2ME 표본 `8238f5449347` 은 tick 그대로다(§2). 스크립트만 바꿨다 — 엔진 `*.rs` 변경 0.

**왜**: 티켓 `wie-perf-watch-native-axis-java-samples-use-cpu-seconds-and-paints-not-ticks`(채택 제안 `2026-11-22-upstream-sync2-s1-rustjava-pin-0-4-1#p1`). `wie_validate` 의 루프는 쉬지 않아 게임이 자는 동안에도 tick 이 는다. Java 실행 비용이 바뀌면 «일하는 tick» 과 «빈 tick» 의 섞임이 달라져, tick 으로 나눈 값은 전/후가 같은 단위가 아니다 — #605 의 compare 가 `835acd535a5f` 에 −67% 를 냈는데 CPU 초는 같았다(`docs/report/0572` §6 · §10-2).

**사용자 영향**: 없다. 이용자가 보는 것은 바뀌지 않는다 — 주간 감시 도구의 판정 단위다. 다음 주간 회차부터 증적 md 의 그 두 표본 행이 `native/paint` 로 찍힌다.

### 1. 현행 (할 일 0)

- `perf-watch` 는 Java 표본을 갈라 재지 않았다. native 값은 `nativeOne()` 의 식 하나(`CPU ms × 50M ÷ ticks`)였고 표본의 통신사를 보지 않았다.
- native 축의 고정 표본은 7개이고 그중 Java 로 도는 것은 셋이다: J2ME `835acd535a5f` · `8238f5449347`, SKT `d1234e0ddb75`. 티켓 근거에 나오는 `abc0c5789259` 는 고정 표본이 아니다(0572 의 게이트② 가 짚은 판). S1b(#616) · S2(#603)는 이 도구를 건드리지 않았다 — `scripts/perf-watch.*` 의 main 마지막 커밋은 `1eb0b397b` 다.

### 2. 바꾼 것 — 세 Java 표본을 어떻게 나눴나

| 표본 | 60초에 그리는 장수(이번 측정) | 판정 단위 | 왜 |
|---|---|---|---|
| J2ME `835acd535a5f` | 881 ~ 1,581 | **1000 paints 당 CPU ms** | 프레임마다 자는 판 — 자는 동안의 빈 tick 이 분모에 섞인다 |
| SKT `d1234e0ddb75` | 1,012 ~ 1,188 | **1000 paints 당 CPU ms** | tick 수가 같은 순간의 두 쪽에서 1.1 ~ 3.0배 갈린다(§3) |
| J2ME `8238f5449347` | **1** | 50M tick 당 CPU ms(그대로) | 나눌 그린 장수도 게임 루프도 없다 |

- **`8238f5449347` 은 티켓의 «Java 표본 3개» 가운데 바꾸지 않은 하나다.** 세 회 모두 두 쪽이 paints 1 · `stop` `max-ticks`(50M tick 을 CPU 6.9 ~ 7.3초에 다 돈다)였다 — 그린 장수로 나눌 수 없고, 0572 §10-2 가 잰 «게임이 청한 sleep» 도 0회다. 이 표본의 tick 은 전부 같은 빈 걸음이라 Java 실행 비용이 섞임을 바꿀 수 없다: #605 를 사이에 두고 −0.4 · −0.1 · −0.6% 였다(§3). 이 표본이 재는 것은 처음부터 실행기의 빈 걸음 값이다(`perf-watch.mjs` 의 SAMPLES 주석).
- per paint 실행은 `--max-ticks` 를 풀어 두 쪽이 60초를 끝까지 같이 돈다(종전 상한 50M 은 tick 이 부푼 쪽을 먼저 세운다 — §3 의 2회에서 두 쪽이 80M · 100M 이었다). `stop` 이 `deadline` 이고 paints ≥ 100 인 실행만 센다.
- **같은 순간 강제**: 행에 짝의 출발 시각(`t0`)을 적고, `judge()` 는 per paint 짝의 두 쪽 `t0` 이 1초 넘게 다르면(또는 없으면) 그 짝을 세지 않는다 — 유효 짝이 2 미만이면 종전대로 `unmeasured` 다. `run()` 은 원래도 두 쪽을 한 번에 띄웠다. 이번에 더한 것은 «따로 잰 행을 이어 붙인 짝» 이 판정에 들어가지 못하게 하는 쪽이다. (`-fix` 회차: `t0` 은 이제 두 쪽이 각자 띄우는 순간에 찍는다 — §8.)
- 그린 장수를 고른 까닭: `paints` 는 어느 핀의 `wie_validate` 든 결과 줄에 있다. 게임 루프 횟수(청한 sleep)는 `--pacing` 이 있어야 나오고 `d1234e0ddb75` 에서는 2회뿐이다(0572 §10-2).
- 증적 md: 머리에 두 단위가 갈린다는 한 줄(`-fix` 회차가 «`ok` 가 뜻하지 않는 것» 두 줄을 더했다 — §8) · 표의 축 칸이 `native/paint` · 원자료 표에 `CPU ms · ticks · paints` 칸. `perf-watch.sh` 머리와 `AGENTS.md` 의 주간 감시 문단에도 한 줄씩.

### 4. 새 단위가 못 보는 것

`wie_validate` 의 루프는 쉬지 않는다 — 마감까지 돈 실행의 CPU 초는 «한 일» 이 아니라 스케줄러가 준 몫이다. 그래서 «paints 당 CPU» 가 무엇을 읽는지는 그 판이 CPU 에 묶였는지, 자기 박자에 묶였는지에 따라 갈린다.

- ⑴ **`835acd535a5f` 는 호스트가 바쁠 때와 한가할 때 읽는 것이 다르다.** 이번 측정(CPU 몫 0.30 ~ 0.70)은 CPU 에 묶인 쪽이라 B 가 더 그린다(−2.8 ~ −19.4%). 0572 §10-2 의 한가한 다섯 짝(몫 0.80 ~ 0.91)을 새 분모로 셈하면 **+5.1 · +5.3 · +6.9 · +7.3 · +7.3%** 다(같은 CPU 초에 B 가 5 ~ 7% 덜 그린다 — 프레임 주기 28 → 30 ms). 한가한 호스트의 주간 회차였다면 #605 는 이 표본에서 5% 문턱을 넘겼을 것이다. 그 값은 실제로 덜 그린 것이지만 Java 실행 비용이 아니라 게임이 자는 길이다. ★이 다섯 값은 0572 의 표에서 셈한 것이고 이번 회차에 한가한 호스트에서 다시 잰 것이 아니다.
- ⑵ **`d1234e0ddb75` 는 굶지 않는 한 움직이지 않는다.** 타이머 박자(약 19.6 ~ 19.8 paints/초)에 묶인 판이라, 엔진이 그 박자를 못 맞출 만큼 느려지기 전에는 paints 도 CPU 초도 그대로다. 옛 분모는 이 표본에서 값이 회마다 3배씩 흔들렸으므로 잃은 감도는 없다 — 다만 «ok» 가 «Java 가 느려지지 않았다» 는 뜻은 아니다.
- ⑶ 실행기의 한 걸음이 비싸지는 변경(`perf-watch.sh slow` 가 만드는 꼴)은 박자에 묶인 판의 paints 를 바꾸지 않으므로 per paint 두 표본에서는 보이지 않는다. 그 축은 KTF · LGT 네 표본과 `8238f5449347`(빈 걸음 값)이 본다. 개악 대조 빌드로 이것을 재지는 않았다.
- ⑷ 고정 표본에 «마감 없이 도는 Java 판» 이 없다. §3 의 `abc0c5789259` 처럼 부하와 무관하게 같은 값을 내는 표본이 있어야 per paint 가 ⑴ · ⑵ 없이 Java 실행 비용을 읽는다 — 표본 교체는 이 티켓의 경계 밖이라 하지 않았다.
- ⑸ **⑴ 의 값을 도구의 판정 규칙에 넣으면 같은 두 빌드가 한가할 때는 «퇴행», 바쁠 때는 `ok` 다**(게이트② F4 · `-fix` 회차의 재계산). 0572 §10-2 의 `835acd535a5f` 8짝(30초 실행 · CPU 초와 paints/초)을 새 분모로 셈해 이 도구의 `judge()` · `pairUp()` 에 그대로 넣었다. ★다시 잰 값이 아니다 — 0572 의 표에서 셈한 것이다.

  | 묶음(0572 §10-2 의 회) | CPU 몫 | 회별 «후가 전보다 느린 %» | 중앙값 | 편차 | 문턱 | 도구의 판정 |
  |---|---|---|---:|---:|---:|---|
  | 한가 — 1차로 3 · 4 · 5회 | 0.80 ~ 0.91 | 5.1 · 5.3 · 6.9 | 5.3 | 0.8 | 5 | alarm |
  | 한가 — 짝 재측으로 5 · 7 · 8회 | 0.85 ~ 0.91 | 6.9 · 7.3 · 7.3 | 7.3 | 0.2 | 5 | alarm → **퇴행** |
  | 바쁨 — 1 · 2 · 6회 | 0.43 ~ 0.48 | −3.5 · −13.8 · −9.6 | −9.6 | 4.2 | 8.4 | ok |
  | 섞임 — 3 · 4 · 1회 | 0.48 ~ 0.83 | 5.1 · 5.3 · −3.5 | 5.1 | 4.1 | 8.2 | noisy |

  - 같은 순간 짝이 맞추는 것은 두 쪽의 **CPU 초**까지다(§3 의 9짝에서 차이 ≤ 2.8%). 부호를 고르는 것은 그 회차의 호스트 부하다 — 한가하면 게임이 자는 길이(박자)를, 바쁘면 같은 CPU 몫으로 그린 장수를 읽는다. 그 핀은 Java 실행 비용을 «줄인» 변경이었는데(0572 §10-2) 한가한 묶음에서는 도구 규칙으로 퇴행이다.
  - 거짓 퇴행이 서려면 1차와 짝 재측 두 묶음이 같은 부하 형상(둘 다 한가)이어야 한다. 주간 잡은 `host-load-guard --recovered` 를 시작 때 한 번만 보므로 한가한 회차가 그 형상이다. 회차 중에 부하가 바뀌면 편차가 문턱을 올려 `noisy` 로 간다(섞임 행).
  - 위 +5 ~ 7% 는 그때의 실행기 박자에 딸린 값이다: 0573 이 들어온 뒤의 트리에서는 한가한 짝(몫 0.99)이 전/후 같았다(30.3 / 30.3 paints/초 · 1짝 · 0572 §10-7). 달라지는 것은 크기이고, «한가 = 박자 · 바쁨 = 그린 장수» 라는 읽는 것의 갈림은 그대로다.
  - 식 · 문턱 · 표본은 바꾸지 않았다. 이것은 식의 오류가 아니라 이 단위가 읽는 것의 한계이고, 닫는 자리는 운영자가 매주 읽는 증적 md 의 머리다(§8). 재계산의 입력과 도구 출력: `~/orchestrator/reports/evidence/wie-perf-watch-native-axis-java-samples-use-cpu-seconds-and-paints-not-ticks-fix/`(`f4-recompute.mjs` · `f4-tool-verdict.md` · 저장소 밖).
