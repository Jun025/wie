### 1. 만든 것 — `AotCache`

```rust
// wie_cli/src/bin/wie_validate.rs · build_emulator
aot: (std::env::var("WIE_AOT").as_deref() == Ok("native"))
    .then(|| Box::new(NativeExecutor::new(AotCache::for_this_binary().map(|cache| Box::new(cache) as _))) as _),
```

| | |
|---|---|
| 자리 | 사용자 캐시 디렉터리의 `validate-native-aot/`(macOS `~/Library/Caches/net.dlunch.wie/` · Linux `~/.cache/wie/` — `directories::ProjectDirs`). `WIE_AOT_CACHE_DIR=<dir>` 이 있으면 그 자리. 저장소 안에는 아무것도 쓰지 않는다 |
| 파일 | 컴파일 요청 하나에 파일 하나. 이름 = `<이 바이너리의 길이>-<mtime ns>-<실행기의 키 64자>` |
| 크기 | 판당 21.4 MB(LGT) · 24.5 MB(KTF) — 0608 이 잰 14 ~ 15 MB 에서 늘었다(예산이 든 코드). `smoke_gate` 의 244판을 한 번 돌리면 209건 · 4.36 GiB(§4) |
| 지우는 규칙 | 빗나감에서는 아무것도 지우지 않는다(낡은 기록은 «다른 이름»이라 읽히지 않는다). **저장할 때** 디렉터리 합이 상한(8 GiB)을 넘으면 쓴 지 오래된 파일부터 지운다 — 옛 바이너리의 기록이 나가는 자리가 여기다. 방금 쓴 기록은 지우지 않는다 |
| 쓰기 | 옆에 `….<pid>.tmp` 로 쓰고 `rename` — 쓰다가 죽은 실행과 같은 판을 동시에 도는 두 실행이 반쪽 기록을 남기지 않는다. 남은 `.tmp` 는 다른 파일과 같이 오래되면 나간다 |
| 캐시를 못 쓸 때 | 캐시 디렉터리를 알 수 없거나 자기 바이너리를 못 읽으면 캐시 없이 돈다(종전의 켬). 읽기 · 쓰기 오류는 실행기가 경고만 찍고 컴파일한다(upstream 의 처리 그대로) |

- **기록은 그것을 쓴 바이너리만 읽는다 — 이름 머리의 길이 · mtime 이 그 표식이다.** 실행기의 키(`wie-core-arm-native/src/cache.rs`)는 게스트 이미지 · 컴파일 한도 ·
  호스트 ISA · `RunFrame` 의 배치를 덮지만 **생성기의 코드 자체는 덮지 않는다**. upstream 은 그 자리를 손으로 올리는 상수(`AOT_CACHE_VERSION` — «generated code
  가 바뀌면 올려라»)에 맡긴다. 검증 러너는 엔진을 고친 직후에 도는 물건이라, 그 상수를 한 번 잊으면 고친 생성기가 아니라 «앞 빌드가 만든 코드»를 재고도 아무
  표시가 없다. 다음 후보 ⒜(생성기를 고친다)가 바로 그 경우다. 그래서 러너 쪽에서는 바이너리가 바뀌면 무조건 빗나가게 했다.
  - 값: 엔진과 무관한 재빌드도 한 번 식는다. 그리고 **디버그와 release 는 서로의 기록을 못 쓴다** — 실행기의 키는 두 빌드에서 같았다(같은 판의 파일 이름 뒷부분이
    같다 · 이번에 본 것). 표식을 빼면 release 로 채운 캐시를 디버그가 읽는다. 그 길은 열지 않았다(위 까닭) — 좁히려면 표식을 «생성기 소스의 해시»로 바꾸는 것이
    다음 자리다(코드에 `ponytail:` 주석).
- **새 의존은 없다.** `directories` 는 `wie_cli` 가 이미 가진 의존이고, 임시 파일은 `tempfile` 대신 `std::fs::rename` 으로 했다. 루트 `wie` 의 `src/cli/aot_cache.rs` 를
  그대로 쓰지 않은 까닭이 그것이다(그 파일은 다른 패키지에 있고 `tempfile` 을 쓴다 · 크기 상한이 없다).
- **지속 캐시는 첫 준비에만 쓰인다**(`NativeExecutor::prepare` 의 `cache.take()` — upstream). 게스트가 명령 캐시를 비운 뒤의 재컴파일(LGT 54판 전부 · 0607 §3)은
  캐시를 타지 않는다.

**시험 1건**(`aot_cache_misses_other_keys_and_other_binaries_and_drops_the_oldest_over_its_cap` · `wie_validate` 의 시험 모듈):
빗나감은 디렉터리도 만들지 않는다 · 쓴 기록은 통째로 바뀐다 · **다른 키는 빗나간다**(`RunFrame` 의 배치나 게스트 이미지가 바뀌면 실행기가 건네는 키가 바뀐다 —
`offset_of!(RunFrame, budget)` 가 그 입력 하나다) · **다른 바이너리는 빗나간다** · 상한을 넘으면 가장 오래 전에 쓴 기록이 나가고(누가 썼든) 방금 쓴 것은 남는다 ·
`.tmp` 가 남지 않는다. 실행기 쪽의 같은 축 — «저장소가 다른 키로 만든 기록을 돌려줘도 실행기가 버리고 다시 컴파일한다» — 은 upstream 시험
`persistent_preparation_restores_without_decoding_and_rebuilds_rejected_entries` 의 넷째 회차(`max_region_blocks += 1`)가 이미 지킨다(기록 머리에 키가 들어 있다).

### 5. 판정 — 검증 러너의 기본값

**아직이다.** 0609 가 남긴 까닭(켠 실행은 실행마다 전체를 컴파일한다)은 release 바이너리에서는 풀렸다. 남은 것은 디버그 바이너리의 첫 실행 하나다.

- **release — 켤 수 있는 값이다.** 적중: 첫 화면 끔 + 0.11 ~ 0.29초 · RSS 113 ~ 140 MB(에뮬레이터 셋을 같이 돌려도 0.4 GB) · 달릴 때 −84%(LGT) ·
  `smoke_gate` 244판 달라진 판 0. 빗나감(바이너리 하나가 판 하나를 처음 돌릴 때): 첫 화면 1.3 ~ 2.2초 · RSS 380 ~ 570 MB — 15초 기한의 15% 안쪽이고 그 실행이
  캐시를 채운다(§4 의 «채움» 팔이 그것이다).
- **디버그 — 캐시가 차 있으면 되고, 비어 있으면 안 된다.** 적중은 첫 화면 2.8 · 7.2초로 기한 안이다. 빗나감은 18.6 · 24.6초로 기한(15초)을 넘는다.
  그리고 **기한 15초짜리 실행은 그 캐시를 다 채우지 못한다.** 빈 캐시에서 디버그 바이너리를 `--timeout 15` 로 한 번씩 돌렸다(혼자 · 1회씩): LGT 는 컴파일이 12 ~ 13초에
  끝나 기록 1건을 남기지만 그 실행은 첫 화면 전에 기한이 와서 `FAIL`(paints 0) 이고, KTF 는 컴파일이 기한 안에 끝나지 않아 설치 0 · 기록 0 · `FAIL` 이다.
  즉 빈 캐시에서 디버그 `smoke_gate` 를 기본 켬으로 돌리면 ARM 판이 FAIL 을 내고, 컴파일이 15초를 넘는 판은 다시 돌려도 같다(§4 의 디버그 표본이 그 모양이다).
  바이너리 표식(§1) 때문에 엔진을 고쳐 다시 지을 때마다 그 상태로 돌아간다 — 표식을 빼도 생성기를 고친 회차에서는 같은 일이 난다.
- 검증 러너를 부르는 스크립트 가운데 `smoke_gate.sh` · `lgt_render_probe.sh` · `game-lab-recensus.sh` 와 `AGENTS.md` 의 러너 블록이 디버그 바이너리를 쓴다(0609 §8).
  그래서 기본값은 `aot: None` 으로 두고 스위치는 측정용으로 남긴다.

**⒜(블록 머리 예산)가 이 까닭을 푸는가 — 못 푼다고 본다.** ⒜ 가 되돌릴 수 있는 것은 예산을 넣으며 는 몫뿐이고 그 바닥은 «예산이 없는 켬»이다. 그 디버그 첫 화면이
11.9 · 12.8초였다(0609 §3 · 1회씩 · 혼자 돌린 값) — 기한의 80 ~ 85% 이고, 에뮬레이터 셋을 같이 돌리는 스윕에서는 넘을 것이다(컴파일이 코어를 다 쓴다 · 재지 않았다).
⒜ 의 몫은 달릴 때의 +0.79 ms 와 release 빗나감의 0.2 ~ 0.8초 · 80 ~ 130 MB 다(검수 minor ③ `codegen.rs:493` 의 무조건 PC 저장 포함) — 기본 켬을 막는 자리가 아니다.

**이 까닭을 푸는 길**(넣지 않았다 — 고르는 것은 총괄 몫이다):

1. **디버그 빌드에서 컴파일러 쪽 크레이트만 최적화한다 — 재 보니 이것이 그 까닭을 없앤다.** 디버그의 빗나감이 느린 것은 게스트 코드가 아니라 «최적화 없이 지은
   cranelift» 가 도는 시간이다. 같은 커밋을 `cargo build` 에 `--config profile.dev.package.<크레이트>.opt-level=3` 만 더해 스크래치에 지었다(`Cargo.toml` 무변경 ·
   cranelift 8개 + `regalloc2` · `smallvec` · `rustc-hash` · `bumpalo` · `sha2` · `wie-core-arm-native` — 열넷). 같은 자 · 2짝:

   | 디버그 + 그 열넷만 opt-level 3 | 끔 | 켬 · 빗나감 | 켬 · 적중 | (지금의 디버그 · 빗나감 → 적중) |
   |---|---|---|---|---|
   | LGT · 첫 화면까지 | 2.77 · 2.85 s | **3.48 · 3.81 s** | 2.86 · 2.87 s | 18.6 → 7.20 s |
   | LGT · 컴파일 대기 | — | 1.29 · 1.47 s | 0.59 · 0.58 s | 12.8 → 1.51 s |
   | LGT · 피크 RSS · CPU user(45초 실행) | 305 MB · 44.2 s | 643 MB · 52.6 s | 406 MB · 46.6 s | 658 → 425 MB · 148 → 70 s |
   | KTF · 첫 화면까지 | 1.55 · 1.59 s | **2.94 · 2.86 s** | 1.85 · 1.86 s | 24.6 → 2.80 s |
   | KTF · 컴파일 대기 | — | 2.23 · 2.16 s | 1.12 · 1.11 s | 23.9 → 2.12 s |
   | KTF · 피크 RSS · CPU user | 315 MB · 43.0 s | 833 MB · 52.5 s | 379 MB · 43.5 s | 856 → 379 MB · 171 → 45 s |

   12회 전부 `PASS` · rc 0 · 경고 0줄 · load1 4.6 ~ 9.8. **빈 캐시의 첫 화면이 18.6 · 24.6초에서 3.6 · 2.9초가 된다**(끔 + 0.8 · 1.3초 · 기한의 25% 안쪽). 끔의 값은 그대로다
   (해석기 쪽 크레이트는 건드리지 않는다). 저장소에는 같은 꼴의 선례가 있다 — `Cargo.toml` 의 `[profile.dev.package.wie-core-arm]` · `[…arm32_cpu]` `opt-level = 1`.
   값: `Cargo.toml` 을 고친다(착지하면 릴리스가 한 번 선다) · 디버그 빌드가 그 크레이트만큼 길어진다(재지 않았다) · 열넷 가운데 어느 것이 값을 내는지는 가르지 않았다.
   wasm 산출물은 `profile.web` 이라 닿지 않는다.
2. **검증 스윕을 release 바이너리로 돌린다.** `smoke_gate.sh` 는 `BIN=` 을 이미 받는다(§4 가 그렇게 돌았다). `lgt_render_probe.sh` · `game-lab-recensus.sh` 와

  캐시 디렉터리도 만들지 않는다(`AotCache` 는 그 `then` 안에서만 생긴다 · 이 회차의 끔 실행 뒤 사용자 캐시 디렉터리에 `validate-native-aot/` 가 없다).
- 게임 파일명 유입(`node scripts/corpus-name-inflow.mjs`): **4회 / 3쌍(BOUNDED)** · 판단 필요 **0건(SUFFIX-ATTACHED)**. 넷 다 `wie_validate.rs` 에 main 부터 있던 주석 줄이다
  (도구는 고친 파일의 본문 전체를 본다) — 이 PR 이 더한 줄에 든 것은 0 이다(`git diff origin/main...HEAD` 의 `+` 줄에서 세 이름을 세어 0 · 0 · 0).

### 8. 한계 · 하지 않은 것

- **장면은 LGT 1판과 KTF 1판(가벼운 부팅 화면) · 기기 1대 · 3바퀴다**(0607 ~ 0609 와 같다). 측정 내내 다른 레인의 부하가 있었다(load1 3.2 ~ 12.0).
- **검증 러너의 기본값은 바꾸지 않았다**(티켓의 경계 — 판정만 낸다). 저장소 안에서 `WIE_AOT` 를 켜는 스크립트 · CI 는 여전히 0 이다.
- **캐시의 상한(8 GiB)은 상수다.** 환경 변수로 빼지 않았다 — 바꿀 일이 생기면 그때 뺀다. 지우는 순서는 «쓴 지 오래된 것부터»이고 «읽은 지 오래된 것부터»가
  아니다(적중해도 시각을 고치지 않는다): 상한이 한 바이너리의 코퍼스 한 바퀴보다 크게 잡혀 있는 동안에는 두 규칙이 같은 것(옛 바이너리의 기록)을 지운다.
- **상한을 넘겨 지우는 것은 시험(10바이트 상한)으로만 봤다.** 실제 디렉터리가 8 GiB 에 닿게 돌려 보지는 않았다.
- **바이너리 표식은 길이 + mtime 이다**(내용 해시가 아니다 — 디버그 바이너리 128 MB 를 실행마다 해시하지 않으려고). 바이너리를 `cp` 로 옮기면 mtime 이 바뀌어
  식는다(`cp -p` 는 유지한다). 측정에 쓴 스크래치 사본은 한 번 복사한 뒤 그대로 썼다.
- **KTF 의 «적중이 빗나감보다 높다»(§2)는 가르지 않았다.** 무거운 KTF 장면이 이 자에 없다(0607 §3 과 같은 한계).
- **`perf-watch` 네이티브 축은 다시 재지 않았다**(티켓의 표에 없다).
- **브라우저(wasm 생성기)는 건드리지 않았다.** upstream 에 PR 을 보내지 않았다.
- **측정 바이너리는 코드 커밋 `bc6afc290` 이다.** 그 뒤의 커밋이 고친 `*.rs` 는 주석 한 줄(기록 크기 «14 to 15 MB» → «21 to 25 MB»)이다. 게이트와 러너 블록은
  그 줄이 든 나무에서 돌렸다.

  캡처를 견주는 몇 줄이다(0609 의 것에 팔 이름과 캐시 디렉터리만 더했다). 임대는 실행 · phase 마다 1건이다. 표 · 래퍼 · 게이트 로그는 저장소 밖
