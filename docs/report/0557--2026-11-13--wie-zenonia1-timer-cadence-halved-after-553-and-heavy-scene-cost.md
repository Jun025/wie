## [2026-11-13] LGT `3cc7a9b4cb15` 박자 판정 — 현행 초당 18프레임이 게임 자신의 주기(55ms)다 · 계기 표면 `frames_painted()` (wie-zenonia1-timer-cadence-halved-after-553-and-heavy-scene-cost)

**무엇을**: 「#553 뒤 박자가 절반」 신고를 수로 갈랐다. 박자는 고치지 않았다(현행이 정답이다). 넣은 것은 둘이다. ⑴ 셸이 «게임이 실제로 낸 화면/초»를 잴 수 있게 하는 표면 `WieEmulator.frames_painted()`. ⑵ `kernel.rs` 주석의 「37ms 타이머」를 55ms 로 바로잡았다(그 주석이 이번 조사의 물음을 만들었다).

**왜**: 운영자 지시(2026-11-13 · 이어하기 뒤 «갑자기 엄청 느리다»). 앱 쪽 조사(`~/orchestrator/reports/otterpebble-featurephone-zenonia-save-continue-slowdown-rootcause.done.md`)가 원인을 엔진 두 가지로 좁혔고, 이 회차가 그 둘을 판정했다.

**사용자 영향**: 게임 속도는 그대로다(코드의 타이머 경로를 건드리지 않았다). 10-13 이전의 빠른 속도는 엔진 결함으로 게임이 두 배로 돌던 것이고 지금이 게임이 정한 속도다. 무거운 장면이 그 속도에 못 미치는 것은 남아 있다(§3). 셸은 다음 엔진 판부터 그 느려짐을 수로 볼 수 있다(§4 · 셸 배선은 otterpebble 몫).

### 1. 박자 판정 — 정답은 55ms(초당 18.18프레임)
**판정 한 문장**: 이 게임의 정답 박자는 **초당 18회(55ms)** 다 — 게임 코드가 주기를 `1000 ÷ (4 × 속도설정 + 6)`ms 로 정하고(`0x19f18`) 기본 속도설정이 최고값이라 18프레임/초이며, 환경설정에서 속도를 바꾸면 Set 간격이 그 식대로 55 → 166 → 100ms 로 움직였다(아래 표). 36회/초(#553 이전)는 타이머 사슬이 둘이던 결함이고 27회/초(「37ms」)는 요청값을 주기로 잘못 읽은 것이다.

**계수 표** — release `wie_validate`(`origin/main` `2e66f9d68`) · `RUST_LOG=wie_wipi_c::api::kernel=debug` · `--keys` 로 화면 고정 · 창은 로그 시각 기준. «요청값»은 `MC_knlSetTimer` 의 timeout, «간격»은 이웃한 Set 사이의 벽시계다.

| 화면 | 창 | Set/초 | 프레임당 Set · 거절 · Def | 요청값 중앙(최소~최대) ms | Set 간격 중앙 ms |
|---|---|---|---|---|---|
| 부팅 직후(첫 화면) | 10 s · 182회 | 18.20 | 1 · 0 · 0 | 48 (46~49) | 55.0 |
| 알림 화면(주기 333) | 4 s | 3.0~3.5 | 1 · 0 · 0 | 330 | 333.0 |
| 타이틀 | 16 s · 291회 | 18.19 | 1 · 0 · 0 | 36 (15~37) | 55.0 |
| 메뉴 | 12 s · 208회 | 17.33 | 1 · 0 · 0 | 35 (15~38) | 55.2 |
| 인트로 성 대화 | 26 s · 464회 | 17.85 | 1 · 0 · 0 | 29 (15~32) | 55.0 |
| 환경설정 · 속도 4(기본) | 12 s · 215회 | 17.92 | 1 · 0 · 0 (+설정 변경 5회¹) | 39 (33~39 · 다시 걸 때 55) | 55.0 |

- **요청값은 화면마다 다르고 간격은 같다.** 요청값 36·48·29·39 어느 화면에서나 Set 간격은 55.0ms 다. 게임이 「주기 − 이번 프레임에 쓴 시간」을 건다는 뜻이다.
- **게임 코드**(ELF `.text` · capstone · 커밋 0):
  - 프레임 루프 `0x5fc8`: `t0 = MC_knlCurrentTime()` → 한 프레임 실행(`vtbl+0x50`) → `d = [this+0x8c] − (now − t0)` → `d < [this+0x90]` 이면 `d = [this+0x90]` → 재무장 `0x4678`(`MC_knlSetTimer` 한 번만 부른다 · Def·Unset 없음).
  - 최소값 `[this+0x90]` = **15**(생성자 `0x5ecc` 의 `movs r3, #0xf`). 표의 «최소 15»가 이것이다.
  - 주기 `[this+0x8c]`: 부팅의 첫 Set 은 47(`0x160c`) · 알림 화면은 333(`0x1df6`) · 게임 화면은 `0x19f18` 이 `1000 ÷ max(1, 4·s + 6)` 으로 쓴다(`s` = 설정의 부호 있는 1바이트). 화면의 속도 1~4 가 s = 0~3 이고 프레임/초는 6 · 10 · 14 · **18** 이다. 기본값은 4(최고)다.
  - 주기를 바꾸는 길 `0x5f9c → 0x4720 → 0x46d4` 는 Unset → Def → Set 을 부른다. 그 호출이 타이머 콜백 «안»에서 나면, 돌아온 프레임 루프의 꼬리 재무장이 같은 타이머에 한 번 더 Set 한다.
- **티켓의 세 물음**:
  - 틱 격자 올림인가 — **아니다.** 60Hz 브라우저의 55.4ms(앱 쪽 회신 18.03~18.09회/초)는 게임의 55.0 에 발화 지연(정수 ms 시계)이 붙은 값이다. 격자 올림이면 66.7ms 다.
  - 거절된 Set 때문에 긴 기한이 남는가 — **아니다.** 거절은 주기를 다시 걸 때마다 1회뿐이고(알림 → 타이틀 실측: `Unset` · `Def` · `Set(55)` 0.9ms 뒤 `Set(51)` 거절), 남는 기한은 방금 건 55ms 다. 정상 상태의 거절은 0 이다.
  - 그 전 판은 사슬이 둘이라 두 배였는가 — **그렇다.** #553 이전에는 그 거절될 Set 이 두 번째 대기가 됐고, 두 콜백이 각자 55ms 로 다시 걸어 사슬 둘이 끝까지 돌았다. 알림 화면을 지나 타이틀에 들어서는 첫 전환부터 두 배였던 까닭이다(앱 쪽 회신의 커밋 쌍 34.15 ↔ 18.03 · 0521 §3 의 발화 548 ↔ 282). 설정 값을 바꿀 때마다 같은 묶음이 나므로, 그 판에서는 설정을 만질수록 사슬이 더 늘 수 있었다(그 판으로 재지는 않았다 — 추론이다).
- 근거 출처: 게임 코드(위 주소) · 설정 실측(위 표) · 참조 에뮬레이터의 Set 거절(0520 §1). 한계: 실기 영상은 없다. 실기에서 무거운 장면이 몇 프레임이었는지는 모른다(게임 규칙상 프레임이 40ms 를 넘기면 주기는 «걸린 시간 + 15ms»다).

### 2. 고치지 않은 것 — 박자
- 현행 18회/초가 옳으므로 타이머 코드를 바꾸지 않았다. #553 · #554 의 시험(`test_set_timer_on_a_pending_timer_fails` · `test_unset_timer_cancels_a_pending_timer`)은 그대로 통과한다. 큐 성장도 없다: 110초 런 내내 프레임당 Set 1 · 간격 55.0 이다.
- #553 전수 표의 다른 거절 타이틀(`cdd3eb5f9142` `4892a1abc0f8` `1cd151222bde` `79d9bc10be82`)은 다시 재지 않았다. 고칠 결함이 없어서다.
- `wie-wipi-c/src/api/kernel.rs` 의 주석 「3cc7a9b4cb15: 40/s of a 37ms one」을 55ms 로 고쳤다. 0384 가 요청값 36~37 을 주기로 읽은 것이 출처다.
- `compat.json` 의 이 행(`speed: ok`)은 그대로 둔다. 박자가 바뀌지 않았고, speed 축은 «타이머가 제때 발화했는가»를 재는데 그것은 지금도 0ms 지연이다. ★그 축은 §3 의 느려짐을 못 본다(타이머는 제때 울리고 프레임이 길다).

- **후보**(예상 이득 · 위험). 한두 줄로 닫히는 것은 없어 이 회차는 아무것도 고치지 않았다.

### 4. 계기 표면 — `frames_painted()`
- `WieEmulator.frames_painted() → number`: 게임이 지금까지 화면에 낸 프레임 수(누적 · u32). `WebScreen::paint` 가 화면에 올릴 때마다 1 오른다. 셸은 두 시점의 차 ÷ 경과 시간으로 화면/초를 얻는다. 계약 `methods` + `framesPaintedNote`.
- 왜 이것인가: `achieved_speed()` 는 굶는 게임에서 0.84 바닥에 붙고 셸의 포화 비율도 15 → 4회/초 하락에 72~82% 그대로였다(앱 쪽 회신 §1). 엔진은 «게임이 원한 주기»를 모른다(이 게임은 최소 15ms 를 늘 걸어 «늦음»으로 보이지도 않는다). 낸 화면 수는 플랫폼을 가리지 않는 가장 작은 사실이다. 타이머 발화 수는 넣지 않았다(WIPI-C 전용이고 이 게임에서는 화면 수와 같은 수다).
- 한계: «제 속도»의 기준값은 주지 않는다. 다시 그릴 것이 없으면 안 그리는 게임은 낮게 읽힌다. 셸은 같은 세션 · 같은 게임 안의 변화로 읽어야 한다.
- 시험: `contract-roundtrip.mjs` A(부팅 직후 0) · C(그리는 fixture 뒤 1 이상). ★**되돌리면 red**: `paint` 의 증가 줄을 지우면 C 가 `got 0` 으로 FAILED 다(68/69 · rc=1). 원복 69/69.
