**왜**: 추천 후속 작업 `2026-09-28-ktf-classloader-cluster-8-verdict#p1` 채택. 그 티켓은 「3종뿐이고 가설이 안 서면 구현하지 말고 판정 회신」이라고 적었다.

**사용자 영향**: 없다. 세 게임은 전과 같이 이름 붙은 오류(`Unsupported KTF client.bin layout`)로 멈춘다.

### 1. 전체 세기 — 3종뿐이다

같은 포맷의 넷째 타이틀은 없다. 표준 스텁이 아닌 파일은 모두 이미 알려진 3종이다.

### 2. 진입 ABI — 가설 셋 중 둘은 실행으로 확인했고, 셋째가 막는 벽이다

이미지 머리(재배치 적용 전 이미지 상대 값 · 세 타이틀 모두 같은 모양):

| 오프셋 | `1d5831e42a8a` | 뜻 (실측) |
|---|---|---|
| +0x0c | 0x57344 | `MNInterface` · 예외 클래스 이름 문자열 표 |
| +0x10 | 0x5772c | 클래스 이름 포인터 표 |
| +0x14 | 0x480 | 코드 시작 |
| +0x18 | 0x5ed6c | **GOT 시작** = 코드가 `sl` 에 넣는 값(`ldr r3,[pc]; mov sl,r3; add sl,pc` 를 계산하면 정확히 이 값이다) |
| +0x1c | 0x5f2a4 | GOT 끝 = 이미지 끝 |
| +0x08 | 0x5f2c0 | bss 끝 |
| +0x20 · +0x28 | 0x13580001 | 재배치 대상이 아닌 상수(뜻은 모른다) |
| +0x24 | 0x52745 | Thumb 진입 함수 |

**확인한 가설 1 — 재배치는 두 번 한다.** 앞의 표는 오프셋을 가리킨다. 마지막 오프셋(0x5ed60)이 GOT(0x5ed6c)보다 앞에 있으므로 GOT 334칸은 표에 들어 있지 않다.
표만 적용하면 GOT 값이 이미지 상대 값으로 남는다. 그 상태에서 실행하면 `get_interface(0x57348)` 이 기준 주소 없이 호출됐다.
그래서 `[+0x18, +0x1c)` 에도 기준 주소를 더해야 한다. 이것은 표준 스텁이 이미지 머리 `[재배치2 시작, 끝, …]` 로 하는 두 번째 재배치와 같은 방식이다.

**확인한 가설 2 — +0x24 는 `init(param)` 이다.** `param[0]` 을 함수 포인터로 읽고 `param[0]("MNInterface", -1, -1)` 을 호출해 결과를 bss 전역에 저장한다. 결과가 0 이면 -1 을 돌려준다.
표준 `InitParam4` 의 첫 칸이 `fn_get_interface` 이므로, 우리 `get_interface` 서비스 스텁을 그 자리에 둔 4바이트 구조로 불렀다.

실측 방법: 임시 패치로 `load_native` 의 명명 오류 갈래를 바꿨다. 두 번 재배치하고 +0x24 를 호출하게 했다. 패치는 되돌렸고 커밋하지 않았다. release `wie_validate`, `RUST_LOG=wie_ktf=trace` 로 돌렸다.

| 타이틀 | GOT 범위(재배치 후) | 호출 | 결과 |
|---|---|---|---|
| `b907b0faf483` | 0x14ca70..0x14cf9c | `get_interface(0x13ecb4)` → `Unknown MNInterface` | init 이 `0xffffffff` 를 돌려줌 |
| `1d5831e42a8a` | 0x15ed6c..0x15f2a4 | `get_interface(0x157348)` → `Unknown MNInterface` | 같음 |
| `83fc429f9cbe` | 0x15d4c4..0x15db04 | `get_interface(0x156388)` → `Unknown MNInterface` | 같음 |

세 타이틀 모두 진입부터 인터페이스 요청까지 같은 경로로 들어왔다. 진입 가설은 선다.

**막는 벽 — 가설 3 · `MNInterface`.** 이 이미지가 요청하는 호스트 인터페이스는 `MNInterface` 하나뿐이다. `WIPIC_knlInterface` · `WIPI_JBInterface` · `WIPI_exe` 문자열은 세 이미지 모두 0건이다. 그러므로 JVM 서비스도 이 인터페이스를 거친다.
- 호출 칸: 선형 스캔 휴리스틱으로 찾은 호출 지점은 19곳이다(`GOT[iface] → 전역 → 인터페이스 → [+off]`). 서로 다른 오프셋은 10개(0x20 · 0x24 · 0x38 · 0x40 · 0x44 · 0x48 · 0x54 · 0x60 · 0x64 · 0x74)이고 세 타이틀이 **똑같다**. 정적 링크된 같은 런타임이라는 뜻이다. 분기를 따라가지 않는 스캔이므로 10은 **하한**이다. 가장 큰 오프셋을 보면 표는 최소 30칸이다.
- 뜻을 알아낸 칸은 두 개다. `+0x40` 은 클래스 이름 표의 이름으로 부르고, 결과를 out 포인터로 받고, 성공하면 0 을 돌려준다(클래스 해석). `+0x20` 은 실패했을 때 `("java/lang/Error", 0)` 으로 부른다(throw). 나머지 여덟 개 이상은 모른다.
- 참고 자료: `MNInterface` 문자열은 `vendor_sdk/` 7,118개 파일에서 0건이고, 이 repo 에서는 `docs/report/0330` 에만 있다.
- 그 뒤도 모른다. 표준 경로는 `WipiExe → ExeInterface → fn_init / get_class` 로 클래스를 내보내는데 여기에는 그것이 없다. init 이 성공한 다음 호스트가 무엇을 불러 클래스를 얻는지, 첫 Jlet 을 어떻게 시작하는지 근거가 없다. 코드는 `fp`(r11)를 스레드 문맥으로 쓰는 예외 프레임 도우미(이미지 +0x2c 부근)를 갖고 있다. 그 문맥의 배치도 모른다.

### 3. 판정 — 구현하지 않는다

- **효과**: 3 / 296 (1.0%). 넷째 타이틀은 없다.
- **비용**: 두 번째 로더 경로(재배치 두 번 + bss + +0x24 호출)는 약 30줄이고 위 실증에서 이미 돈다. 비싼 것은 그다음이다. `MNInterface` 30칸 이상을 **참고 자료 없이** 역공학해야 하고, 클래스를 내보내는 ABI와 `fp` 문맥 배치도 풀어야 한다. 휴리스틱이 찾은 10칸만 해도 각 칸의 인자 모양을 호출 지점마다 역추적해야 한다. 추측으로 채운 칸은 틀려도 에뮬레이터가 알려 주지 않고 게임 로직이 조용히 어긋난다.
- 로더 앞부분만 넣으면 오류 문구가 `Unsupported … layout` 에서 `Unknown MNInterface` 로 바뀔 뿐 부팅하는 타이틀은 0이다. 그래서 그것도 넣지 않았다. 지금 명명 오류가 더 정확하다.
