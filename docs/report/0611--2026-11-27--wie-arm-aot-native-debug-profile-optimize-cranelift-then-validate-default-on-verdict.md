## [2026-11-27] 디버그 빌드에서 AOT 컴파일러 쪽 크레이트 다섯만 최적화한다 — 빈 캐시 첫 화면 20 ~ 27초 → 3.9 · 3.0초 · 검증 러너 기본 켬은 가능 (wie-arm-aot-native-debug-profile-optimize-cranelift-then-validate-default-on-verdict)

**무엇을**: `Cargo.toml` 의 dev 프로파일에 다섯 줄을 더했다 — `cranelift-codegen` · `cranelift-frontend` · `regalloc2` · `sha2` 는 `opt-level = 3`,

코드 0줄 · 새 의존 0 · `Cargo.lock` 무변경.

**왜**: `STATE.md` «다음» ⑴ ⒞(총괄 선택 2026-11-27). 검증 러너에서 네이티브 ARM AOT 를 기본으로 켜지 못하는 마지막 까닭이 «디버그 바이너리가 빈 캐시로 도는

**사용자 영향**: 없다. dev 프로파일은 게시되는 wasm 산출물(`web` 프로파일)에 닿지 않는다. 제품 기본값(`aot: None`)과 검증 러너의 기본값은 그대로다 —
`WIE_AOT=native` 가 없으면 `wie_validate` 는 종전과 같다. 브라우저 배선 0 · export 표면 변화 0 · 고지 0건 · 게임 파일 무수정.
★`Cargo.toml` 을 고쳤으므로 착지하면 릴리스가 한 번 선다(`publish-artifact.yml` 의 `**/Cargo.toml` — 산출물의 바이트는 같아야 한다).

**판정: 검증 러너 기본 켬 — 가능하다.** 막던 까닭 하나(디버그 바이너리의 빈 캐시 첫 실행)가 풀렸다: 디버그 `smoke_gate` 244판이 기한 15초 그대로

디렉터리). 장면 · 자는 0610 §3 과 같다(LGT 1판 · KTF 1판 · `MC_grpFlushLcd` 첫 줄까지 · 회마다 새 빈 캐시 디렉터리 · `/usr/bin/time -l`). 한 묶음 안에서 변형을

### 3. `smoke_gate` — 디버그 바이너리로 끔 / 켬(빈 캐시에서) 나란히

`scripts/smoke_gate.sh` 그대로(`TIMEOUT` 15 · `RETRY` 2) · **디버그 바이너리**(커밋된 `Cargo.toml` 로 지은 `target/debug/wie_validate` 의 사본 · `BIN=`) ·
줄기 3개(에뮬레이터 ≤ 3) · (팔, 묶음)마다 long 임대 1건(8건 · 4분 40초 ~ 5분 43초씩). 묶음마다 끔을 먼저, 켬을 바로 뒤에 돌렸다. 켬은 `WIE_AOT=native` 에
캐시 디렉터리 하나(시작할 때 비어 있다 · 저장소 밖)를 네 묶음이 이어 쓴다 — 0610 §4 의 «켬 · 채움» 팔과 같은 꼴이다.

| 디버그 · 244판(LGT 54 · KTF 190) | 끔 | **켬 · 빈 캐시에서 시작** | 0610 의 디버그 표본(LGT 18판 · 켬) |
|---|---|---|---|
| PASS / FAIL | 244 / 0 | **244 / 0** | 기한 40초로 12 / 6 · 기한 15초(채운 뒤) 11 / 7 |
| 끔과 판정이 다른 판 | — | **0** | 6 · 7 |
| 기준선 242행 대비 regressions · absent | 0 · 0 | **0 · 0** | 줄기 셋 다 regressions |
| 이 팔이 쓴 캐시 기록 | 0 | 209건 · 4.36 GiB | 11건 |
| 벽시계(네 묶음 합) | 약 21분 10초 | 약 21분 30초 | — |
| 묶음을 끝낼 때의 load1 | 6.1 ~ 8.1 | 9.2 ~ 12.0 | 약 40 |

- 두 팔 통틀어 러너 출력의 `FAIL` 줄은 0 이다(다시 돌린 판이 없다). 줄기 24개 전부 rc 0 · «OK: no regressions vs baseline».
- 기록 209건은 0610 의 release 채움 팔과 같은 수다(LGT 45 · KTF 164 — 게스트 이미지가 같은 판들이 기록 하나를 나눠 쓴다). 곧 244회 가운데 적어도 209회가
  빗나감(컴파일하고 기록을 쓴 실행)이었고 그 전부가 15초 안에 화면을 냈다.
- 0610 의 표본과 견줄 때: 그때는 다른 레인의 부하로 load1 이 약 40 이었고 이번은 6 ~ 12 다. 그래서 «부하가 높을 때도 전부 통과한다»까지는 이 표가 말하지 않는다 —
  말하는 것은 한 판의 첫 화면이 3 ~ 4초(§1)라 기한까지 11초가 남는다는 것이다.
- 적중 팔(채운 캐시로 한 번 더)은 돌리지 않았다 — 티켓이 물은 것은 끔 / 켬(빈 캐시)이고, 적중의 첫 화면은 §1 의 표(2.95 · 1.75초)가 빗나감보다 이르다.

### 4. 판정 — 검증 러너의 기본값

**가능하다.** 0610 이 남긴 까닭은 «디버그 바이너리가 빈 캐시로 도는 첫 실행이 기한 15초를 넘는다» 하나였다. 그 첫 화면이 3.9 · 3.0초가 됐고(끔 + 1.0 · 1.4초),
`smoke_gate` 의 기본 바이너리 · 기본 기한으로 244판이 끔과 같은 판정을 냈다. release 쪽은 0610 에서 이미 값이었다(244판 세 팔 · 달라진 판 0).

기본값을 바꾸는 다음 티켓의 범위(이 회차는 바꾸지 않았다):

1. **바꿀 줄** — `wie_cli/src/bin/wie_validate.rs` 의 `aot:` 한 식(지금 `WIE_AOT == "native"` 일 때만 `NativeExecutor`)을 기본 켬으로 뒤집고 `WIE_AOT=off` 로 끈다 ·
   그 위 주석과 파일 머리의 스위치 설명. 제품 기본값(`wie_featurephone` 의 `aot: None`)은 그대로 둔다.
2. **러너 블록 · 스윕** — `AGENTS.md` 의 러너 블록 여섯 픽스처와 `smoke_gate`(디버그 244판)를 그 기본값으로 끔과 나란히 다시 본다. 해석기를 재는 도구

   돌리므로 그 호스트의 첫 실행을 손 dispatch 로 한 번 본다(검증 러너가 x86-64 에서 네이티브 AOT 를 돈 적은 없다).
3. **문서** — `AGENTS.md` 의 러너 블록 · `smoke_gate` 항에 캐시 자리(사용자 캐시 디렉터리 · 상한 8 GiB · `WIE_AOT_CACHE_DIR`)와 «새로 지은 바이너리는 캐시가

### 5. CI 에 닿는가

**닿는다 — `cargo test --all` 을 도는 잡 셋이고, 캐시가 낡은 동안은 실행마다 다섯 크레이트와 그 위를 다시 짓는다.**

- 디버그(dev · test 프로파일)로 이 크레이트들을 짓는 잡: `rust.yml` 의 `cargo test --all`(PR 은 ubuntu/stable 한 다리 · 주간은 여섯 다리) · 주간 `coverage.yml`
  (tarpaulin) · 주간 `doc-liveness.yml`(네 게이트 + 러너 블록). clippy 세 줄은 코드를 생성하지 않는다. wasm 을 짓는 잡(`web.yaml` · `engine-contract.yml` ·
  `publish-artifact.yml`)의 의존 그래프에는 다섯 가운데 하나도 없다(`cargo tree --target wasm32-unknown-unknown` — `wie-web` · `wie_featurephone` 0건).
- **캐시**: `rust.yml` · `coverage.yml` 의 `target` 캐시 키는 `Cargo.lock` 의 해시뿐이다. 이 PR 은 `Cargo.lock` 을 바꾸지 않으므로 키가 정확히 맞아 **낡은 캐시를
  받고 · 끝나도 다시 저장하지 않는다**(`actions/cache` 는 키가 정확히 맞으면 저장을 건너뛴다). 곧 착지 뒤 `Cargo.lock` 이 다음에 바뀔 때까지 실행마다 §2 끝의 재빌드를
  한다 — 이 Mac 에서 24 크레이트 · 88.9초 · CPU 288초. `Cargo.lock` 은 최근 닷새에 여덟 번 바뀌었다(`git log -- Cargo.lock` · 2026-11-22 ~ 26).
- **이 PR 의 실행으로 잰 값**: @@CI-RUN@@
- 캐시가 새로 선 뒤의 몫은 깨끗한 빌드의 차이뿐이다(§2 — CPU +17% · 그 실행 한 번).

`Cargo.toml` 이 최종인 나무에서 돌렸다(그 뒤 바뀐 것은 문서뿐이다). 무거운 것은 `build-slot` 으로 감쌌다.

- `cargo fmt --all -- --check` rc 0 · `cargo clippy --all -- -D warnings` rc 0 · `cargo clippy --target wasm32-unknown-unknown -- -D warnings` rc 0 ·
  `cargo +beta clippy --all -- -D warnings` rc 0.
- `RUST_MIN_STACK=4194304 cargo test --all` rc 0 — 결과 줄 72개 · **1072 passed · 0 failed**(main 과 같은 수 — 시험을 더하지 않았다).
  `wie-core-arm-native` 의 시험은 이제 `opt-level 1` 로 지은 크레이트로 돈다(dev 프로파일의 패키지 지정은 시험 빌드에도 닿는다 · `debug-assertions` 와
  오버플로 검사는 그대로 켜져 있다 — 바꾼 것은 `opt-level` 뿐이다).
- 러너 블록 여섯 픽스처(커밋된 프로파일의 디버그 바이너리): 끔 6/6 `PASS` · 켬 · 빈 캐시 6/6 `PASS`(ARM 픽스처 넷이 기록 4건) · 켬 · 그 캐시로 다시 6/6 `PASS`

### 7. 한계 · 하지 않은 것

- **검증 러너의 기본값은 바꾸지 않았다**(티켓의 경계). 저장소 안에서 `WIE_AOT` 를 켜는 스크립트 · CI 는 여전히 0 이다. 제품 기본값(`aot: None`)도 그대로다.
- 장면은 LGT 1판과 KTF 1판 · 기기 1대 · 변형마다 2짝이다(H · E 만 4짝). 변형 사이 0.5초 아래의 차이는 가르지 않았다(같은 변형이 묶음 사이에 0.6 ~ 0.7초 흩어진다).
- 깨끗한 빌드 시간은 변형마다 1회다(지금 3회 · E 2회). 다른 레인의 부하가 있는 호스트에서 쟀고 `jobs = 5` 다 — 벽시계보다 CPU 열을 읽을 것.
- `opt-level 2` 와 `"s"` 는 재지 않았다(티켓은 1 과 3 의 비교 한 번). 열넷 밖의 크레이트(`hashbrown` · `rayon` · `gimli` 등)도 재지 않았다 —
  고른 다섯의 빗나감이 끔보다 1.0 · 1.4초 늦은 자리에 남은 몫이 있을 수 있다.
- 「제네릭뿐인 크레이트는 쓰는 쪽의 `opt-level` 로 지어진다」는 설명은 잰 값에 맞는 추정이다(생성된 코드를 열어 보지 않았다).
- release 바이너리의 값(0610 §3)은 다시 재지 않았다 — dev 프로파일은 release 에 닿지 않는다. `perf-watch` · 브라우저는 건드리지 않았다. upstream 에 PR 을 보내지 않았다.
- 측정 래퍼는 스크래치에 뒀다(변형 하나를 짓는 것 · 첫 화면 한 묶음 · `smoke_gate` 줄기를 나누는 것 — `scripts/smoke_gate.sh` 는 그대로 불렀다). 임대는 빌드마다
  short 1건 · 측정 묶음마다 long 1건이다(스윕 전체를 한 임대로 감싼 것 0 · 에뮬레이터 동시 ≤ 3).
