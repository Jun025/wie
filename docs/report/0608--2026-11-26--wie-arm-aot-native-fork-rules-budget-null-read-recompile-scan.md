### 1. ⑴ 버린 목록 훑기 — 주소 범위 하나

```rust
// wie-core-arm/src/aot.rs
invalidated_span: Range<u64>,                         // 버린 영역이 덮었던 주소 전부 — 늘기만 한다
…
if !self.invalidated_span.contains(&u64::from(key.pc)) {   // Aot::recompile 머리
    return;
}
```

- 0607 §4 의 스크래치 변형(+8줄)이 출발점이고 뜻은 같다. 빈 범위를 `u64::MAX..0` 으로 두면 clippy(`reversed_empty_ranges`)가 서서 `0..0` 에서 시작해
  첫 영역의 범위를 그대로 받게 했다.
- **결과가 같은 단락이다.** `invalidated` 에 들어가는 길은 `invalidate()`(그때 범위를 넓힌다)와 `poll_recompilations` 의 되넣기(원래 거기서 꺼낸 것이라
  이미 범위 안)뿐이고 범위는 줄지 않는다. 범위 밖 PC 는 어느 영역에도 없으니 훑어도 `None` 이다(0607 게이트② 검수 §3 ⒜ 가 같은 읽기를 했다).
- **이미지 안의 구멍까지 거를 필요는 없었다**(티켓이 프로파일로 정하라고 한 것). ⑴ 만 넣은 빌드의 성 대화 3회에서 `aot.rs` 가 루프 표본에 든 것은
  0 · 0 · 0.4% 다(0607 의 켬은 89 ~ 91%). 남은 루프 표본의 51 ~ 57% 는 컴파일된 코드를 부른 줄(`wie-core-arm-native/src/lib.rs` 의 `execute`)이다.
  SVC 스텁(`0x7100xxxx`)은 이미지 밖이라 전부 걸러진다.
- **시험**: 새로 넣지 않았다. 범위를 넓히는 줄을 지우면(변이) 이미 있는 `invalidated_regions_recompile_on_entry_without_blocking_other_code` ·
  `native_code_changes_only_after_explicit_instruction_cache_invalidation` 이 red 다(돌려서 확인 — 다시 컴파일이 안 일어난다). 훑기를 «건너뛴다»는 쪽은
  속도 성질이라 위 프로파일이 그 확인이다.

### 2. ⑵ 널 페이지 읽기 — 폴트를 해석기로 넘긴다

```rust
// wie-core-arm-native/src/lib.rs · NativeExecutor::execute
6 if frame.fault_address < 0x1000 => return Ok(CompiledExit::InterpretOne),
6 => return Ok(CompiledExit::GuestFault),
```

- 0607 §7 이 «폴트를 해석기로 넘기는 길과 영역을 만들 때 가르는 길 중 재서 고른다»고 했다. **넘기는 길로 했다** — 엔진에 이미 있는 길이다:
  `Arm32CpuEngine::run` 은 `InterpretOne` 을 받으면 그 명령 하나를 해석기로 돌리고 다음 명령에서 다시 컴파일된 코드로 들어간다(upstream 이 wasm
  실행기의 메모리 넘기기에 쓰는 것). 해석기의 읽기는 0 을 읽고(`Arm32CpuMemory::read_page`), 쓰기는 거기서 종전과 같은 폴트로 끝난다.
  가르는 길은 주소가 실행 때 정해져 영역을 만들 때 알 수 없고, 생성된 코드에 0 페이지 포인터를 심으면 지속 캐시가 깨진다(코드에 호스트 주소가 들어간다 —
  읽기로 본 것이고 지어 보지는 않았다).
- **넘겨도 되는 근거 — 폴트한 명령은 아무것도 바꾸지 않은 상태다.** 생성기를 읽어 확인했다(`codegen/memory.rs`): 페이지 검사(`guard_page` ·
  `transfer_range`)가 그 명령의 첫 읽기 · 쓰기 · 레지스터 기록보다 앞에 있고(여러 워드 전송은 두 페이지를 다 본 뒤 옮긴다), 폴트 블록은 그 명령의
  PC 를 적고 나온다. 레지스터는 메모리 명령 앞에서 전부 맞다(`eliminate_dead_alu_stores` 는 ALU 가 아닌 명령에서 전부 살린다). 플래그는
  «뒤에서 덮이기 전에 아무도 읽지 않는 갱신»이 빠져 있을 수 있는데, 그것은 `InterpretOne` 계약이 원래 허락하는 범위다(`wie-core-arm-aot` 의 `execute` 주석).
- 이 근거는 **네이티브 생성기**의 것이다. 그래서 엔진이 아니라 실행기 안에 두었다 — wasm 실행기를 붙일 때는 그쪽 생성기에서 같은 것을 확인하고 그쪽에 둔다.
  엔진의 `GuestFault` 갈래(종전 fork 주석 «넘길 수 없다»)는 주석만 고쳤다.
- **시험** `compiled_code_reads_through_null_like_the_interpreter`(`arm32_cpu.rs` · 두 엔진을 나란히): `ldr r0,[r0]`(r0 = 0 · 0xffc) → 0 ·
  `ldmia r0,{r1,r2}`(r0 = 0) → 0 · 둘째 워드가 0x1000 을 넘는 전송과 0x1000 의 읽기 → `InvalidMemoryAccess(0x1000)` · `str r0,[r0]`(r0 = 0) →
  `InvalidMemoryAccess(0)`. 여섯 경우 모두 그 PC 가 컴파일돼 있음과, 읽기에 성공한 경우 복귀 명령이 네이티브로 돌았음을 같이 본다.
  코드는 `0x30000` 에 올린다(0607 §6 ⑴ 의 함정 — `0x1000` 이면 64 KB 호스트 페이지가 널 페이지를 매핑한다). 넘기는 줄을 지우면(변이) 첫 경우에서
  `left: "Err(InvalidMemoryAccess(0))"` 로 red 다.
- upstream 시험 한 줄을 고쳤다: `persistent_preparation_restores_without_decoding_and_rebuilds_rejected_entries` 가 주소 1(널 페이지)의 폴트에
  `GuestFault` 를 기대했다 → `InterpretOne`(fork 주석).
- 실제 판(`2b1ed0c8d061` — 0391)의 그 읽기는 긴 키 경로 뒤라 이번에도 돌리지 않았다.

### 5. ⑶ 명령 예산 — 실행기 루프만으로는 안 된다 · 그래서 멈췄다

**왜 안 되나**(코드 읽기):

1. **컴파일된 호출은 «몇 명령을 돌았는지»를 돌려주지 않는다.** 영역 함수는 종료 코드 하나만 돌려주고(`RegionFn … -> u32`) `RunFrame` 에 세는 칸이 없다.
   실행기와 엔진이 아는 것은 들어간 PC 와 나온 PC 뿐인데, 나온 PC 가 분기의 목적지면 어느 명령에서 나왔는지 — 그 사이에 몇 개를 돌았는지 — 알 수 없다.
2. **루프는 호출 «안»에서 돈다.** 생성기의 `commit` 은 다음 PC 가 같은 영역에 있으면 뒤로 가는 분기도 영역 안 점프로 만든다(`codegen.rs` 의
   `self.entries.get(&pc)`). 실행기 루프가 영역을 이어 부르지 않게 고쳐도, 한 영역 안에서 도는 대기 루프는 돌아오지 않는다.
   0607 §7 이 ⒝ 로 적은 «`aot.rs` 의 정책 상수로 뒤로 가는 분기를 뺀다»는 성립하지 않았다 — 상수(`MAX_REGION_BLOCKS` 등)는 영역의 크기를 정할 뿐이고,
   블록 하나짜리 루프(`subs r0,#1; bne .-2`)는 블록이 하나여도 제 머리로 뛴다.
3. **시험은 «정확히»를 본다.** `yields_every_ten_thousand_instructions_across_svc` 는 첫 내줌에서 r0 = 5,000 을 단언한다. 영역의 크기로 어림해 세는
   길은 이 시험을 지나지 못하고, 지나게 만들면(일직선 구간만 맞게 세면) 루프가 돌아오지 않는 본래 문제를 가린 green 이 된다.

티켓 할 일 2 가 «실행기 `lib.rs` 의 이어 부르기 루프 외에 생성기까지 고쳐야 하면 그 지점에서 멈추라»고 했다. 여기가 그 지점이다.

- **⑶ 은 들어가지 않았다.** 검증 러너에서 기본값으로 켜지 못하는 까닭이 하나 남아 있다(§5). 원형은 스크래치 빌드 하나이고 그 값(컴파일 대기 · RSS)의
  원인은 가르지 않았다.
- **장면은 LGT 1판과 KTF 1판(가벼운 부팅 화면)** · 기기 1대 · 3바퀴. KTF 의 무거운 장면은 이번에도 없다(이 자에 키 경로와 프레임 표지가 선 KTF 장면이 없다 —
  0607 §3 과 같다). 측정 내내 다른 레인과 내 빌드 · 게이트의 부하가 있었다(load1 3.3 ~ 11.0).
- **⑴ 만의 값은 커밋 전 작업 트리로 지은 바이너리의 것이다**(`stage1.patch`). 그때는 빈 범위가 `u64::MAX..0` 이었고 커밋된 코드는 `0..0` 에서 첫 범위를
  그대로 받는다 — 같은 뜻이지만 같은 바이트는 아니다. ⑴ + ⑵ 의 값은 커밋 `cb04c9972` 를 지은 것이다.
- **브라우저(wasm)는 돌리지 않았다.** ⑵ 의 근거는 네이티브 생성기를 읽은 것이고, wasm 생성기의 폴트가 같은 성질인지는 보지 않았다.
- **실제 판의 널 읽기는 돌리지 않았다**(`2b1ed0c8d061` · 긴 키 경로 뒤). 두 엔진 단위 시험이 그 자리다.
- **`under_aot` 의 green 셋 중 둘은 게스트 코드를 돌리지 않는다**(`a_nested_hold_reports_the_outer_one` · `a_thread_that_ends_holding_leaves_no_hold_behind`) —
  AOT 를 붙여도 볼 것이 없는 시험이다. 열한 건을 같은 꼴로 두려고 넣었다.
- **`smoke_gate` 는 부팅 15초의 «뜨고 그린다»만 본다.** 재시도로 PASS 가 된 판이 있었는지는 스크립트가 남기지 않는다.
- **지속 캐시의 값은 스크래치 변형 하나 · 판당 3회다**(§3). 검증 러너의 스위치에는 캐시가 없다(`NativeExecutor::new(None)`) — `smoke_gate` · 프로파일 ·
  `perf-watch` 의 켬은 전부 실행마다 컴파일 비용을 낸 값이다.
- **스크래치 빌드 셋**: ⑴ 만의 빌드 · §5 의 원형 · 지속 캐시를 붙인 변형. 전부 작업 트리에 얹어 지었다가 `git checkout` 으로 되돌렸고 커밋하지 않았다.
  패치 · 표 · 캡처 · 게이트 로그는 저장소 밖 `~/orchestrator/reports/evidence/wie-arm-aot-native-fork-rules-budget-null-read-recompile-scan/` 에 있다.
- 드라이버를 `scripts/` 에 두지 않았다: 프로파일 · `smoke_gate` · `perf-watch` 는 저장소의 스크립트를 그대로 불렀고, 스크래치에 둔 것은 한 회를 부르는 래퍼 ·
  줄기를 나누는 래퍼 · 캡처를 견주는 몇 줄이다(0607 §9 와 같은 꼴). 임대는 실행 · phase 마다 1건이다(가장 긴 것 약 5분).
