### 1. 무엇이 바뀌었나 — run · 머리 · 세 가지 나가는 길

```rust
// wie-core-arm-native/src/codegen.rs
split_runs(ir, heads)                         // 블록을 run 으로 — 곧게 이어지는 명령 묶음 · 길어야 16
// run 의 머리(= 진입점)
left = budget; brif(left < run_len, short(pc), covered)     // 모자라면 이 run 은 돌지 않는다
budget = left − run_len                                     // 건너뛴 조건 명령도 센다(해석기도 한 걸음으로 센다)
// run 안의 명령은 한 줄기다 — 명령마다 블록을 만들지 않고, `commit` 은 run 의 마지막 명령에서만 블록을 끝낸다
short(pc):  regs[15] ← pc; → resume           // 영역 안의 간선은 PC 를 적지 않는다 — 머리가 넘길 때 제 PC 를 적는다
resume:     return InterpretOne (4)           // 머리가 넘긴 run · 중간으로 들어온 진입
fault(pc, address, rest): budget += rest      // 폴트한 명령과 그 뒤 — 머리가 깎은 것을 돌려준다

// wie-core-arm-native/src/lib.rs · NativeExecutor::execute
4 => return Ok(CompiledExit::InterpretOne),
```

- **run** 은 «들어가면 끝까지 도는» 묶음이다: 안의 모든 명령이 실행되든 조건으로 건너뛰든 바로 뒤 명령으로 넘어간다. 그래서 머리가 길이만큼 한 번에 깎아도 수가 맞는다.
  중간에서 나가는 길은 폴트 하나뿐이고, 폴트는 «그 명령부터 run 끝까지»의 수를 돌려준다(종전의 `+ 1`). 널 읽기는 종전대로 `InterpretOne` 으로 넘어가 해석기에서 세어진다.
- **모자라면 그 run 은 해석기가 돈다.** 머리에서 `남은 예산 < run 길이` 면 아무것도 돌지 않고 PC 를 그 머리에 둔 채 `InterpretOne` 으로 나온다. 엔진의 루프는 고치지 않았다
  (`arm32_cpu.rs` 의 `run` 은 0줄) — 원래 있던 `InterpretOne` 처리가 한 명령을 해석하고 다음 PC 를 다시 찾는다. 그 PC 는 run 의 중간이라 또 `InterpretOne` 이고, 남은 예산이
  0 이 될 때까지 그렇게 간다. 그래서 **예산 N 은 정확히 N 명령 뒤에 내준다** — 컴파일된 코드가 있든 없든 같은 명령에서다.
- **머리만 진입점이다.** upstream 은 영역의 모든 명령에 진입 블록을 하나씩 두고 `Switch` 가 어느 명령으로든 뛴다. 여기서는 run 의 첫 명령만 제 블록을 갖고, 나머지
  명령의 `Switch` 칸은 `resume` 하나를 가리킨다(표의 모양 · 크기는 upstream 과 같다). 매니페스트의 `instruction_pcs` 는 그대로 전부다 — 엔진은 어느 명령에서든 들어오고,
  머리가 아닌 자리는 돌려받는다.
- **영역 안의 간선은 다시 PC 를 적지 않는다**(upstream 의 «Internal edges need no published PC» 로 돌아갔다 — 0609 검수 minor ③ 의 «무조건 PC 저장»이 없어졌다).
  간선이 닿은 머리가 run 을 넘길 때만 제 PC 를 적는다(`short`). run 의 중간을 가리키는 분기(디코더는 만들지 않는다 — IR 은 바깥 입력이다)는 영역을 떠나는 간선처럼 PC 를
  적고 나간다.
- **진입의 `left == 0` 검사는 없앴다.** 예산이 0 이면 머리의 검사가 같은 일을 한다. 실행기의 `frame.budget == 0` 은 남겼다(다음 영역에 들어가 봐야 첫 run 을 돌려받을 뿐이다).
- **캐시 키에 표식 한 줄**(`cache.rs` — `b"budget counted a run at a time"`). 생성된 코드의 꼴이 바뀌었는데 키의 다른 입력은 그대로라서다. 0610 §6 이 적은 대로 로컬 `wie`
  의 캐시에는 바이너리 표식이 없다. upstream 의 `AOT_CACHE_VERSION` 을 올리지 않은 까닭: 그 상수는 `wie-core-arm-aot` 에 있어 wasm 산출물에도 들어가고, upstream 이 올릴 때마다
  충돌한다.

### 2. 머리를 어디에 두는가 — 디코더의 블록만으로는 9% 가 해석기로 샌다

**티켓의 문안(«분기 목적지와 분기 다음 명령»)대로 디코더의 기본 블록 머리만 진입점으로 두면 못 쓴다.** 그렇게 지은 첫 판에 세는 줄을 스크래치로 넣어 25초씩 돌렸다
(실행기를 부른 횟수 · «머리를 지난 진입»으로 돌려받은 횟수 · 컴파일된 코드가 돈 명령 수):

| 머리 | LGT `3cc7a9b4cb15` — 머리를 지나 해석기로 간 명령 / 컴파일된 코드가 돈 명령 | KTF `155972cac664` |
|---|---|---|
| 디코더의 블록 머리만 | 9.39M / 96.6M — **약 9%** (영역 사이 이동 190만 번 가운데 77만 번이 run 의 중간에 떨어진다) | 1.05M / 22.2M — 약 5% |
| + 이미지의 분기가 가리키는 주소 | 2.04M / 103.2M — 2.0% | 재지 않았다 |
| + 이미지 안의 «코드 주소인 워드» | 54,438 / 118.2M — **0.046%** | 33,090 / 36.1M — **0.092%** |

- **까닭**: 디코더는 아직 아무도 덮지 않은 첫 주소에서 영역을 연다. 함수 뒤의 그 주소는 리터럴 풀이나 패딩(`46c0`)이고, 거기서 «명령으로 읽히는 것»이 다음 함수로 흘러
  들어간다 — 다음 함수의 첫 명령이 블록의 중간이 된다. upstream 은 모든 명령이 진입점이라 이것이 문제가 아니었다. 가장 많이 떨어진 자리들이 그 모양이었다: 리터럴 뒤의
  잎 함수(`ldr r3,[r0,#4]` — 137만 번 가운데 88만 번) · `bx rN; nop` 이 줄지은 호출 받침 · `ldr ip,[pc,#4]; bx ip` 꼴의 ARM 받침 · `push {…, lr}`.
- **넣은 것**(`entry_addresses` · `split_runs`): ⑴ 이미지의 모든 분기(ARM `B` · `BL` · `BLX` · Thumb `B` · `B<cond>` · `BL` · `BLX`)가 가리키는 주소 ⑵ 이미지 안의 워드
  가운데 그 값이 이미지 안의 주소인 것(리터럴 풀 · 표에 든 함수 주소 — 홀수면 Thumb) ⑶ `lr` 을 쌓는 `push`(실행 중에 만든 포인터로 불리는 함수의 첫 명령) ⑷ run 은 길어야
  16 명령. 이미지를 ARM 으로도 Thumb 으로도 데이터로도 한 번에 읽는다(디코더가 훑는 방식과 같다). 그래서 아무도 들어오지 않는 머리도 생긴다 — 머리 하나의 값은 검사 한 번이고,
  빠뜨린 머리 하나의 값은 그리로 들어오는 진입이 전부 해석기로 가는 것이다. 두 판의 이미지(418 · 496 KB)에서 머리는 ARM 12,374 · 9,911개 · Thumb 17,187 · 18,022개,
  훑는 데 4.0 · 3.9 ms 다.
- **실행기가 주소를 기억한다**(`NativeExecutor::heads`). 재컴파일 요청이 받는 이미지는 버려진 영역의 제 코드뿐이고, 그 영역을 부르는 쪽은 앞선 요청의 이미지에 있다. LGT 는
  부팅 직후 명령 캐시를 통째로 비우므로(0607 §3) 기억하지 않으면 재컴파일된 코드는 다시 디코더의 머리만 갖는다. 지속 캐시가 적중한 실행도 이미지를 훑는다(같은 까닭).

- upstream 의 `compare_run` 에 있던 «네이티브 코드가 돌았다» 단언은 예산이 없는 실행에만 남겼다. 곧은 사슬의 중간에서 들어가는 진입(`native_arithmetic_conditions_and_shifts_
  match_interpreter` 의 `chains`)은 결과를 해석기와 견주고 «네이티브 코드는 돌지 않았다»를 단언한다.
- `compiled_code_reads_through_null_like_the_interpreter` 는 접근 앞에 `mov` 를 하나 둔다 — run 의 첫 명령에서 폴트하면 프레임이 받은 그대로 돌아와 «네이티브 코드가 거기까지
  갔다»를 볼 수 없다. 여섯 행 전부 그 깃발을 단언한다(종전에는 «복귀가 네이티브 코드다»를 봤다 — 널 읽기 뒤의 복귀는 이제 해석기 몫이다).
- `core.rs` 의 짝 시험 `tests::under_aot` 11건은 손대지 않았고 전부 green 이다.

### 6. 선점의 단위가 명령에서 run 으로 — 관측할 수 있는 차이

| | 0609(명령마다) | 이 PR(run 마다) |
|---|---|---|
| 예산 N 으로 도는 명령 수 · 슬라이스가 끝나는 명령 | 정확히 N · 해석기와 같은 자리 | **같다** — 조각 대조 시험이 그대로 통과한다 |
| 슬라이스의 끝을 누가 도는가 | 컴파일된 코드가 마지막 명령까지 | 마지막 run 에 못 미치는 몫(16 명령 미만)은 해석기 |
| 다음 슬라이스의 시작 | 멈춘 명령부터 컴파일된 코드 | 멈춘 자리가 run 의 중간이면 다음 머리까지 해석기 |
| 널 읽기(`InterpretOne`) 뒤 | 바로 다음 명령부터 컴파일된 코드 | 그 run 의 끝까지 해석기(16 명령 미만) |
| 예산으로 나올 때 프레임의 레지스터 | 영역이 «죽었다»고 본 ALU 기록은 적히지 않을 수 있다(0609 §1) | **전부 적혀 있다** — 죽은 기록을 지우는 분석을 run 마다 따로 돌린다(머리를 넘어 지우지 않는다) |
| 〃 플래그 | 죽은 갱신은 적히지 않을 수 있다 | 같다 — 다만 나오는 자리가 머리뿐이다 |

게스트가 보는 것(어느 명령에서 내주는가 · 그때의 레지스터와 메모리)은 달라지지 않는다. 달라지는 것은 «어느 엔진이 그 명령을 도는가»와 그 값(시간)이다.
머리를 지난 진입은 한 명령마다 실행기를 한 번 부르고 해석기가 한 걸음 가므로 컴파일된 코드보다 훨씬 비싸다 — §2 가 그 몫을 센다.

### 9. 한계 · 하지 않은 것

- **«예산 이전»까지 다 돌아오지는 않았다.** LGT 의 컴파일 대기는 0.79 → 0.69초(예산 이전 0.60) · 프레임당은 평균으로 0.24 ms 가 남는다(§3). 머리마다의 검사를 더 줄이는 길
  (예: 영역 안의 간선에서 남은 예산을 다시 읽지 않기)은 재지 않았다.
- **장면은 LGT 1판과 KTF 1판(가벼운 부팅 화면) · 기기 1대 · 3바퀴다**(0607 ~ 0611 과 같다). KTF 의 프레임당 값은 세 팔을 가르지 못한다. 측정 내내 다른 레인의 부하가 있었다
  (load1 3.5 ~ 11.5 · 0단계는 7.7 ~ 51.7).
- **«머리를 지난 진입»의 몫은 부팅 12초로만 코퍼스 전체를 봤다**(§2). 게임 안쪽에서 실행 중에 만든 포인터로만 불리는 잎 함수가 뜨거운 판이 있으면 그 판은 그만큼 느리다 —
  정확함과는 무관하고, 한 번에 16 명령 미만이다.
- **머리를 고르는 넷 가운데 셋은 어림이다**(이미지의 주소 워드 · `push` · 16 명령). 틀려도 값은 속도뿐이다: 머리가 남으면 검사 한 번, 모자라면 해석기 몇 걸음이다.
- **`entry_addresses` 는 분기 인코딩 일곱을 디코더(`wie-core-arm/src/aot/analysis.rs`)와 따로 한 번 더 읽는다.** 생성기 크레이트는 디코더에 기대지 않는다. 디코더가 새 분기
  인코딩을 배우면 여기도 고쳐야 그 목적지가 머리가 된다(시험이 지금의 일곱을 고정한다).
- **실행기가 기억하는 주소는 줄지 않는다.** 게스트가 코드를 고쳐 써도 옛 주소가 남는다(머리 하나 더). 그리고 재컴파일된 코드의 꼴이 «그때까지 본 주소»에 달린다 — 동작은
  같다(어느 명령에서 내주는가는 머리와 무관하다). 지속 캐시는 첫 준비만 쓰고, 그때의 주소는 그 준비의 이미지에서만 나온다(같은 키 = 같은 코드).
- **죽은 플래그 갱신은 예산으로 나올 때 적히지 않을 수 있다**(0609 §1 과 같은 단서 — 이제 나오는 자리가 머리뿐이고 레지스터는 전부 적힌다 · §6).
