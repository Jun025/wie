### 1. LGT `a16f08d025eb` — 원인과 고침

진단(임시 `warn!` · 커밋 0 · release):

```
DBG genref class=<수신자> iface=<게임 선언 인터페이스> cell=0x1401334 words=[1400aac, 87f80, 8802c, 87fb8, 88004, 88054, 884f4, …]
DBG 0x64 recv entries=[…10칸 Object…, (87f40,None), (87f80,None), (87fb8,None), (88004,None), (8802c,None), (88054,None), (884f4,None)]
DBG 0x64 iface entries=[…10칸 Object…, 11칸 전부 빈 stub]
```

- 게임 선언 인터페이스의 참조 칸은 **0번 워드 = 인터페이스 클래스, 그 뒤 = 수신자의 target 을 인터페이스 메서드 순서로**다. 칸의 6개 target(`87f80 8802c 87fb8 88004 88054 884f4`)은 전부 수신자 vtable 에 있다(순서는 다르다 — 인터페이스 순서다).
- 그 모양이 0377 이 정한 `0x64` 반환 표(0번 = 인터페이스 raw class, `1 + i` = 수신자의 메서드 `i` target)와 **같다**. 즉 컴파일러가 표를 이미 만들어 두었다.
- 종전 코드는 인터페이스 자신의 vtable 로 표를 만들었다. 게임 선언 인터페이스는 메서드 목록이 0개라 이름을 못 붙이고, 표가 Object 10칸 + 빈 칸이 됐다. 호출부(`0x11188` 디스어셈블 · `ldr r3,[r0,#4]` = 1번 워드)가 0 을 읽고 게임 자신의 «메서드 없음» import `0x40` 을 불러 죽었다.
- ★주의: 종전 표의 1~9번 워드는 0 이 아니라 Object 메서드(`getClass` 등)였다. 인덱스가 거기 걸리는 호출부가 있었다면 죽지 않고 **엉뚱한 메서드**를 불렀을 것이다. 영향 범위(§3)를 LGT AOT 18종 전부로 잡은 이유다.
- 고침: 인터페이스 포인터가 `generatedClasses` 에 있으면(게임 선언) 수신자 계층에서 0번 워드가 그 인터페이스인 참조 칸을 찾아 돌려준다. 못 찾으면 종전 경로. 외부(호스트) 인터페이스 칸은 0번 뒤 워드가 «슬롯 번호»라 같은 답이 아니다 — 그쪽은 건드리지 않는다.
