## [2026-10-06] verify-browser 배포 후 검증 — 대기 타임아웃 흔들림에 «새 페이지 1회 재시도» (wie-verify-browser-run-game-wait-flake-two-in-a-day)

**무엇을** — `scripts/verify-browser.mjs` 의 부팅→업로드→실행 흐름을 한 «시도»로 묶고, 그 안의 대기가
`TimeoutError` 로 끝나면 **새 페이지(새 컨텍스트)로 한 번만** 다시 한다. 실패한 시도의 콘솔·`http ≥400`
줄은 버리지 않고 출력한다. `setInputFiles` 대기는 기본 30s → 다른 대기와 같은 10s.

**왜 — 분포(main push `web.yml` 60회 · 2026-10-01~06 · 실패 2)**

| 업로드→`run-game` | 0.81 / 중앙 1.55 / p90 1.97 / 최대 **2.17 s** | 10 s 대기 초과 (run 37345625572) |

- **이봉(bimodal)이지 꼬리가 아니다** — 정상 최대 2.17 s 와 실패 10/30 s 사이에 표본이 0. ⇒ 대기 상한 상향은 무력(«느린» 게 아니라 «멈춘» 페이지).
- **Pages 전파 지연 기각** — 실패 회차의 배포→goto 간격이 정상 분포 한가운데다. 준비 대기를 넣을 근거가 없다.
- **wasm 크기 기각** — wasm 은 `run-game` 클릭 뒤에 받는다. 두 실패 모두 그 앞에서 멈췄다.
- 남는 가설: **한 번의 페이지 로드가 간헐적으로 상호작용 상태에 못 닿는다**(두 번 다 손 재실행 rc=0). 근인은 미확정 —
  종전 스크립트는 예외로 죽으며 수집한 로그를 **출력하지 않아** 증거가 없었다. 이번부터 실패 시도의 로그가 남는다.

**약화하지 않았다** — 누출 감사는 **모든 시도의 요청 합집합**을 본다(재시도가 1차 시도의 요청을 지우지 못한다).
로컬 대조(가짜 페이지 · 외부 호출 0): 정상 rc=0 · 1차만 멈춤 rc=0 · **항상 멈춤 rc=1(두 번 시도 후 red)** ·
