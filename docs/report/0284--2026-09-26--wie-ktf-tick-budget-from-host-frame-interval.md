## [2026-09-26] tick 예산을 호스트 프레임 간격에서 — `Emulator::tick_for` · `FramePacer` · 60Hz 불변 (wie-ktf-tick-budget-from-host-frame-interval)

**무엇을**: 채택 제안 `2026-09-25-ktf-frame-pacing-arm-preemption-tick-budget#p1`.
⑴엔진: `Emulator::tick_for(budget_ms)` 신설 · `tick()` 은 **기본 구현**(`tick_for(TICK_BUDGET_MS)` = 14ms)으로 남김.
`System::tick_for` · `Executor::tick_for` 도 같은 모양(기존 `tick` 은 그대로 위임).
⑵`wie_backend::FramePacer`(신규 파일): 호스트가 `tick` 을 부르는 간격에서 예산을 정한다. 상한 14 — **60Hz 이하에서는 종전과 같다**.
⑶배선 3곳: `wie_featurephone`(rAF · 포크 호스트) · `wie-web`(rAF · upstream 호스트) → `FramePacer` · `wie_validate` → `--frame-hz <HZ>`(기본 off = 종전 `tick()` 그대로).

**왜**: 고정 14ms 는 120Hz 화면(프레임 8.3ms)에서 **매 tick 이 프레임을 넘긴다**(#291 검수 비차단 지적). 쉬지 않는 게스트는 그 예산을 다 쓴다.

**사용자 영향**: 60Hz 기기 — 변화 없음(아래 표, 3타이틀 모두 fps·tick 동일). 120Hz 기기 — 바쁜 게스트의 tick 이 프레임 안에 들어온다(프레임 넘김 87~100% → 8~37%). 대신 영웅서기4 처럼 넘김으로 60Hz 보다 빨랐던 타이틀은 자기 60Hz 속도로 돌아온다(43.5 → 37.9~39.4fps · 60Hz 는 35.1~36.8).

### upstream 경계 — 시그니처 변경 최소화

- `Emulator` 트레잇: `tick_for` 가 **필수**, `tick` 이 **기본 구현**. 호출부(테스트·LGT 런타임 중첩 tick·네이티브 `wie_cli`) **0곳 수정**.
  반대(`tick_for` 에 기본 구현 `self.tick()`)는 기각 — 예산을 **조용히 무시하는** 구현이 컴파일된다. 지금 모양은 구현체 4개(ktf·lgt·skt·j2me)가 각 2줄씩 바뀌고, 빠뜨리면 컴파일이 멈춘다.
- `wie_featurephone` 의 JS 수출면 **무변경**(`tick()` 인자 없음 그대로) ⇒ `docs/contracts/featurephone-engine-contract.json` 무변경 · otterpebble 셸 수정 0 으로 효과가 닿는다. 간격은 호스트 크레이트 안에서 `Date.now()`(플랫폼 `now()` 와 같은 시계)로 잰다.
- `FramePacer` 는 새 파일 하나(`wie-backend/src/frame_pacer.rs`) — upstream 파일과 겹치는 줄이 없다.
- 네이티브 `wie_cli` 창 호스트는 `tick()` 유지(`new_events` 마다 불려 프레임 간격이 아니다).

### FramePacer — 설계가 네 번 바뀌었다 (전부 실측이 바꿨다)

| 판 | 규칙 | 실측 결함 |
|---|---|---|
| 1 | 창 **최솟값** − 2ms | rAF 60Hz 에서 **예산 13** — 늦은 콜백 다음의 이른 콜백이 짧은 간격을 만든다. 영웅서기4 36.5 → 33fps |
| 2 | 중앙값 ±1ms 평균 − 2.5ms · 추정치가 오르면 재탐침 | 60Hz 동일 ✓. 120Hz 에서 **부팅 중** 첫 탐침이 60Hz 로 학습 → 영웅서기 제로 568 tick 전부 예산 14 |
| 3 | + 스팟 탐침(120 표본마다 4ms 1회) · 오름 재탐침 제거 | 예산이 창을 따라가며 **스스로 커진다**(넘김 → 긴 간격 → 큰 예산 → 더 넘김) — 놈3 5 → 14 |
| 4 | + 오름 재탐침 복원 | 동작하나 바쁜 게스트가 tick 의 **60~70% 를 탐침**에 쓴다 |
| **5 (이 PR)** | 예산은 **마지막 탐침이 정한 주기**에서 · 창은 표류 감지(반창 이상일 때만)에만 · 스팟 탐침은 빠른 화면 발견에만 | 아래 표 |

주기 = 창 64표본 중앙값 ±1ms 안 표본의 평균(정수 ms 시계가 잃는 소수부 복원). 예산 = `floor(주기 − 2.5ms)`, 1~14 로 자름 ⇒ 60Hz 14 · 120Hz 5 · 144Hz 4.
직전 tick 끝에서 1ms 안에 시작한 호출은 표본이 아니다(부팅 연속 호출 · 프레임 시계 없는 루프).

### 측정 — 하네스 = #291 증적의 `harness.html`/`run.mjs` + `hz` 인자 · LaunchServices Chrome(CDP) · 20초 창 · 교대 짝 2회 · load1 90~173

`hz=0` = 실제 rAF(이 맥 화면 60Hz). `hz=120` = **모사 120Hz vsync 격자**(격자 2ms 전 setTimeout → 격자까지 spin · 넘긴 tick 은 다음 격자로).
spin 은 렌더러 CPU 라 120 행의 f/cpu 는 양쪽에 같은 잡음이 낀다 — **엔진 ms/frame**(Σtick ÷ 프레임) 을 같이 적는다.
base = `origin/main` `39071d6d` · after = `55bd1354`(최종 로직 · 이후 커밋은 문서뿐).

- 60Hz: 세 타이틀 모두 **짝 안 차이가 짝 사이 차이보다 작다**. 디버그 빌드(예산 getter · 커밋 안 함)로 본 예산 분포 — 14 가 **99.2~99.4%**, 나머지는 스팟 탐침 4ms(0.6~0.8%).
- 120Hz 바쁜 게스트(놈3 · 제로): fps 같고 프레임당 엔진 시간 **−20~22%** · f/cpu **+20~26%**. 모사 격자가 부하 아래 늦게 깨어나 탐침이 주기를 약 9.5ms 로 읽는다 ⇒ 예산 7 이 많아 넘김이 0 이 되지 않는다(실 rAF 는 vsync 정렬이라 이 잡음이 작다고 본다 — **실기 120Hz 로는 재지 않았다**).
- 영웅서기4 120Hz fps 하락은 대가다: base 는 tick 의 39~40% 가 프레임을 넘기며 60Hz 보다 많은 CPU 몫을 받았다. after 는 그 몫을 돌려주고 자기 60Hz 속도(35~37)보다 약간 위다.
- 부팅·끝 화면 비흑 픽셀: 같은 화면끼리 같다(영웅서기4 76,088 · 놈3 약 54k · 제로 약 69.7k).
