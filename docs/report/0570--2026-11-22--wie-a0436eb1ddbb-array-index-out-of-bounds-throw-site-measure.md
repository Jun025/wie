## [2026-11-22] `a0436eb1ddbb` 놀이 중 `ArrayIndexOutOfBoundsException: 13 > 12` — 던지는 자리 · 그때의 지도 · 원인: 꾸러미에 실린 전 주인의 설정 파일이 «저장 있음»이라 말하는데 저장 파일은 꾸러미에 없다 (wie-a0436eb1ddbb-array-index-out-of-bounds-throw-site-measure)

**무엇을**: 0552 §3 이 남긴 물음(한 판이 놀이 중 `13 > 12` 예외를 10분에 수백~수천 번 낸다 — 엔진 탓인가)에 답했다. 던지는 자리는 게임 클래스 `GameCanvas.h(II)B` 의 바이트코드 오프셋 31(`baload`)이고, 배열은 47×12 타일 지도 `cq` 다. 게이트② 반려(F1~F5)를 받아 **던질 때의 지도를 직접 쟀다**: 564칸 가운데 562칸이 -1 이다 — jar 자원 `data/1.dat` 의 값이 아니다(§3-B). 원인도 쟀다: 이 꾸러미에는 전 주인의 `option.dat` 가 실려 있고 그 5·6번 바이트(저장 칸 표시)가 «두 칸 다 저장 있음»이다. 그래서 놀이는 «이어하기» 경로로 들어가고, 그 경로는 지도를 자원이 아니라 저장 파일 `…savedata.<칸>` 에서 읽는다. 그 파일은 꾸러미에 없다. 게임은 없는 것을 실패로 다루지 않고 빈 지도로 놀이를 시작한다. 판정은 **엔진 API 탓(⒝)이 아니다** — 자원 읽기와 파일 유무 답은 맞다. 예외를 내는 것은 게임 코드(빈 지도 대비 없음 · 위쪽 범위 검사 없음)이고, 그 길로 들어서게 하는 것은 꾸러미에 실린 파일 조합이다(§4). 엔진과 `compat.json` 은 고치지 않았다.

**왜**: 0552 는 이 예외가 엔진 쪽 값 때문일 수 있다고 보고 카드(`2026-11-06-progression-stuck-confirm-only-15-remeasure#p0`)로 남겼다. 첫 판정(「게임 상수만으로 곧장 157걸음」)은 지도 «내용»이 어디서 오는지를 재지 않았고, 검수가 그 판 jar 의 실제 지도에서는 방문객이 예외 자리에 닿을 수 없음을 보였다. 엔진 결함을 게임 탓으로 닫을 수 있는 자리라 다시 쟀다.

**사용자 영향**: 이 문서로 바뀌는 표시·동작은 없다. 알게 된 것: 이 판은 지금 누구에게나 «전 주인의 저장을 이어하기»로 시작하는데 그 저장이 없어서 빈 지도로 논다 — 방문객이 지도 밖으로 걸어 나가 예외가 나고, 그 프레임에는 윗줄 표시와 캐릭터가 빠진다. 전 주인의 `option.dat` 를 올리지 않은 스크래치 사본에서는 같은 키로 새 게임이 시작되고 지도가 자원대로 실리며 420초 동안 예외가 0번이다. 그 처분(한 판에만 걸리는 행)은 이 회차의 몫이 아니라 제안 1건으로 남겼다(§4).

### 1. 어떻게 쟀나

- 엔진: `origin/main` `b6ef84444` 의 release `wie_validate`.
- 계측: crates.io `jvm-bytecode` 0.1.1 사본을 저장소 밖 스크래치에 두고 인터프리터의 예외 갈래에 `eprintln!` 만 더했다. 예외가 `ArrayIndexOutOfBoundsException` 일 때 프레임마다 오프셋 · 명령 · 그 프레임에 처리기가 있는지 · 지역 변수(정수만) · 자바 스택을 찍고, 메서드마다 한 번 코드 전체를 찍는다. 빌드는 `cargo build --release … --config patch.crates-io.jvm-bytecode.path=<스크래치>` 로 했고 `Cargo.lock` 은 되돌렸다. 게스트가 보는 동작은 그대로이고, 저장소에 들어간 계측은 0 이다.

### 2. 던지는 자리 · 배열 출처

- 던지는 자리: `GameCanvas.h(II)B` 오프셋 31 `baload`. 642번 모두 같은 자리이고, 인자도 642번 모두 `h(342, 255)` 다.
- 부르는 길(안쪽 → 바깥): `h(II)B` 31 ← `x(B)V` 43 ← `ap()V` 617 ← `a(ZZ)V` 1 ← `w()V` 9074(613번) 또는 7622(29번) ← `paint(Graphics)` 25 ← `Canvas.handlePaintEvent`. 게임 프레임 6개 어디에도 처리기가 없다(`handler=None`). 예외는 `paint` 밖으로 나간다.
- 배열: 정적 필드 `cq`(`[[B`). `<clinit>` 오프셋 6547 ~ 6555 가 만든다(6547 `bipush 47` · 6549 `bipush 12` · 6551 `multianewarray` · 6555 `putstatic cq`). 같은 꼴의 `cr`(47×12) · `cs`(31×12)가 바로 뒤에 있다. 초기화 `am()V` 도 `행 < 47` · `열 < 12` 로 돈다. 길이 12 는 지도의 열 수이고 실행 중에 바뀌지 않는다. ★바뀌지 않는 것은 «크기»다 — 칸의 «내용»은 상수가 아니다(§3).
- `h(x, y)` 가 하는 일: `j(x, y)` 로 픽셀을 타일 칸으로 바꾼다(열 = x / 28 · 행 = (y / 14) × 2 뒤 모서리 표로 보정). 그 다음이 전부다 — 「행 < 0 이거나 열 < 0 이면 -3 을 돌려준다. 아니면 `cq[행][열]` 을 돌려준다.」 **아래쪽 검사만 있고 위쪽(열 ≥ 12 · 행 ≥ 47) 검사가 없다.**
- x = 342 면 열 = 342 / 28 = 12 다. 지도 너비는 12 × 28 = 336 픽셀이므로 342 는 동쪽 끝을 6 픽셀 넘은 자리다.

### 3. (342, 255) 는 어디서 오나 — 걸음은 상수, 지도 내용은 자원이나 저장에서 온다

- `ap()V` 는 걸어 다니는 개체(화면의 방문객) 30칸을 돌며 `x(i)` 를 부른다. `x(i)` 는 「지금 위치 + 방향별 한 걸음」 자리의 타일을 `h` 로 미리 본다.
- 개체를 내는 `ao()Z` 는 시작 타일과 방향을 정적 표에서 읽는다. `<clinit>` 에서 푼 값: 시작 표 `aD = [[13, 0, 2], [13, 0, 2], [7, 10, 1]]` · 걸음 표 `aH = [[-2, -1], [-2, 1], [2, 1], [2, -1]]`. 시작 픽셀은 (28, 98) · 방향 2 의 한 걸음은 (+2, +1) 이다.
- 그 직선은 (28 + 2n, 98 + n) 이고 n = 157 에서 **(342, 255)** 가 된다. 잰 인자와 두 좌표가 모두 맞는다(재측정 R 의 24번도 전부 `h(342, 255)`).
- ★**여기까지가 상수다. 「방문객이 그 직선을 157걸음 끝까지 가는가」는 상수가 정하지 않는다.** `x(B)V` 는 미리 본 칸이 그 방문객의 `cR[i]` 와 같거나 -2(길)일 때만 걷고, -4(갈림길)면 방향을 다시 고른다(`a(BZ)V` — 이웃 칸이 -2 · -4 인 방향만 후보). 즉 걸음은 지도 `cq` 의 «내용»이 정한다.
- 지도 내용이 오는 길은 둘이고, 둘 다 플랫폼 API 를 거친다(첫 판정의 「플랫폼 API 호출 0 · 엔진 값이 들어가지 않는다」는 틀렸다 — 직접 호출만 세었고 읽는 «데이터»의 출처를 세지 않았다).
  - 새 게임: 적재 `c()V` 가 `c(false)`(→ `am()` 이 전 칸을 -1 로) 다음 단계에서 `r(Q[ca])` 를 부른다. `r(B)V` 는 jar 자원 `data/<n>.dat`(566바이트 = 머리 2 + 47×12)를 `b(String)[B` 로 읽어 `cq` 전체를 덮는다. `b` 는 `Class.getResourceAsStream` → `InputStream.available()` 크기로 배열 → `read([BII)` 한 번(반환값은 버린다)이다.
  - 이어하기: `c()V` 의 화면 모드 1 갈래가 `c(true)`(→ `am()`) 다음에 `ag()Z` 를 부른다. `ag` 는 `XFile.exists("…savedata.<칸>")`(게임이 정한 저장 파일 이름 — 앞부분은 이 문서에 옮기지 않았다 · 증적에 전문)이 참일 때만 그 파일을 열어 저장된 놀이(지도 포함)를 되살린다. 이 갈래에는 `r` 호출이 없다.
- 모서리 표 `ah` · `ai` 도 상수가 아니다. `<clinit>` 은 `null` 을 넣고 `a()V` 가 `/c/py` · `/c/px` 를 `getResourceAsStream` + `read` 로 채운다(검수가 그 값이 jar 바이트와 같음을 확인했다 · 판정에 영향 없음).
- 방향을 다시 고르는 `a(BZ)V` 도 `h` 와 같은 버릇이다. 이웃 칸을 볼 때 짝수 행 갈래는 아래쪽만 검사하고, 홀수 행 갈래는 검사가 없다.

### 3-B. 던질 때의 지도 — 쟀다 (재측정 R · 대조 C1)

**⑴ 던질 때의 `cq`** — R 의 예외 24번 전부가 같은 값이다. 그 런의 공원 번호는 `ca = 0` 이고 `Q[0] = 1` 이므로 견줄 자원은 `data/1.dat` 다.

| 칸 | 던질 때 잰 값(R · 24/24) | 자원 `data/1.dat` 값 | 같은가 |
|---|---:|---:|---|
| `cq[13][0]`(방문객이 나오는 칸) | -1 | -2 | **다르다** |
| `cq[19][3]`(직선 위 갈림길) | -1 | -4 | **다르다** |
| `cq[35][11]`(예외 때 서 있는 칸) | -1 | -3 | **다르다** |

| 그 방문객의 `cR[i]`(i = 1) | -1 | — | — |
| `ca` · `cb` | 0 · 0 | — | — |

지도는 `am()` 이 채운 -1 그대로다(두 칸은 놀이 중에 쓰인 값이다). `cR[i]` 도 -1 이라 `x(B)V` 의 «미리 본 칸 == `cR[i]`» 가 모든 칸에서 참이다 — 방문객은 방향을 한 번도 다시 고르지 않고 직선을 끝까지 간다. 검수 F1 의 예측(「균일한 지도일 때만 n = 157 에서 넘는다」)과 정확히 같다.

**⑵ 왜 자원 값이 아닌가** — R 과 60초 런 X(원본 꾸러미)에서 잰 것:

| 물음 | 잰 값 |

### 4. 판정 — 엔진 API 탓(⒝)이 아니다 · 게임 코드가 내고, 꾸러미의 파일 조합이 그 길로 보낸다

- **⒝ 는 배제됐다.** 엔진이 게임에게 준 답 가운데 원 단말과 다르다고 볼 것이 없다.
  - 자원 길: `getResourceAsStream("data/1.dat")` 성공 · `available()` 566(= 자원 크기) · `read` 566 · 지도가 자원과 칸 단위로 같다(§3-B ⑶). 이 길이 틀렸다면 새 게임에서도 지도가 비었을 것이다.
  - 파일 길: `XFile.exists("…savedata.0")` = 0 은 맞는 답이다 — 그 파일은 꾸러미에 없다. 실려 있는 `option.dat` 는 있다고 답했고 66바이트를 그대로 읽혔다.
- **예외를 내는 것은 게임 코드다(⒜ — 근거를 새로 적는다).** ① 이어하기 경로는 저장 파일이 없어도 실패로 다루지 않고 `am()` 이 채운 빈 지도로 놀이를 시작한다(`ag()Z` 는 파일이 없을 때 지도에 손대지 않고 돌아오고, 부른 쪽은 반환값을 버린다). ② 빈 지도에서는 방문객이 직선을 끝까지 가고, `h(II)B` 에는 위쪽 범위 검사가 없다(§2). 길이 12 인 배열의 12번 칸을 `baload` 로 읽으면 어느 자바 VM 에서나 같은 예외다.
- **그 길로 들어서게 하는 것은 꾸러미에 실린 파일 조합이다.** `option.dat` 는 «두 칸 다 저장 있음»이라 말하는데 저장 파일은 꾸러미에 없다. 원 단말에 그 저장이 있었는지는 이 꾸러미로는 알 수 없다. 엔진은 꾸러미에 있는 파일을 그대로 올렸다.
- 첫 판정의 근거 2(「인덱스로 들어가는 값이 전부 게임의 정적 표와 그 산수다」)는 **철회한다**. 표와 산수는 직선을 정할 뿐이고, 끝까지 가는지는 지도 내용 — 자원이나 저장 파일, 곧 플랫폼 API 를 거친 데이터 — 이 정한다.
- `Random`: `a(BZ)V`(방향 다시 고르기)와 `ao()Z` 오프셋 166 의 `q(4)`(값은 `cP[i][3]` 으로 가고 좌표에는 안 들어간다)가 쓴다. `q(n)` 은 `abs(nextInt() % n)` 이라 후보가 1개 이상일 때만 범위 안이다 — 후보가 0개면 `q(0)` 은 0 으로 나누기다. 재측정의 빈 지도에서는 방향을 다시 고르지 않으므로 이 길을 타지 않았다.
- 한계: 원 단말에서 직접 본 것은 아니다. 「저장이 없는데 이어하기를 고르면 원 단말에서도 빈 지도로 논다」는 바이트코드에서 읽은 것이다(파일 유무 말고는 플랫폼 값이 그 갈래에 들어가지 않는다). 대조는 `option.dat` 를 통째로 뺀 사본 하나다 — 두 바이트만 -1 로 바꾼 사본(sha12 `ae9d01452c04`)은 만들기만 하고 돌리지 않았다. `cq` 를 쓰는 다른 메서드(놀이기구 건설 등)는 읽지 않았다.
- 엔진이 한 일: 예외가 `paint` 밖으로 나오면 그 프레임의 나머지 그리기가 빠지고 놀이는 이어진다.
- ⇒ 이 회차의 엔진 수정 0 · `compat.json` · 진도 표기 변경 0 · 조정 행 0.
- ⇒ **제안 1건**(worklog `proposals`): 이 판에서 전 주인의 `option.dat` 를 올리지 않아 새 게임으로 시작하게 한다. 대조 C1 이 그 결과를 이미 쟀다(지도가 자원대로 · 예외 0 · 날짜가 간다). 한 판에만 걸리는 행이라 운영자 채택과 장부(`docs/contracts/runtime-adjustments.tsv`) 등재가 있어야 하고, 전 주인의 설정(소리 등)도 같이 빠진다. 규모: SKT 지원 행 82개 가운데 41개 꾸러미가 jar · `.mod` · `.msd` · `.wmr` 밖의 파일(`.dat` 34개 등)을 싣는다 — 그중 «설정은 저장이 있다는데 저장이 없는» 꾸러미가 몇인지는 재지 않았다.

**게이트② 지적을 닫은 곳**

- F1(판정 근거가 jar 의 실제 지도와 모순): 던질 때의 `cq` 를 쟀다 — 자원 값이 아니라 -1 균일이다(§3-B ⑴). 원인 후보 둘을 갈랐다: 엔진의 자원 읽기는 맞고(§3-B ⑶), `r` 이 생략되는 갈래(이어하기)가 탄 길이며 그 갈래로 보낸 것은 꾸러미의 `option.dat` 다(§3-B ⑵).
