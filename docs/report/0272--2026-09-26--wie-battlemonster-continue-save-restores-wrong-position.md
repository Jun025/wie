## [2026-09-26] 배틀몬스터 «이어하기» 비정상 위치 = 아카이브에 딸려 온 저장 플래그 · 엔진 저장/복원은 정상 (wie-battlemonster-continue-save-restores-wrong-position)

**무엇을**: 운영자 보고 「이어하기 하면 캐릭터가 비정상 위치에서 움직이지 않는다」의 원인 계급을 판정했다. **코드 변경 0.**
측정 + 판정 + 후속 제안(셸 1 · 엔진 1).

**왜**: P0 운영자 실플레이 보고. 가설 H1(저장 없음을 «있다»고 답함) · H2(바이트 순서·폭) · H3(손상 저장본)을 가르라는 티켓.

**사용자 영향**: 엔진 동작은 바뀌지 않는다. 원인은 게임 zip 안의 파일이라 고치는 자리는 셸(otterpebble)이다 — 제안으로 넘겼다.

### ⑴ 게임이 쓰는 저장 API · 저장 위치

- API = `org/kwis/msp/io/File`(`binary.mod` 임포트) + `DataInputStream`/`DataOutputStream`. 파일은 **두 개**(바이너리 UTF-16 리터럴 표):
  `mastercom.sav`(10 B · 공통 설정 + «저장 있음» 플래그) · `master.sav`(1,900 B · 진행 데이터).
- 우리 쪽 경로: `LgtEmulator::from_archive` 가 **zip 의 모든 파일**을 `FilesystemOverlay` 가상층에 올린다(`add_virtual`) —
  읽기는 플랫폼 FS 우선·가상층 폴백, 쓰기는 플랫폼 FS. 플랫폼 FS = 검증기 `MemoryFilesystem`(실행마다 빔) ·
  웹 셸 `WebFilesystem`(JS 가 IndexedDB 로 보존). ⇒ 두 호스트 모두 zip 에 든 `mastercom.sav` 를 게임에게 보인다.

### ⑵ H1 — 참. 단 원천은 스텁이 아니라 **zip 에 든 `mastercom.sav`**

`배틀몬스터.zip` 은 원래 폰의 앱 폴더 덤프라 `mastercom.sav`(2008-05-22)를 싣고 있고 `master.sav` 는 없다.

| `mastercom.sav` | 바이트 | 출처 |
|---|---|---|
| 게임이 새로 만든 기본값 | `03 01 32 00 00 00 00 00 00 00` | 깨끗한 저장소 첫 부팅(읽기 FNF → 모드 4 로 생성) |
| 게임이 저장한 뒤 | `03 01 32 **01** 00 00 00 00 00 00` | 옵션 → 저장하기 직후 — ★byte[3] 만 00→01 |
| zip 에 든 것 | `02 00 1e **01** 00 0f 42 40 01 01` | 원래 폰 덤프 — byte[3]=01 인데 `master.sav` 없음 |

⇒ byte[3] = «저장 있음» 플래그. zip 사본은 플래그만 켜진 **고아**다.

- 같은 바이너리 · zip 에서 `mastercom.sav` 만 뺀 로컬 사본(커밋 안 함) 대조:
  메뉴 커서 **1 새로하기**(zip 원본은 **2 이어하기**) · 새로하기 대화상자 「게임을 새로 시작합니다.」(원본은 「저장된 데이타가 있습니다」).
  ⇒ Acceptance ①(«저장 없음이면 대화상자가 안 뜬다»)은 **저장소가 정말 비어 있으면 성립** — 엔진은 없는 파일을 «있다»고 답하지 않는다.
- zip 원본으로 이어하기 → `master.sav` 읽기 모드 열기 = `FileNotFoundException`(java_exceptions 1) → 게임이 삼키고 **0 상태**로 마을에 들어간다.
  같은 키 스크립트(main 빌드 · `OK OK LSOFT OK 1 RIGHT RIGHT RIGHT` · 5 s 간격) **3/3** 에서 RIGHT 한 번당 변한 화소 **0–377**(주인공 불동).
  이것이 운영자 화면이다(#306 회차도 이어하기 경로에서 같은 0 상태를 따로 봤다).

### ⑶ H2 — 거짓. 저장 → 종료 → 이어하기가 저장 시점 그대로 복원되고 움직인다

깨끗한 저장소(디스크 `Filesystem` · 스크래치)에서 새로하기 → 숲 튜토리얼 → 마을 → RIGHT 로 이동 → CLR → 옵션 → 저장하기 → 「저장되었습니다.」 → 프로세스 종료 → 새 프로세스로 이어하기.
새로하기 경로는 `origin/main` 에서 숲의 장면 스레드 사망(StringBuffer 22)으로 막히므로 **저장 생성은 #292 head `3c316f7f`** 위에서 했다. 복원은 두 빌드로 쟀다.

| 비교(240×320 = 76,800 화소) | 변한 화소 |
|---|---|
| 저장 직전 프레임 ↔ 이어하기 직후(#292) | 1,261 (NPC 대기 동작) |
| 저장 직전 프레임 ↔ 이어하기 직후(**main**) | 871 |
| 이어하기 뒤 무입력 4 s(대조) | 946 |
| 이어하기 뒤 LEFT 1 s · RIGHT 0.5 s(#292) | 65,155 · 64,424 |
| 이어하기 뒤 RIGHT · RIGHT(main · 2회) | 42,233 · 51,108 / 52,069 · 48,420 |

- 저장본 두 개(마을 도착 A · RIGHT 로 이동 뒤 B)를 `cmp -l` 하면 **정확히 3바이트**가 다르다:
  int@4·int@8 = 플레이 시간 분·초(07:55 → 09:04 · 화면 시계와 일치) · int@20 = X `0x128 → 0x1a0`(+120) · int@24 = Y `0x2ff` 불변(가로로만 움직였다).
  ⇒ 빅엔디언 `writeInt`/`readInt` 가 제자리다 — 바이트 순서·폭 결함 없음.

### ⑷ H3 — 참(형태가 다름)

운영자의 «저장된 데이터»는 운영자가 만든 저장본이 아니라 **zip 에 든 원래 폰 덤프의 `mastercom.sav`** 다 —
등재 회차가 **새 브라우저 프로필**에서 이미 「저장된 데이타가 있습니다」를 본 것이 그 증거다. 게임이 저장을 쓰는 곳은
옵션 → 저장하기(과 게임 안 자동저장 문구들)뿐이고, 새로하기 튜토리얼 도중에는 `master.sav` 쓰기가 **0** 이었다.

### ⑸ 원인 계급 · 왜 엔진을 고치지 않았나

**원인 계급 = 게임 저장본 손상(아카이브에 딸려 온 고아 저장 플래그).** 스텁 반환 · ABI 행 · 바이트 순서 · 셸 저장소 로직은 아니다.

엔진에서 «zip 의 저장 파일을 숨기기»는 하지 않았다. 코퍼스 LGT **91개 중 최소 4개**가 이름부터 저장 파일인 것(`*.sav`·`Save*.dat`·`*save*.do`)을 싣고,
그중 라이브 `메이플스토리2007` 은 **완전한** 저장본(`P/maplesave1.do`·`P/maplesave2.do`)을 싣는다. 패키지 밖 파일 중 무엇이 «내려받은 데이터»이고
무엇이 «이전 소유자의 저장»인지는 파일만 보고 가를 수 없다 ⇒ 일괄 규칙은 라이브 타이틀의 동작을 바꾼다. 타이틀별 결정은 등재 해시를 쥔 셸의 몫이다.
