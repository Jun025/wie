## [2026-11-25] ARM 해석기 — 실행 중인 64KB 코드 페이지를 기억하는 인출 경로를 만들어 쟀고, 빨라지지 않아 넣지 않는다 (wie-arm-interpreter-instruction-fetch-skip-page-table-within-same-64kb-page)

**무엇을**: 측정 기록이다. 엔진 코드는 main 과 같다(이 PR 의 `wie-core-arm` 차이 0줄). 인출 경로에 «마지막 코드 페이지» 기억을
넣은 구현을 브랜치에 커밋해(`831d34f8a` · `dad9756fe`) 같은 순간 짝 3회로 쟀고, 그 두 커밋을 같은 브랜치에서 되돌렸다.

**왜**: 운영자 채택 제안 `2026-11-22-arm-interpreter-throughput-step1#p1`(0575 §5 ⒜) — 명령 인출이 매번 거치는 널 주소 검사와
페이지 표 조회를 건너뛰면 프레임당 최대 2 ms 가 준다는 어림. 그 어림은 줄 단위 표본 몫에서 온 것이었고, 0575 가 스스로
«실제 값은 그 변경의 전/후를 재야 안다»고 적어 둔 자리다.

**사용자 영향**: 없다(제품 줄 0 · wasm 산출물 불변). 재 보니 프레임당 실행 루프 시간이 **22.54 → 22.88 ms(+0.34 ms · +1.5%)** 로
세 짝 모두 같은 방향(+1.3 ~ +1.9%)이었다 — 빨라지지 않고, 잡음 크기만큼 느려진다. 그래서 넣지 않는다.

### 1. 먼저 다시 잰 것 — S3 착지 뒤에도 그 몫은 남아 있다 (할 일 0)

자는 0575 §2 그대로다: LGT `3cc7a9b4cb15` 인트로 성 대화 첫 쪽 · 네이티브 `wie_validate`(release + 줄 표) · `xctrace`
Time Profiler 8초 창 · «창 안의 루프 표본 ÷ 프레임 수». 기준 = main `933bf58da`(S3 병합 `23a94715f` 포함) 3회.

| | 0575 의 main `76cc27c57` | 지금 main `933bf58da` |
|---|---|---|
| 프레임당 실행 루프 | 20.68 · 20.81 · 21.50 → 21.00 ms | 22.78 · 22.54 · 22.29 → **22.54 ms** |
| 게스트 메모리 shim(줄 번호 없는 우리 코드 포함) | 18.0 ~ 19.3% → 3.94 ms | 16.5 ~ 17.7% → **3.84 ms** |
| 그중 인출(호출자가 `execute_thumb` · `execute_arm` 의 인출 줄) | (어림 2.96 ms = shim × 1 ÷ 1.334) | 1.97 · 1.98 · 1.71 → **1.89 ms** |
| 〃 데이터 읽기 · 쓰기(호출자가 `arm32_cpu` 의 다른 줄) | (어림 0.98 ms) | 0.66 · 0.61 · 0.71 → **0.66 ms** |
| 〃 호출자를 가르지 못한 것¹ | — | 1.39 · 1.23 · 1.25 → 1.29 ms |
| 우리 run 루프(`ArmEngine::run`) | 8.2 ~ 8.6% → 1.76 ms | 12.9 ~ 13.2% → **2.93 ms** |

¹ 되짚기에 `arm32_cpu` 프레임이 없이 shim 바로 위가 `run` 을 부른 자리(`core.rs:506`)인 표본이다 — 인출인지 데이터인지 가를 수 없다.

- **shim 의 몫은 그대로다(3.94 → 3.84 ms).** 티켓의 «몫이 사라졌으면 하지 않는다»에는 해당하지 않아 구현으로 갔다.
- 인출 · 데이터의 가름은 이번에 처음 «호출자»로 쟀다(집계 스크립트의 사본에 호출자 줄 판정을 더한 것 — §6). 0575 의 2.96 ms 는
  호출 횟수 비율로 나눈 어림이었고, 호출자로 가르면 인출은 1.9 ms(가르지 못한 것을 전부 인출로 쳐도 3.2 ms)다.
- ★**옆에서 본 것 — 우리 run 루프가 1.76 → 2.93 ms 로 늘어 있다**(전체 루프 21.00 → 22.54 ms 의 대부분). 0575 때의 run 은 명령마다
  PC 하나만 읽는 루프였고, S3 가 들여온 AOT 배선이 그 루프에 명령당 검사(백엔드가 있는지 3회 · `lookup_entry` · `interpret_one`
  깃발 읽고 쓰기)를 더했다. 두 빌드를 같은 순간에 짝지어 잰 것은 아니다(0575 는 3일 전 · 같은 빌드 3회 ±2% 가 그때의
  근거) — 그래서 이 회차의 결론에 쓰지 않고 worklog 제안 1건으로 남긴다.

### 2. 만든 것 (되돌린 두 커밋)

`run` 이 PC 의 64KB 페이지가 바뀔 때만 페이지 표에서 그 페이지의 **위치**(주소 + 포인터 · 사본이 아니다)를 풀어 shim 에 넘기고,
shim 의 `get_page` 는 주소가 그 페이지면 비교 1회로 포인터를 돌려준다. 널 읽기 특례(`read_page` 의 `NULL_READ_LIMIT` 검사)는 그 앞에
그대로 둔다. 외부 크레이트 무접촉 · 페이지 크기와 매핑 정책 무변경 · `arm32_cpu.rs` 한 파일 +86 −3(`831d34f8a` 84/3 · `dad9756fe` 4/2).

### 3. 낡을 수 있는 경로 전부와 그 처분 (할 일 2)

기억은 `run` 의 지역 변수 하나다 — 호출마다 빈 값에서 시작한다. `run` 은 `&mut self` 를 쥐고 있고 밖으로 되부르는 길이 없으므로
(SVC 는 `run` 이 값을 돌려주며 끝난다) 엔진의 다른 메서드는 `run` 과 겹쳐 실행될 수 없다.

| 코드가 바뀌는 길 | 어디로 오나 | 왜 낡지 않나 |
|---|---|---|
| 게임 자신의 쓰기(실행한 코드를 고쳐 쓰는 판 — 0575 §7 ③) | shim `w8/w16/w32` → `get_page` | 같은 포인터로 쓴다. 다음 인출이 그 바이트를 읽는다 |
| 범용 훅 설치 · `unhook` · 그림자 대조의 되돌렸다 덮기 · 잠금 해제 패치 · SVC 스텁 · 로더 | 전부 `ArmEngine::mem_write` → `EmulatedMemory::write_range`(`wie-core-arm` 안에서 `.mem` · `.pages` 를 만지는 파일은 `arm32_cpu.rs` 하나) | `run` 과 `run` 사이에만 일어난다. 그리고 사본이 아니라 위치라 값도 같다 |
| 매핑 | `EmulatedMemory::map` — 페이지 표 칸을 쓰는 유일한 자리 | 빈 칸만 채운다. 칸을 비우거나 바꾸는 코드는 없다(매핑 해제 자체가 없다) · `run` 중에 닿지 않는다 |
| AOT 로 컴파일된 코드 · 캐시 유지 명령 해독 | 페이지 표를 통째로 받는다(`MemoryAccess::pages`) | 백엔드가 있으면 명령마다 다시 잡는다 · 실행이 실패해 백엔드를 버리는 자리에서 기억도 버린다(`dad9756fe` — 이어받은 회차가 코드를 읽다 찾아 더했다) |

마지막 줄은 값이 틀어지는 문제가 아니라 포인터 별칭 규칙 쪽이다(컴파일된 코드가 페이지를 직접 만진 뒤 그 전에 잡은 포인터를
다시 쓰게 된다). 그 경로까지 Miri 로 돌렸다: 새 시험 · 널 읽기 시험 · AOT 실패 뒤 해석기 복귀 시험 · 메모리 시험 3건 = 6건이
Stacked Borrows 와 Tree Borrows 양쪽에서 통과(각 6 passed · 미정의 동작 보고 0).

### 4. 시험 · 개악 (구현 커밋 위에서)

- 새 시험 `rewritten_code_on_the_executing_page_runs_its_new_bytes` — ⑴ 페이지를 기억한 뒤, 인출 전에 게스트 저장이 뒤쪽 명령을
  고친다 → 고친 명령이 실행되고 그 바이트가 메모리에 있다 ⑵ `run` 사이의 호스트 쓰기 → 새 명령이 실행된다 ⑶ 페이지 경계를 넘는 실행.
- 널 읽기 특례는 기존 시험 `guest_reads_through_null_are_zero_but_writes_and_higher_reads_still_fault` 가 잡는다 — green.
- `cargo test -p wie-core-arm --lib`: 173 passed · 0 failed.

| 개악 | 결과 |
|---|---|
| M1 — 주소를 견주지 않고 기억한 페이지를 돌려준다 | **red 12건**(훅 시험 8 · AOT 대조 시험 4). ★새 시험은 통과한다 — 그 시험의 저장이 실행 중인 페이지 안이라 다른 페이지의 데이터 접근을 보지 못한다 |
| M2 — 위치 대신 페이지의 사본을 기억한다(낡는 캐시) | **red 3건** — 새 시험이 `the store reached memory, not a cached copy`(`[1, 34]` ≠ `[7, 34]`)로 잡는다 |
| M4 — 페이지가 바뀌어도 다시 잡지 않는다 | green 173 — 틀려지지 않고 느려질 뿐이다(`get_page` 가 주소를 견주므로 다른 페이지는 표로 간다) |

### 5. 전/후 — 같은 순간 짝 3회 (할 일 1 · 3)

전 = main `933bf58da` · 후 = `dad9756fe` 의 코드(측정 빌드는 그 커밋과 주석 2줄의 문구만 다르다 — 줄 수가 같아 줄 표도 같다).
전 → 후 순서로 번갈아 6회 · 6회 전부 캡처로 같은 쪽(성 대화 첫 쪽)임을 확인했다.

² 후 2회째는 run 루프의 표본이 «줄 번호 없음»으로 풀렸다(0575 §2 각주 1 과 같은 현상 — run 루프 0.7% · 줄 번호 없음 18.9%).
우리 쪽 합으로는 읽을 수 있어 그 줄에만 넣었다.

- **전체는 세 짝 모두 느려지는 쪽이다(+1.3 ~ +1.9%).** 같은 빌드 3회의 폭(전 22.29 ~ 22.78 · ±1.1%)과 같은 크기라 «느려졌다»고
  단정할 수는 없지만, «빨라졌다»는 읽을 수 없다. 제안이 어림한 −2 ms 는 나오지 않았다.
- **묶음별로는 옮겨 갔을 뿐이다.** 인출 −0.21 ms · 데이터 접근 +0.23 ms(비교 1회의 대가 — 할 일 3) · run 루프 +0.7 ms(명령마다
  PC 의 페이지를 견주고, shim 구조체에 두 낱말을 더 싣는다). 줄 단위 표본은 옆으로 미끄러지므로(0575 §2) 이 가름은 약하고, 서는 것은
  프레임당 합이다.
- **왜 이득이 없나.** 기억 경로가 하는 일(주소 자르기 · 기억한 주소와 비교 · 포인터 읽기)과 원래 경로가 하는 일(주소 자르기 · 표
  칸 읽기 · 비었는지 검사)이 명령 수로 거의 같다. 표는 512KB 지만 이 장면에서 닿는 칸은 몇 개뿐이라 캐시에 있다. 0575 가 인출에
  돌린 표본은 그 검사들의 값이 아니라 shim 을 거치는 호출 자체와 이웃 줄에서 미끄러진 몫이었다.

**판정: 넣지 않는다.** 얻는 것이 없고 `unsafe` 포인터 하나와 그 불변식(§3)이 남는다. 구현은 `831d34f8a` · `dad9756fe` 에 있고
패치 사본을 증거 폴더에 두었다.

### 6. 하지 않은 것 · 한계

- **`smoke_gate` ktf · lgt 전/후와 wasm 계약 3종은 돌리지 않았다.** 넣는 코드가 없어 견줄 «후»가 없다(이 PR 의 엔진 차이 0줄 ·
  wasm 산출물 불변). `smoke_gate` 는 청크 3개로 나눠 long 임대 줄에 세웠다가 판정 뒤 시작 전에 내렸다(실행 0).
- 장면 1개(LGT 1판 · 네이티브) · 기기 1대 · 3짝. KTF 와 브라우저(wasm)는 재지 않았다 — 네이티브에서 이득이 0 인 변경을 그쪽에서
  다시 잴 근거가 없었다.
- 프로파일은 실행 1회마다 short 임대로 돌렸다(1회 약 3분). long 풀의 한 칸을 다른 저장소의 스위트가 2시간 넘게 쥐고 있었다.
- §1 의 «run 루프 1.76 → 2.93 ms» 는 다른 날의 두 빌드다. 같은 순간 짝이 아니다.
- 호출자 가름(§1 · §5 의 인출 / 데이터)은 `scripts/arm-interp-profile.mjs` 의 스크래치 사본에 더한 판정이다(`arm32_cpu` 0.1.2 의
  `thumb.rs:105` · `arm.rs:100` 이 인출 줄). 저장소에 넣지 않았다 — 크레이트가 바뀌면 낡는 줄 번호다.
- 원자료(6회의 export · TOC · 표 · 호출자 가름 · 개악 로그 · Miri 로그 · 패치)는 저장소 밖
  `~/orchestrator/reports/evidence/wie-arm-interpreter-instruction-fetch-skip-page-table-within-same-64kb-page/` 에 있다.
