- 같은 창에서 두 행을 더 봤다: `c361632541a7`(고정 60 · 59.9 → 65.1) · `fb80e97cbc57`(마감에서 남은 만큼 자는 꼴 · 17.9 → 19.9). 같은 읽기다.
- `abc0c5789259` 의 루프는 갱신에 경과 시간을 넘기지 않는다(`run()` 안에 시계 읽기가 없다) — 주기가 는 만큼 **게임 진행도 같이 느려진다**(0573 §9 의 «같이 느려진다» 꼴). 나머지 두 판이 경과 시간으로 진행을 보정하는지는 읽지 않았다.

### §5 꼴이 다른 한 행 — `b42e4242866b`

- 그리기 388 → 329/초(−15% · 2회) · 브라우저 창 14,016 → 12,298(−12%) · 12,913 → 12,413(−4%). **게스트 sleep 수는 그대로다**(642 → 641).
- 루프: `while (true) { if (그리기 끝남) { 장면별 repaint(…); 깃발 내림; } yield(); }` — 그리기가 끝날 때마다 한 걸음 가는 꼴이고, 첫 화면(잰 구간)의 이 루프에는 잠이 없다(계수기에 잡힌 20 ms 잠은 전 · 후 같은 수이고 이 루프 밖에서 온다 — 출처는 가리지 않았다). 게임 안 장면에는 `sleep((4 − 속도) × 50)` 이 있다.
- 달라진 것: repaint → 그리기 지연 p50 이 0 → 1 ms 가 됐고(22초 창), 그 사이 루프의 `yield` 가 8,868 → 871,812회 헛돈다. 한 장에 2.6 → 3.0 ms.
- 판정: 요청한 잠이 없는 화면이라 «요청한 속도로의 복귀»가 아니다 — 처리량이 준 것이다. 다만 전 · 후 모두 초당 300장을 넘고(화면은 초당 60번 바뀐다), 게임 안 장면은 50 ~ 200 ms 잠으로 도는 꼴이라 1 ms 는 2% 아래다. 게임 안 장면은 재지 않았다(키 없음).

### §7 정적 계수 「목록의 게스트 sleep 판은 SKT 2행」 이 틀린 까닭

- **SKT 82행 중 80행은 `.jar` 가 32바이트 머리 뒤에 zip 이 오는 꼴이다**(`20 00 00 00 00 00 00 00 …` · zip 은 오프셋 32부터 — 엔진의 `SktEmulator::loadable_jar` 가 보는 그 머리). 첫 바이트가 `PK` 인 것만 여는 읽기는 그 80행에서 클래스 파일을 하나도 못 본다. 이 회차가 같은 방식으로 세면 2행이 나오고(재현), 머리를 건너 읽으면 **82행 전부**에 `java/lang/Thread.sleep(J)V` 참조가 있다(시한 있는 `Object.wait` 는 12행).
- KTF · LGT 의 「0」 도 같은 성질이다: 그 꾸러미의 `.jar` 에는 클래스 파일이 없다(KTF 269행 중 3행 · LGT 78행 중 0행에서만 읽힌다 — 게임 코드는 네이티브 이미지다). 「sleep 을 안 부른다」 가 아니라 「읽을 클래스가 없다」 였다. KTF 는 네이티브 코드가 Java 인터페이스 호출로 같은 JVM 의 `Thread.sleep` 에 닿는다(§3 의 동적 계수).
- 같은 계수를 옮겨 적은 문서: `docs/report/0573--2026-11-22--wie-upstream-sync2-s2-backend-executor-sleep-deadline-cooperative-poll.md` §9 「영향 범위 — 정적」 표와 그 아래 문단 · `docs/worklog/2026-11-22-upstream-sync2-s2-executor-sleep-deadline-cooperative-poll.json` 의 `summary`. 이 회차는 그 둘을 고치지 않았다(티켓 범위 — 이름만).
