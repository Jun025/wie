- 판정: `7ca47380 → d92edc49` 는 두 표본 모두 **퇴행**이다(문턱 5 · 짝 재현). 나머지 29커밋은 문턱 아래 ok 다.
  - 구간 전체 +27.8% 중 +25.7% 가 이 한 커밋 몫이다. 남는 1~3% 는 문턱 아래라 더 가르지 않았다.
- 0527 숫자와 맞는다. `bd770b73` 대비 `7ca47380` +7~10%, `a90f1472` +32~41% 이고, 1.37 / 1.08 ≈ 1.27 이다.
- **무엇이 비싸졌나(코드 읽기 · 측정은 위 표)**: `d92edc49` 에서 엔진 크레이트에 들어온 것은 `wie-backend::SpeedClock` 모듈 하나다. 그것을 부르는 곳은 `wie_validate` 와 `wie_featurephone` 둘뿐이다(`git grep SpeedClock d92edc49`).
  `wie_validate` 의 `HeadlessPlatform::now()` 는 종전에 `SystemTime` → `Instant::from_epoch_millis` 였다. 이제는 `as_secs_f64()*1000` → `SpeedClock::now` 를 거친다(spin `Mutex` 잠금 + f64 앵커 계산 + 단조 `max`).
  host tick 마다 부르는 `clock.budget()` 도 같은 잠금을 한 번 더 잡는다.
- `wie_validate` 의 tick 은 `tick_for` 호출 1회다. 쉬는 표본은 모든 태스크가 잠들어 있어 tick 이 곧바로 끝난다. 50M tick 이 약 10 s 이니 tick 당 ≈ 110~200 ns 다.
  그 빈 tick 하나가 잠금 2~3회를 새로 잡는다. 거기서 ≈ +30~50 ns · +25% 가 나온다. 0527 이 «쉬는 J2ME 도 +37% 라 게임 경로로는 설명되지 않는다»고 적은 것과 맞는다.
- **고칠 것 없음 — 근거**:
  ⑴ 배포 네이티브 호스트 `wie_cli`(창)의 `now()` 는 이 구간에서 바뀌지 않았다. `SpeedClock` 을 쓰지 않는다.
  ⑵ 브라우저도 같은 시계를 거치지만, 아래 §3 에서 `7ca47380 → 26f79198`(이 커밋 포함) 구간의 paints 분포는 그대로다. 브라우저 tick 은 60 Hz 로 오고, 게스트 일에 비해 잠금 몇 번은 묻힌다(0527 §2 의 spin 64 와 같은 모양).
  ⑶ 이 축이 재는 것은 «빈 host tick 의 하네스 비용»이다. 게임 시간은 벽시계(`now()`)를 따르니 게임은 느려지지 않는다. 쉬는 표본에서는 바쁜 대기의 반복 수만 준다.
- 주간 감시에 남는 것: 다음 회차(10-25)의 A 는 `a90f1472` 라 이 계단은 다시 경보가 나지 않는다. 다만 이 축의 «+%» 가 하네스 시계 비용에 민감하다는 사실은 남는다(§5).
