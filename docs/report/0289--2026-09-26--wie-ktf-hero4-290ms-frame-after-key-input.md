## [2026-09-26] 영웅서기4(KTF) 키 입력 직후 긴 프레임 — 리소스를 읽을 때마다 돌던 전체 GC (wie-ktf-hero4-290ms-frame-after-key-input)

**무엇을**: KTF WIPI-C 의 `MC_knlGetResourceID` / `MC_knlGetResource` 가 리소스 바이트를 이름별로 캐시한다.
같은 이름을 다시 요청하면 JVM 을 거치지 않고 캐시에서 준다.

**왜**: 두 함수가 호출될 때마다 JVM 스트림을 열고 `collect_garbage`(한 번에 약 5.4ms)를 돌렸다.
영웅서기4 는 같은 이름에 대해 `GetResourceID` → `GetResource` 를 연달아 부르고, 화면이 바뀔 때마다 다시 부른다.
이 호출은 SVC 하나 안에서 끝나므로 ARM 선점이 쪼갤 수 없다. 이것이 제안 p0 가 말한 「선점이 닿지 않는 49~72ms tick」의 정체다.

**사용자 영향**: 메뉴·화면 전환 직후의 멈칫임이 줄어든다. 게임 동작은 같다(리소스는 읽기 전용 아카이브 항목이다).

### 판정 (계약 1) — 계측 추적 · `wie_validate --inject` · 프로파일러 패치는 커밋하지 않음

| 항목 | 값 |
|---|---|
| 부팅 이후 30ms 넘는 tick 16개의 시간 합 | 661ms |
| 그중 리소스 읽기 안의 `collect_garbage` | **382ms (58%)** |
| 가장 긴 tick 67ms(키 `03_LSOFT` 직후) | GC 8회 = 45ms |
| 화면 전환 프레임 203ms · 166ms | GC 가 132ms · 107ms (**65% · 64%**) |
| 실행 전체의 GC 호출 | 223회 — 서로 다른 이름 80개 · **같은 이름을 다시 읽은 것 143회(64%)** |

⇒ 원인은 **우리 스텁 비용**이다. 게스트 작업량이 아니다. 선점이 안 되는 이유는 GC 가 SVC 핸들러 안에서 동기로 돌기 때문이다.

### 전/후 (계약 2) — 같은 입력 · 교대 짝 base→fix→fix→base · load1 111~121

| | base-0 | fix-0 | fix-1 | base-1 |
|---|---|---|---|---|
| GC 호출 (다시 읽은 것) | 89 (49) | 44 (**4**) | 44 (**4**) | 63 (34) |
| 부팅 이후 GC 시간 | 1128ms | 398ms | 518ms | 960ms |
| 가장 긴 tick | 291ms (GC 7회 231ms) | 178ms (GC 0) | 224ms | 427ms (GC 8회 316ms) |
| 가장 긴 프레임 | 440ms (GC 268ms) | 323ms (GC 0) | 311ms (GC 0) | 246ms |
| 판정 | PASS · 입력 27/27 | PASS · 27/27 | PASS · 27/27 | PASS · 27/27 |

- **다시 읽는 GC 는 사라졌다**(49·34 → 4·4). 남은 4회는 없는 이름이다 — 없는 이름은 캐시하지 않는다(뒤에 생길 수 없지만, 캐시해서 얻을 것도 없다).
- 처음 읽는 이름의 GC 는 **남는다**(이름당 1회). fix-1 의 224ms tick 에는 첫 읽기 GC 5회가 들어 있다.
- ★**가장 긴 프레임 수치는 이 부하에서 결론을 주지 못한다.** base-1 의 최장 프레임(246ms)이 fix 두 회보다 짧다.
  load1 110 이상이면 GC 1회가 5ms 가 아니라 30ms 가 넘게 걸리고, GC 가 없는 프레임도 게스트 ARM 계산만으로 200~320ms 가 된다.
  fix 쪽 최장 프레임(323ms · 311ms)은 GC 0 이고 대부분 `arm=` 이다 — **선점되는 게스트 계산**이며 우리가 줄일 몫이 아니다.
- 브라우저 하네스(`fps`·간격 max) 재측은 하지 않았다. 필요하면 0255 의 하네스로 부하가 낮을 때 짝을 다시 잰다.
