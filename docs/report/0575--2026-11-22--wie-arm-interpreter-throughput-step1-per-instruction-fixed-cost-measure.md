**무엇을**: 측정과 선택지다. 해석기 · `arm32_cpu` 코드는 한 줄도 고치지 않았다. 넣은 것은 계측 도구
(`scripts/arm-interp-profile.sh` · `.mjs`)와 키 대본 1개(`docs/keys/lgt-3cc7a9b4cb15-intro-castle.keys`)뿐이다.

**왜**: 운영자 채택 제안 `2026-11-13-lgt-cadence-verdict-and-frames-painted#p0`(무거운 장면에서 시간의 약 80% 가 ARM 명령
해석 루프). 총괄 결정으로 제안 전체(노력도 L)를 한 번에 하지 않고 이 1단계 — 지금 수를 다시 재고, 명령당 고정비를

기준 초당 16.0 → 16.8~18.2 화면, 2배 느린 기기에서 9.5 → 10.0~11.2 로 오른다(모형 값 · §5).

### 1. 같은 장면을 다시 잰다 — 브라우저 저녁 마을 (할 일 1)

같은 스크립트에 넣으면 그때 수(12.08 s · idle 22.9% · 57.2%)가 그대로 나온다.

### 2. 네이티브 표본 — 실행 루프 안에서 어디에 쓰나

브라우저에서는 해석기가 wasm 함수 하나로 합쳐져 안을 가를 수 없다. 안은 네이티브 `wie_validate`(release + 줄 표)를
`xctrace` Time Profiler 로 떠서 가른다(0559 §4 의 방법 · 이번에 `scripts/arm-interp-profile.sh` 로 옮겼다). 장면은
네이티브로 닿는 가장 무거운 곳인 인트로 성 대화 첫 쪽이다(키를 기다리며 멈춰 있어 창을 어디에 잡아도 같은 화면).
빌드 둘: **main**(`08875c372`) · **main + #604**(네이티브에서도 `log` trace 를 빼는 열린 PR — 착지하면 이것이 main 이다).

`RUST_LOG=…kernel=debug` 로 게임의 프레임 표식(타이머 재무장 · 0557 §1)을 같이 찍어, 녹화 창 안의 «루프 표본 ÷
프레임 수»를 냈다. 부하에 흔들리지 않는 자는 이것이다 — 표본 수와 화면/초는 둘 다 부하를 따라 움직인다.

- ★**`trace!` 몫은 표본이 부풀렸다.** main 에서 5.13 ms 로 잡혔지만 뺀 빌드의 루프는 1.81 ms 만 줄었다. 나머지 3.3 ms 는
  바로 옆 코드(명령별 분기 +1.9 · shim +0.7 · 레지스터 +0.5 · 플래그 +0.5)의 시간이 그 줄로 미끄러져 찍힌 것이다.
  짧은 코드 한 줄의 표본 몫은 «줄일 수 있는 양»의 상한으로만 읽어야 한다. 이 회차의 예상 이득에는 이 비율(35%)을
  하한으로 붙였다(§5).
- 같은 쌍을 타이틀 메뉴에서 잰 것(부하 99~135 에서 키가 빠져 성까지 못 간 실행): 16.49 → 13.97 ms(−15.3%).
- 분해의 비율은 장면을 가리지 않았다: 캡처를 못 남긴 앞선 8회(성 · 내레이션이 섞임)에서도 해독은 23.9~27.5% 였다.
- 루프 밖: 표본의 24% 가 `mach_absolute_time`(네이티브 러너가 타이머를 기다리며 헛도는 몫 · 0559 와 같다).

### 3. 계수 — 명령 하나에 무엇이 몇 번

표본이 «어디»라면 계수는 «몇 번»이다. 우리 run 루프와 메모리 shim 에 세는 코드를 넣은 **버리는 빌드**(스크래치 트리 ·
커밋 0 · `arm32_cpu` 는 손대지 않음)로 벽시계 창 안의 실행을 셌다. 패치와 원자료는 저장소 밖 증거 폴더에 있다(§8).

| | LGT `3cc7a9b4cb15` 성 대화 첫 쪽(캡처 확인) | 같은 판 · 내레이션+성(창 70~95 s) | KTF `155972cac664` 키 없이 25~55 s |
|---|---|---|---|
| 센 명령 | 3.32억(프레임 172 → **프레임당 193.2만**) | 5.05억 | 4.99억 |
| Thumb 비율 | 99.69% | 99.95% | 100% |
| 해독 — 대조한 표 줄 수(21줄 중 평균) | **7.25** | 7.57 | 6.46 |
| 분기 사이 평균 길이 | 9.60 명령 | 7.30 | 21.55 |
| 메모리 shim 호출/명령 | **1.334**(인출 1 + 읽기 0.256 + 쓰기 0.078) | 1.328 | 1.232 |
| 실행된 주소 수 · 실행의 90% / 99% 를 덮는 수 | 6,831 · 140 / 2,007 | 22,207 · 56 / 1,383 | 6,973 · 231 / 1,726 |
| 블록 진입 주소 수 · 90% 를 덮는 수 | 977 · 37 | 3,363 · 9 | 886 · 47 |
| 실행된 적 있는 코드에 닿은 쓰기(§7) | 0 | 게스트 2 | 0 |

- 명령 종류(성 대화): Shifted 19.8%(표 4번째 줄) · ImmOp 16.6%(5) · **CondBranch 10.6%(18)** · AluOp 10.3%(3) ·
  SingleXferI 8.8%(10) · PcLoad 8.3%(7) · AddSub 7.3%(2) · HwXferI 6.2%(11) · HwSgnXfer 5.6%(9). 표의 첫 줄 `Branch` 는
  1.6% 다 — 대조 순서가 쓰임과 맞지 않는다.
- 코드를 읽어 센 고정 횟수(Thumb 명령 하나마다 · 종류 무관): 레지스터 파일 접근 **6회**(run 의 PC 1 · `thumb_mode` 의
  CPSR 1 · `execute_thumb` 의 PC 1 · CPSR 1 · PC 전진 읽기+쓰기 2 — 그중 5회가 `REG_MAP[bank][reg]` 두 번 찾기를
  거치는데 PC · CPSR 은 뱅크와 무관하다) · 인출 1회 · run 루프의 비교 3회 · `trace!` 2회(main) · 명령별 `match` 분기 1회.
- 계측을 켜면 이 장면이 초당 6.9 프레임으로 떨어진다(포화). 그래서 «초당 명령»이 아니라 «프레임당 명령»을 썼다.

### 5. 선택지 · 추천 (할 일 3)

예상 이득의 «위»는 §2 의 프레임당 ms 그대로, «아래»는 그 35%(§2 의 `trace!` 가 표본 몫 대비 실제로 준 비율)다.
기준 = main + #604 의 성 대화 20.98 ms/프레임.

- **⒜ 우리 쪽 호출부만(포크 없음).** 대상은 인출 경로(3.2 ms)와 run 루프(1.8 ms)다. 지금 인출은 명령마다 널 페이지
  검사 → 512KB 페이지 표 읽기 → `Option` 검사를 거친다. run 루프가 PC 의 코드 페이지를 한 번 풀어 shim 에 넘기면 같은
  64KB 페이지 안의 인출은 비교 1회로 끝난다(성 대화: 코드가 있는 페이지 8개). shim 구조체를 루프 밖으로 빼는 것까지
  **−0.7~2.0 ms(−3~10%)**. 회귀 그물은 기존 메모리 시험 6건 · 널 읽기 시험 · 러너 블록이면 된다. 크기 S.
- **⒝ `arm32_cpu` 를 저장소 안에 들여 해독을 표 한 번 찾기로.** Thumb 는 21줄의 마스크가 `Nop`(`0xbf00` 한 값) 말고
  전부 상위 8비트 안이라 256칸 표 하나면 된다. 해독은 명령 워드만의 함수라 **캐시가 아니고, 무효화가 없다**(§7).
  **−1.9~5.4 ms(−9~26%)**. 비용: 소스 2,312줄을 `patches/arm32_cpu` 로 둔다 — 이 저장소가 `patches/classfile` 로 이미
  하는 꼴(`[patch.crates-io]` · README 에 «버릴 조건»)이다. upstream(`dlunch/arm32_cpu`)은 2026-09-09 뒤로 움직이지
  않아 지금 동기 충돌은 0 이고, 새 릴리스가 나오면 변경(약 40줄)을 다시 얹는다. wasm 산출물이 바뀌므로 KTF · LGT 전
  타이틀이 대상이다 — 그물은 §6. 크기 M.
- **⒞ upstream 기여.** 같은 변경을 `dlunch/arm32_cpu` 에 PR 로. 그 저장소의 선례: 외부 정정 PR #2 는 3일 만에 머지
  (2026-08-18 → 08-21) · 성능 성격의 PR #1(한 줄)은 2026-08-11 부터 응답이 없다. upstream `wie` 는 해석기를 고치는 대신
  사전 번역(AOT)을 택했다(0559 §4). 기다릴 시간을 우리가 정할 수 없으므로 ⒝ 와 **병행**이 맞다 — ⒝ 의 README «버릴
  조건»이 «그 변경이 실린 릴리스»가 된다. PR 을 여는 일은 저장소 밖 행위라 운영자 몫이다.
- **⒟ 묶음 실행(블록 단위 사전 해독 · PC 키).** ⒝ 뒤에도 남는 명령당 고정비 — 인출 15% · run 루프 9% · step · 선행부
  8% — 를 블록당 1회로 줄인다(성 대화 평균 9.6 명령/블록 → 약 1/10). 위로 **−5.9 ms 추가**. 비용이 다르다: 새 계층
  (PC 키 캐시 · 쓰기 두 길의 무효화 · 선점 예산이 블록 단위가 됨 · 블록 중간의 SVC) + 전수 회귀(§6 — 132 임대 ·
  42시간) + 두 해석기를 맞대어 돌리는 도구 신설. 크기 L.

**추천: ⒝ — Thumb 해독 표.** 가장 큰 한 덩이(27%)이고, 같음을 전수로 증명할 수 있고(§6), 실행 중 바뀌는 코드와
만나지 않는다. 다음 조각의 크기는 **M**: 들이기(기계적) + 변경 약 40줄 + 전수 동치 시험 + 이 회차의 자로 전/후.
⒜ 는 독립이라 그 뒤나 옆에서 S 로 한다. ⒟ 는 ⒝ · ⒜ 뒤에 다시 잰 수로 판단한다.

⒝ 의 화면 효과(모형 값 · 0557 §3 의 식 `주기 = max(55, 걸린 시간 + 15)`): 브라우저 저녁 마을은 지금 프레임당 해석기
33.5 ms · 주기 62.7 ms(15.96 화면/초 · load1 98). −9~26% 면 주기 59.7~55 ms → **16.8~18.2 화면/초**(18.2 가 게임
본래 박자). 2배 느린 기기(0559: 9.5 화면/초 · 프레임당 해석기 약 62 ms)는 **10.0~11.2**. ★wasm 의 루프 구성은 직접 가르지 못했다 — 네이티브
비율을 그대로 옮긴 값이고, 다음 조각이 같은 브라우저 쌍으로 잰다.

### 6. 회귀 전수의 비용 · 무엇을 재면 «같다»고 말할 수 있나 (할 일 4)

| 선택지 | «같다»의 증명 | 비용 |
|---|---|---|
| ⒝ 해독 표 | 옛 `decode()` 와 표를 **가능한 워드 전부**에 대조: Thumb 65,536개 · ARM 은 마스크가 보는 24비트 16,777,216개 | `cargo test` 안 · 수 초 · 임대 0 · CI 가 매번 |
| ⒜ 인출 경로 | 메모리 시험(매핑 · 널 읽기 · 미매핑 쓰기) + 러너 블록 | 임대 0 |
| ⒟ · PC 키 캐시 | 판 단위로만 볼 수 있다 — 아래 | 아래 |

판 단위 전수의 수(지원 목록의 ARM 판 = KTF 269 + LGT 78 = **347판** · `--jobs` 3):

| 도구 | 판 × 초 | 한쪽 | 전/후 |
|---|---|---|---|
| `playability-census` 전체(탐침 30 s × 2 + longplay 600 s) | 347 × 660 s = 63.6 에뮬레이터-시간 | 21.2 시간 · 임대 66건 | **42.4 시간 · 132건** |
| 〃 탐침만 | 347 × 60 s | 1.9 시간 · 8건 | 3.9 시간 · 16건 |
| 맞대어 돌리기(그림자 대조와 같은 틀 · 30 s) | 347 × 30 s | 약 1 시간 · 6건 | 한 번이면 된다 |

- **census 는 «판정이 같다»까지만 말한다.** 벽시계로 돌아서, 같은 바이너리를 두 번 돌려도 실행이 다르다(바로 앞
  회차의 표본 10판: `status` 10/10 같음 · speed 축은 부하로 3판이 갈림 · 같은 판의 600초 틱 수가 0.38~1.65배).
  해석기를 바꾼 뒤의 «같다»를 census 로 말하면 그 잡음 폭 안의 차이는 못 본다.
- **«실행이 같다»를 말하는 도구는 오늘 없다.** `hook-shadow-sweep.sh` 는 훅과 게임 자신의 루틴을 견주는 것이라 해석기
  끼리는 견주지 않는다. 다만 그 틀(같은 상태에서 양쪽을 돌려 남긴 것을 비교)은 그대로 쓸 수 있다: `arm32_cpu::Cpu` 가
  `Copy + PartialEq` 라 명령마다 기준 해석기와 새 해석기의 레지스터 파일 · 쓴 메모리를 견주면 된다. 비용의 근거는
  그림자 전수의 실측이다(0565: 264판 × 30 s · 3개 동시 · 임대 5건 · 46분).
- ⒝ 에는 판 단위 전수가 필요 없다. 해독이 같으면 그 뒤 실행은 같은 코드다. 실기 확인은 러너 블록과 이 회차의 자
  (전/후 프로파일 · 브라우저 쌍)로 한다.

### 7. 범용 훅 · 바이트 패치와 해석기 캐시가 만나는 자리 (할 일 5)

**코드는 실행 중에 바뀐다 — 드물게, 그리고 두 길로만.** 설치 시점: 범용 훅(KTF 264판 · 872곳)과 잠금 해제 패치(8곳 ·
3판)는 전부 게임 진입점이 돌기 전에 메모리의 코드를 고친다(`wie-ktf` · `wie-lgt` 의 `init.rs`). 실행 중에 코드가 바뀌는
경우는 셋이다. ① `unhook` — 호스트가 통째로 해 줄 수 없는 복사를 만난 훅 자리에 원래 2바이트를 되돌려 쓴다(방금
실행된 자리다). ② 그림자 대조(개발 도구 · 네이티브 전용)는 훅이 불릴 때마다 그 자리를 되돌렸다 다시 덮는다. ③ 게임
자신: LGT `3cc7a9b4cb15` 는 이미 실행한 ARM 모드 2워드 연결 조각을 고쳐 쓴다(계수 창 20~25초에 2~4회 · 게스트 쓰기).
SVC 스텁은 실행 중에도 생기지만 늘 새 주소다(되쓰지 않는다). 빈도는 낮다: 실행된 코드가 있는 64KB 페이지에 닿은
쓰기가 5.05억 명령에 11회, 성 대화 3.32억 명령과 KTF 4.99억 명령에서는 0회였다 — 코드 페이지와 자주 쓰는 데이터가
섞여 있지 않다. 따라서 **명령 워드로 찾는 해독 표(⒝)는 이 문제와 만나지 않고**(주소가 아니라 워드가 키다), **주소로
찾는 캐시(⒟)만 무효화가 필요하다.** 그 조건은 «캐시가 덮은 페이지에 쓰기가 닿으면 그 페이지의 항목을 버린다»이고,
걸 자리는 둘뿐이다 — 게스트 쓰기(`Arm32CpuMemory::w8/w16/w32`)와 호스트 쓰기(`EmulatedMemory::write_range` — 훅 설치 ·
`unhook` · 패치 · 스텁 · 로더가 전부 이 길로 온다). 게스트 쓰기는 명령당 0.078회라 그 검사가 새 고정비가 된다.

### 8. 도구 · 재현

- `scripts/arm-interp-profile.sh <wie_validate> <game> <keys> <at> <out> [창]` — 키 대본대로 돌리며 `xctrace` 로 창을
  뜨고 표를 낸다. 한 번에 하나만(kperf 잠금) · `build-slot run --long` 으로 감싼다. 이 회차에서 걸린 것 셋을 머리말에
  적었다: 줄 표와 `.dSYM` 이 있어야 한다 · 실행이 녹화보다 먼저 끝나면 xctrace 가 멈춘다(그래서 스크립트가 실행을
  붙잡아 둔다) · **고정 시각의 창은 부하에 따라 다른 화면을 뜬다**(같은 대본의 두 실행이 80초에 하나는 성, 하나는 그 앞
  내레이션이었다 — 그래서 대본을 «첫 대화 쪽에서 멈춤»으로 바꾸고 캡처를 남긴다).
- `scripts/arm-interp-profile.mjs` — 집계. 묶음의 경계(해독 표 · `trace!` 문 · 우리 shim)를 줄 번호가 아니라 프레임이
  가리키는 소스를 읽어 정한다 — 다음 회차들이 고칠 파일이 바로 이 파일들이라서다. `selftest` 가 지어낸 export 로
  파싱과 묶음을 확인한다(참조 풀기 · `trace!` 묶음을 각각 망가뜨리면 red). 0559 의 원자료를 넣으면 그 표(8,575 표본 ·
  39.1% · 24.8 / 23.1 / 16.2 / 11.1 / 9.5)가 그대로 나온다.
- 계수 계측(버리는 패치 275줄) · 그 집계 · 원자료 · 브라우저 프로파일 집계는 저장소 밖
  `~/orchestrator/reports/evidence/wie-arm-interpreter-throughput-step1/` 에 있다. 패치는 `arm32_cpu.rs` 가 바뀌면 낡으므로
  저장소에 두지 않았다.

### 9. 한계

- 기기 1대(M1 Max) · 회차 내내 load1 20~135. 부하에 강한 자(같은 순간의 쌍 · 프레임당 ms · 프레임당 명령)만 썼다.
- 브라우저의 장면(저녁 마을)과 네이티브의 장면(성 대화)은 다르다. 네이티브로는 세이브를 넣을 길이 없다(0557 §6).
- 성 대화의 main ↔ #604 쌍은 1회씩이다(같은 쌍을 한 번 더 돌린 것은 부하로 메뉴에 머물렀다).
- wasm 안의 루프 구성은 가르지 못했다. §5 의 화면 효과는 네이티브 비율을 옮긴 모형 값이다.
- 줄 단위 표본은 옆 줄로 미끄러진다(§2 의 `trace!`). §4 의 «명령별 분기 8.0%» 같은 한 줄짜리 몫은 특히 그렇다.
- KTF 는 계수 1판 · 네이티브 프로파일 0판이다. 범용 훅이 걸린 KTF 판의 루프 구성은 재지 않았다.
- 프레임당 명령 수는 계측 빌드(느려진 실행)에서 셌다 — 느려져도 프레임 하나가 하는 일은 같다고 놓았다.
