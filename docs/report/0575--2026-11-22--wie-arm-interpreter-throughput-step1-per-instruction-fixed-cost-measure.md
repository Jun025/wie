### 5. 선택지 · 추천 (할 일 3)

기준 = main 의 성 대화 21.00 ms/프레임. **예상 이득은 «대상 묶음의 프레임당 ms» 에서 온 어림이고 바닥이 아니다** — 표본
몫과 실제 감소가 얼마나 맞는지 이 회차에 재 본 것은 #604 한 번이고(1.1~1.5배 · §2), 그 한 번을 계수로 옮기지 않았다.
그래서 각 선택지의 완료 조건은 예상치가 아니라 «같은 자로 잰 전/후(교대 3쌍)»다.

- **⒜ 우리 쪽 호출부만(포크 없음).** 대상은 인출 경로(2.96 ms · 14.1%)와 run 루프(1.76 ms · 8.4%)다. 지금 인출은 명령마다
  널 페이지 검사 → 512KB 페이지 표 읽기 → `Option` 검사를 거친다. run 루프가 PC 의 코드 페이지를 한 번 풀어 shim 에 넘기면
  같은 64KB 페이지 안의 인출은 비교 1회로 끝난다(성 대화: 코드가 있는 페이지 8개). shim 구조체를 루프 밖으로 빼는 것까지
  **−2 ms 까지(−10% 까지)** — 대상 4.7 ms 중 그 검사들과 구조체 생성분을 어림한 값이다. 회귀 그물은 기존 메모리 시험 6건 ·
  널 읽기 시험 · 러너 블록이면 된다. 크기 S.
- **⒝ `arm32_cpu` 를 저장소 안에 들여 해독을 표 한 번 찾기로.** Thumb 는 21줄의 마스크가 `Nop`(`0xbf00` 한 값) 말고
  전부 상위 8비트 안이라 256칸 표 하나면 된다. 해독은 명령 워드만의 함수라 **캐시가 아니고, 무효화가 없다**(§7).
  대상은 해독 묶음 5.13~5.47 ms(루프의 24.8~26.3% · main 3회)이고, 평균 7.25회의 대조가 1회가 되므로 그 1회분은 남는다:
  **−4.4~5.5 ms(−21~26%) 부근.** 이 범위의 근거와 한계 — ⑴ 같은 빌드 3회의 해독 몫은 좁다(24.8~26.3%) ⑵ 그러나 빌드가
  바뀌면 묶음 사이의 가름이 옮겨 다닌다: 같은 해독 코드가 직전 main 에서는 7.9 ms 로 찍혔고, 검수의 독립 빌드에서는 루프의
  31.6% 였다 ⑶ 실제 감소는 표본 몫보다 클 수도(#604 가 그랬다 — 이웃 코드까지 빨라졌다) 작을 수도 있다.
  비용: 소스 2,312줄을 `patches/arm32_cpu` 로 두고 `[patch.crates-io]` 로 건다(README 에 «버릴 조건»). 크레이트 저장소
  (`dlunch/arm32_cpu`)는 2026-09-09 뒤로 움직이지 않아 그 축의 충돌은 지금 0 이고, 새 릴리스가 나오면 변경(약 40줄)을 다시
  얹는다. **wie upstream 병합 쪽에는 걸리는 것이 둘 있다**(확인 2026-11-22):
  ① 선례가 사라진다 — 이 저장소가 지금 `patches/classfile` 로 하는 같은 꼴을, 열린 PR #605(RustJava 핀 올리기 · S1)가
  지운다(`patches/classfile` 13파일 + `Cargo.toml` 의 `[patch.crates-io]` 절 전체). #605 가 먼저 착지하면 ⒝ 는 그 절과 관례를
  새로 만드는 쪽이 된다.
  ② `upstream/main`(`24b670780`)은 `arm32_cpu = "^0.1.2"`(우리 `^0.1.0` · 잠금은 둘 다 0.1.2)이고 `[profile.web.package.arm32_cpu]`

  (빌드는 초록인 채 레지스트리 판으로 돌아간다). 그래서 ⒝ 에는 «패치가 실제로 쓰이는가» 가드가 같이 들어가야 한다 —
  예: `Cargo.lock` 의 `arm32_cpu` 항목에 `source` 줄이 없음을 시험으로 잠근다(경로 패치가 쓰이면 그 줄이 없다).
  wasm 산출물이 바뀌므로 KTF · LGT 전 타이틀이 대상이다 — 그물은 §6. 크기 M.
- **⒞ upstream 기여.** 같은 변경을 `dlunch/arm32_cpu` 에 PR 로. 그 저장소의 선례: 외부 정정 PR #2 는 3일 만에 머지

  사전 번역(AOT)을 택했다(0559 §4). 기다릴 시간을 우리가 정할 수 없으므로 ⒝ 와 **병행**이 맞다 — ⒝ 의 README «버릴
  조건»이 «그 변경이 실린 릴리스»가 된다. PR 을 여는 일은 저장소 밖 행위라 운영자 몫이다.
- **⒟ 묶음 실행(블록 단위 사전 해독 · PC 키).** ⒝ 뒤에도 남는 명령당 고정비 — 인출 14% · step · 선행부 13% · run 루프

**추천: ⒝ — Thumb 해독 표.** 가장 큰 한 덩이(루프의 4분의 1)이고, 같음을 전수로 증명할 수 있고(§6), 실행 중 바뀌는

### 6. 회귀 전수의 비용 · 무엇을 재면 «같다»고 말할 수 있나 (할 일 4)

| 선택지 | «같다»의 증명 | 비용 |
|---|---|---|
| ⒝ 해독 표 | 옛 `decode()` 와 표를 **가능한 워드 전부**에 대조: Thumb 65,536개 · ARM 은 마스크가 보는 24비트 16,777,216개 | `cargo test` 안 · 수 초 · 임대 0 · CI 가 매번 |
| ⒜ 인출 경로 | 메모리 시험(매핑 · 널 읽기 · 미매핑 쓰기) + 러너 블록 | 임대 0 |
| ⒟ · PC 키 캐시 | 판 단위로만 볼 수 있다 — 아래 | 아래 |

판 단위 전수의 수(지원 목록의 ARM 판 = KTF 269 + LGT 78 = **347판** · `--jobs` 3):

| 도구 | 판 × 초 | 한쪽 | 전/후 |
|---|---|---|---|
| `playability-census` 전체(탐침 30 s × 2 + longplay 600 s) | 347 × 660 s = 63.6 에뮬레이터-시간 | 21.2 시간 · 임대 66건 | **42.4 시간 · 132건** |
| 〃 탐침만 | 347 × 60 s | 1.9 시간 · 8건 | 3.9 시간 · 16건 |
| 맞대어 돌리기(그림자 대조와 같은 틀 · 30 s) | 347 × 30 s | 약 1 시간 · 6건 | 한 번이면 된다 |

- **census 는 «판정이 같다»까지만 말한다.** 벽시계로 돌아서, 같은 바이너리를 두 번 돌려도 실행이 다르다(바로 앞
  회차의 표본 10판: `status` 10/10 같음 · speed 축은 부하로 3판이 갈림 · 같은 판의 600초 틱 수가 0.38~1.65배).
  해석기를 바꾼 뒤의 «같다»를 census 로 말하면 그 잡음 폭 안의 차이는 못 본다.
- **«실행이 같다»를 말하는 도구는 오늘 없다.** `hook-shadow-sweep.sh` 는 훅과 게임 자신의 루틴을 견주는 것이라 해석기
  끼리는 견주지 않는다. 다만 그 틀(같은 상태에서 양쪽을 돌려 남긴 것을 비교)은 그대로 쓸 수 있다: `arm32_cpu::Cpu` 가
  `Copy + PartialEq` 라 명령마다 기준 해석기와 새 해석기의 레지스터 파일 · 쓴 메모리를 견주면 된다. 비용의 근거는
  그림자 전수의 실측이다(0565: 264판 × 30 s · 3개 동시 · 임대 5건 · 46분).
- ⒝ 에는 판 단위 전수가 필요 없다. 해독이 같으면 그 뒤 실행은 같은 코드다. 실기 확인은 러너 블록과 이 회차의 자
  (전/후 프로파일 · 브라우저 쌍)로 한다.

### 7. 범용 훅 · 바이트 패치와 해석기 캐시가 만나는 자리 (할 일 5)

**코드는 실행 중에 바뀐다 — 드물게, 그리고 두 길로만.** 설치 시점: 범용 훅(KTF 264판 · 872곳)과 잠금 해제 패치(8곳 ·
3판)는 전부 게임 진입점이 돌기 전에 메모리의 코드를 고친다(`wie-ktf` · `wie-lgt` 의 `init.rs`). 실행 중에 코드가 바뀌는
경우는 셋이다. ① `unhook` — 호스트가 통째로 해 줄 수 없는 복사를 만난 훅 자리에 원래 2바이트를 되돌려 쓴다(방금
실행된 자리다). ② 그림자 대조(개발 도구 · 네이티브 전용)는 훅이 불릴 때마다 그 자리를 되돌렸다 다시 덮는다. ③ 게임
자신: LGT `3cc7a9b4cb15` 는 이미 실행한 ARM 모드 2워드 연결 조각을 고쳐 쓴다(계수 창 20~25초에 2~4회 · 게스트 쓰기).
SVC 스텁은 실행 중에도 생기지만 늘 새 주소다(되쓰지 않는다). 빈도는 낮다: 실행된 코드가 있는 64KB 페이지에 닿은
쓰기가 5.05억 명령에 11회, 성 대화 3.32억 명령과 KTF 4.99억 명령에서는 0회였다 — 코드 페이지와 자주 쓰는 데이터가
섞여 있지 않다. 따라서 **명령 워드로 찾는 해독 표(⒝)는 이 문제와 만나지 않고**(주소가 아니라 워드가 키다), **주소로
찾는 캐시(⒟)만 무효화가 필요하다.** 그 조건은 «캐시가 덮은 페이지에 쓰기가 닿으면 그 페이지의 항목을 버린다»이고,
걸 자리는 둘뿐이다 — 게스트 쓰기(`Arm32CpuMemory::w8/w16/w32`)와 호스트 쓰기(`EmulatedMemory::write_range` — 훅 설치 ·
`unhook` · 패치 · 스텁 · 로더가 전부 이 길로 온다). 게스트 쓰기는 명령당 0.078회라 그 검사가 새 고정비가 된다.

### 9. 한계

- 기기 1대(M1 Max) · 다시 뜬 6회의 load1 13~50. 부하에 강한 자(프레임당 ms · 프레임당 명령)만 썼고, 같은 빌드 3회가 ±2%
  안이다. 브라우저 쌍(§1)은 1회이고 원자료가 없다.
- 브라우저의 장면(저녁 마을)과 네이티브의 장면(성 대화)은 다르다. 네이티브로는 세이브를 넣을 길이 없다(0557 §6).
- wasm 안의 루프 구성은 가르지 못했다. §5 의 화면 효과는 네이티브 비율을 옮긴 모형 값이다.
- 줄 단위 표본은 옆 줄로 미끄러지고, 같은 바이너리의 줄 번호도 녹화마다 다르게 풀린다(§2). 묶음의 합과 프레임당 ms 로
  읽어야 한다. §4 의 «명령별 분기 8.9%» 같은 한 줄짜리 몫은 특히 약하다.
- §5 의 예상 이득은 표본 몫에서 온 어림이다. 실제 값은 그 변경의 전/후를 재야 안다.
- KTF 는 계수 1판 · 네이티브 프로파일 0판이다. 범용 훅이 걸린 KTF 판의 루프 구성은 재지 않았다.
- 프레임당 명령 수는 계측 빌드에서 셌다. 두 속도(초당 6.9 · 17.8 프레임)에서 0.3% 안으로 같았다(§3).
