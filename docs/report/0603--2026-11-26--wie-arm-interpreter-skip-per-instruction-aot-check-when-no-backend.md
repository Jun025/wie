**왜**: 운영자 채택 제안 `2026-11-25-arm-interpreter-fetch-code-page-measured-not-landed#p0`(0599 §1 의 «옆에서 본 것»). S3 가 들여온

### 3. 두 후보를 같이 쟀다 — 깃발만 밖으로 빼기 · 루프 가르기 (계약 2)

기준 = main `39dbea741`(0600 의 Thumb 해독 표가 들어가 §1 보다 낮은 값에서 시작한다). 같은 트리에서 세 빌드를 짓고
기준 → 깃발 → 가름 순서로 3바퀴(9회 · 회마다 short 임대).

  세 번으로는 기준의 폭(±1.4%)과 가르지 못한다. 백엔드를 메모리에서 다시 읽지 않게 될 뿐 비교는 레지스터에서 그대로 남고, 그 빌드의
  디스어셈블에서는 예산 카운터가 스택으로 밀려 있다(`step` 뒤 `ldr w10, [sp, #0x50]` · `add`).
- **가르면 S3 가 얹은 몫이 통째로 빠진다.** run 루프 몫 2.93 → 1.71 ms(§1 의 S3 앞 1.72 ms). 프레임당 합은 −1.81 ms 로 그보다 크다 —
  나머지 0.6 ms 는 다른 묶음에서 빠진 것으로 찍히는데, 줄 단위 표본은 옆으로 미끄러지므로(0575 §2) 묶음 가름은 약하고 서는 수는 프레임당 합이다.
- 가름의 세 값은 폭이 넓다(14.37 ~ 15.91 · ±5%). 가장 적게 준 회(1바퀴 · load1 85)로 읽어도 −7.3% 다.
- **잰 빌드와 넣는 코드는 같은 기계어다.** 잰 «가름» 빌드는 주석과 시험이 없는 판이었다. 이 PR 의 소스로 다시 지은 `wie_validate` 의 `run`
  디스어셈블은 명령 851개의 열이 잰 빌드와 같다(`cmp` 로 대조 — 주소만 다르다).

**고른 것: 가름.** 계약은 «루프를 둘로 가르기보다 upstream 충돌 자리가 적은 쪽»을 먼저 보라고 했고, 그 쪽(깃발)은 재 보니 이득이 없다.
충돌 자리로도 가름이 적다:

| | upstream 의 `run` 본문에서 건드리는 자리 |
|---|---|
| 깃발 | 4곳 — 루프 앞 선언 1줄 · 검사 3곳의 조건식(이미 fork 줄) · 실행 실패 자리에 지우는 1줄(새 자리) |
| 가름 | 1곳 — 함수 맨 앞의 `if self.aot.is_none() { return … }`(주석 2 + 코드 3줄). 새 루프는 `impl ArmEngine` 앞에 따로 선 `impl` 블록이라 upstream 줄과 겹치지 않는다 |

값은 루프가 둘이라는 것이다(35줄이 겹친다 — SVC · 널 분기 · 끝 · 예산 · 미정의 명령 · 메모리 오류). 한쪽만 고치면 갈린다. 그래서 §4 의 시험을 둔다.

### 4. 시험 · 개악

새 시험 `the_loop_without_a_backend_stops_where_the_loop_with_one_does` — 같은 프로그램을 백엔드 없는 엔진과 «아무것도 컴파일하지 않은
백엔드가 붙은» 엔진(모든 명령을 upstream 의 루프가 해석한다)에 돌려, 멈춘 사유 · 쓴 예산 · 레지스터 17개가 같은지 본다. 7가지:
예산 0 뒤 예산 소진 · 끝 주소 도달 · 끝 주소와 예산 소진이 같은 순간(끝이 이긴다) · SVC(번호 · lr · spsr) · 미정의 명령(메시지 전문) ·
널로 분기 · 매핑 안 된 주소 읽기.

| 개악 | 결과 |
|---|---|
| M1 — 새 루프에서 예산 검사를 끝 주소 검사 앞으로 | **red 1건** — 새 시험(`"yield after 3"` ≠ `"end after 3"`) |
| M2 — 새 루프에서 SVC 가지를 뺀다 | 새 시험만 돌리면 **red**(`"Invalid memory access; address: 8"` ≠ `"svc 42 …"`). 크레이트 전체로는 끝나지 않는다 — 디버거의 SVC 걸음 시험 4건이 60초 넘게 돈다(9분에 죽였다 · green 아님) |
| M3 — 백엔드가 있어도 새 루프로 보낸다(`if true`) | **red 9건** — AOT 대조 · 무효화 · 진입 시험. 새 시험은 통과한다(백엔드가 아무것도 컴파일하지 않았으니 두 루프가 같은 일을 한다) |
| M4 — 백엔드가 없어도 새 루프로 보내지 않는다(`if false`) | green 179 — 틀려지지 않고 느려질 뿐이다(지금 main 의 동작). 이 갈래를 지키는 것은 시험이 아니라 §3 의 측정이다 |
| M5 — 새 루프에서 메모리 오류 검사를 뺀다 | 새 시험만 돌리면 **red**(`"yield after 10"` ≠ `"Invalid memory access; address: 1342177280"`). 크레이트 전체로는 AOT 대조 시험 1건(`native_branch_exchange_pc_loads_and_interpreter_handoffs_match`)이 끝나지 않는다(죽였다) |

고치지 않은 판은 `cargo test -p wie-core-arm --lib` 179 passed · 0 failed.

- 장면 1개(LGT 1판 · 네이티브) · 기기 1대 · 3바퀴. 측정 내내 다른 레인의 부하가 있었다(load1 6 ~ 105) — 그래서 프레임 수가 아니라
  «프레임당 루프 CPU»로만 읽었고, 회마다 장면을 캡처로 확인했다(15회 전부 기준 화면과 98.5% 이상 같은 바이트 · 인트로 화면은 38.9%).
- **long 풀을 쓰지 못했다.** 한 칸을 다른 저장소의 스위트가 이 회차 내내(55분 넘게) 쥐고 있었고 long 대기 상한은 3600초다. 프로파일 · 브라우저
  축 · `smoke_gate` 를 모두 phase 하나(≈ 3 ~ 6분)마다 short 임대 1건으로 돌렸다(0599 §6 과 같은 처지 · 같은 처분).
- `perf-watch.sh compare` 를 통째로 부르지 않고 그 `measure()` 가 부르는 phase 명령(`perf-watch.mjs resolve · run · judge · report`)을 같은
  인자로 직접 불렀다 — 위 이유(스크립트는 `--long` 임대가 박혀 있다)와, B 가 아직 커밋이 아닌 작업 트리라서다. 네이티브 축은 돌리지 않았다(§3 이 그 자리다).
- `smoke_gate` 는 «후» 빌드만 기준 목록과 대조했다. 0600 처럼 «전»을 같은 순간에 나란히 돌리지 않았다.
